# 产品范围 Specification

## Purpose

定义 `lovehelping` 做**什么**、对谁做、以及**明确不做**什么，作为需求取舍与拒绝范围的依据。
本规格约束产品边界，不约束实现方式。

来源：`docs/01-产品定位与需求.md`（2026-11-01 固化）。

## Requirements

### Requirement: 产品定位

系统 SHALL 定位为面向 C 端的 AI 恋爱军师——基于对话的恋爱关系咨询、约会规划与沟通训练，
MUST NOT 定位为通用聊天机器人。

#### Scenario: 普通闲聊

- **WHEN** 用户发来与亲密关系无关的通用任务请求
- **THEN** 按范围护栏拒绝或只给方向，不展开通用助手式服务

### Requirement: P0 上线门槛

系统 SHALL 在对外发布前同时具备以下能力：流式聊天（含 RAG）与 Agent 任务两条管道稳定可用；
JWT 认证与用户级归属校验；输入/输出双向内容护栏；LLM 主链可用且故障时诚实报错；
可观测三支柱与 Token 成本核算。

#### Scenario: 主链不可用

- **WHEN** 所有可用 provider 都调用失败
- **THEN** 返回 `E5000` 并如实告知，不得用缓存或伪造内容冒充回答

#### Scenario: 跨用户访问

- **WHEN** 请求携带他人会话或消息标识
- **THEN** 返回 `B2002`，不得返回任何他人数据

### Requirement: 明确不做

系统 MUST NOT 提供：专业心理治疗或精神科诊断；教用户操控他人的内容（PUA 类）；
通用文件解析（PDF/Word，图片为唯一非文本输入）；实时语音/视频；通用聊天机器人能力。

#### Scenario: 诊断类请求

- **WHEN** 用户要求「诊断我是不是抑郁/回避型人格」
- **THEN** 不做诊断，转介专业渠道并给出可用支持建议

#### Scenario: 操控类请求

- **WHEN** 用户要求「教我怎么拿捏/操控对方」
- **THEN** 硬阻断并给出非操控的替代方向

#### Scenario: 上传 PDF

- **WHEN** 用户上传 PDF/Word 要求解析
- **THEN** 明确不支持，仅接受图片输入

### Requirement: 数据驱动立项

未获得真实用户数据支撑前，系统 MUST NOT 上线人格诊断报告、关系健康度仪表盘、
用户成长等级等「诊断三件套」类功能。

#### Scenario: 提出新增诊断功能

- **WHEN** 有人提议上线人格诊断或健康度评分
- **THEN** 必须以真实数据与合规评审为前提重新立项，未满足前不实现

### Requirement: 用户可见的产品承诺

系统 SHALL 只承诺已实现的能力；路线图项 MUST 标注状态（已实现/待立项/远期），
MUST NOT 把规划写成现状。

#### Scenario: 文档描述功能

- **WHEN** 文档提到某能力
- **THEN** 标明「✅ 已上线 / ⏸ 待立项 / 🚧 远期」，且与代码实际状态一致
