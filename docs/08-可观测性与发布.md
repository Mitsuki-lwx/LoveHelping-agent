# 08 · 可观测性与发布

## 1. 三支柱现状

已有：actuator、micrometer-tracing-bridge-otel、OTLP exporter（Langfuse）、`MyLoggerAdvisor`。缺：指标体系、日志规范、告警。

## 2. 目标

### 2.1 日志规范

| 级别 | 场景 |
| --- | --- |
| INFO | 登录、会话创建、LLM 调用开始/结束（含耗时/provider/降级与否） |
| WARN | 重试、降级触发、护栏 L2、Agent 心跳超时 |
| ERROR | 降级链全失败、DB 异常、任务补偿标记 FAILED |

模板统一含 `%X{traceId} %X{tenantId}`。**生产禁 DEBUG；正文只打 content_hmac**（07 §6）。

### 2.2 指标（Micrometer → Prometheus → Grafana）

| 指标 | 类型 | 标签 |
| --- | --- | --- |
| `chat.request` | Counter | mode, status |
| `chat.first.token.latency` / `chat.latency` | Timer | mode |
| `llm.call` | Counter | provider, outcome(success/fallback/fail) |
| `llm.tokens` | Counter | provider, type(prompt/completion) —— 成本核算数据源 |
| `llm.latency` | Timer | provider |
| `rag.hit` / `rag.latency` | Counter/Timer | store —— 空结果率监控 |
| `skill.injection` | Counter | —— 进化模块效果 |
| `agent.task` | Counter | status, step_count 分桶 |
| `agent.queue.depth` | Gauge | 池健康 |
| `guardrail.trigger` | Counter | level, rule_id —— 误报率监控数据源 |
| `fallback.rate` | Gauge(窗口) | provider —— 告警主指标 |

**SLO**：聊天成功率 99.5%；降级触发率 < 5%；P95 首 token < 1.5s。

> **恋爱辅助 2 项（SRS §3.2，待立项）**：话术三级建议的**命中率/采纳率**、情绪刹车片的**触发率/误伤率**观测点在立项时定义（刹车片可能复用 `guardrail.trigger` 数据源——**待讨论**，04/06 同口径）。

> **已实现（2026-08-19，Phase 2）**：`llm.call{provider,outcome}`（LlmGateway）、`chat.request{mode}`、
> `guardrail.trigger{level,rule_id}`（ChatService）均已落码；`llm.tokens{type}` 已有。
> **可观测制品**：`ops/grafana/dashboards/lwx-ai-agent.json`（面板）+ `ops/grafana/alerting/lwx-ai-agent-alerts.yml`
> （Prometheus 告警，含错误率>5%、降级率>10%、L3 护栏激增、Agent 失败率等）。
> 其余目标指标（`rag.hit/skill.injection/agent.task/chat.latency`）为规划项——Grafana 面板先行，随实现补充。

### 2.3 追踪

SkyWalking **不引入**（已有 OTel 桥，避免双栈）。MDC 注入 traceId 已有基础；补：SSE 异步链路用 Reactor Context 传播，否则 trace 断在流式段。

### 2.4 Prompt 版本管理

- System Prompt 进配置中心/DB，带 `prompt_version`，随 message 落库（04 §2.2）。
- 所有指标可按 prompt_version 维度对比 —— 这是评估 Prompt 改动的唯一客观依据（配合 Golden Set，09 §4）。

### 2.5 LLM 质量观测

Langfuse 已接入：记录每次对话的 prompt/completion/成本/延迟，与 traceId 关联。用于抽样人工评审与回归对比，**不替代**结构化指标。

## 3. 发布

### 3.1 环境与配置

| 环境 | LLM | 数据 | 用途 |
| --- | --- | --- | --- |
| dev | Mock（WireMock 假 LLM） | 本地容器 | 开发 |
| test | 测试 Key 低配额 | testcontainers | CI |
| pre | 生产 Key，仅白名单账号 | 匿名化数据 | 上线前验证 |
| prod | 生产 Key | 真实（加密） | |

配置全部环境变量注入；Apollo/Nacos **暂不引入**（单应用环境变量 + Spring profile 足够，减少一个依赖）。

### 3.2 灰度（基于发布平台/网关能力，应用侧提供标签）

- 灰度键：固定百分位桶（`userId` 首次映射入桶后**不再移动**，避免旧计划的取模导致用户在版本间跳动）。
- 阶段：1%（2 天）→ 10%（3 天）→ 50%（2 天）→ 100%。观察：错误率、P99、点踩率、降级率、Token 成本环比。

### 3.3 回滚条件（触发任一即回滚）

- 错误率 > 5%，或 P99 较上版本 +50%；
- 点踩率相对基线 +30%；
- 降级率 > 10%。
- DB 变更遵循两段式（04 §5），保证回滚不连带数据回退。

### 3.4 CI/CD

GitLab CI（或 Jenkins）：编译 → gitleaks/依赖扫描 → 单测+集成（testcontainers）→ 镜像 → pre 部署 + 冒烟 → 手动审批 → 灰度。Golden Set 回归作为 Prompt 变更的独立流水线（调真实 LLM，低频触发）。
