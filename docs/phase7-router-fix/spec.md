# 路由规则漏判修复 —— 方案（spec）

## S1 `needTools`：把"位置约束"换成"三类信号"

**问题不是关键词不够，是匹配语义错了**（以 `.{0,5}` 开头 + 全串匹配 = 位置约束）。

被否方案：

| 方案 | 为什么否 |
| --- | --- |
| 只用 `contains`/`find()` 把原关键词表放宽到任意位置 | **引入新误判**：`天气 / 地图 / 最新` 这类**弱主题词**在情感叙述里很常见（"那天下雨天气很糟，他都没来接我"）→ 被判成要查天气 → 走 Agent 多轮 LLM，**比漏判更贵** |
| 直接调 Jev 判路由 | 别的问题；本轮的修复必须**零新增外部依赖**，且不能把一次网络往返加进每次请求 |

**采用方案**：把信号分三类，各管各的漏判面。

```java
// ① 强意图短语：语义上就是"去外部取信息"，出现任意位置即命中
STRONG = 搜索|搜一搜|搜一下|搜下|查一下|查下|查查|查询|查证|联网|上网查|帮我搜|帮我查|帮我找|帮我下载|下载图片|生成PDF|生成文件|搜索图片|导航到

// ② 动作 + 主题：动词与主题词必须**同句相邻**（≤8 字），挡住"天气"类的纯叙述
ACTION_TOPIC = (查|搜|找|看|问|了解|推荐|导航)[^。！？]{0,8}(天气|地图|路况|新闻|政策|最新|附近|票价|营业时间|餐厅|咖啡馆|酒店)

// ③ 原有头部主题词：**保持原样**（今天天气怎么样 / 帮我规划约会 这类短句照旧命中）
HEAD_TOPIC = ^.{0,5}(天气|地图|约会方案|帮我做|帮我规划|导航)
```

**为什么保留 ③ 的旧行为**：它虽然是位置约束，但对**短消息**（真实用户问天气的典型形态）是对的；
本轮只做"加召回"，不做"改判据"——减少"改了 A 坏了 B"的面。③ 带来的既有误判（叙述句里前 6 字含"天气"）
**本轮不扩大也不修复**，如实记在清单里。

## S2 `isAdviceRequest`：只补两种"要话术"的确定形态

```java
(有什么|有没有|有啥).{0,4}(说法|话术)                       // "有什么自然的说法"
(有什么|有没有|有啥).{0,4}(办法|方法|方式|招).{0,12}(回|聊|约|开口|说|追|挽回|道歉)   // "有什么办法能让他主动找我聊"
```

`说法 / 话术 / 开场白` 本身只属于沟通场景，误伤面小；
第二条要求"求方法"后**紧跟沟通动作**，挡住"有什么办法提高网速"这类域外请求。

**不采纳**更宽的做法（如把所有"有什么办法"都算话术）——那会把域外请求从 `normal` 拉进话术链，
而 `isOffTopic` 只锁工程/学术类，网不住它。

## S3 判据与验证

1. **单测**：把语料里与这两条规则相关的用例固化成测试（正例 + 负例），并保留原有正/负例不回归。
2. **反向对照实验**：改回旧实现 → 新测试**必须失败**，且失败项与预期症状一致；恢复后转绿。
3. **语料对照**：重跑 `RuleRouterDump` 与人工标签比对，准确率必须**上升且无新增错例**
   （在 `outputs/rule-router-*.json` 上记 before/after）。
4. **E2E**：真实聊天链路 §7.2/7.3（含工具意图路径）。
