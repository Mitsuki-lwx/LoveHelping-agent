# 03 · 技术决策记录（ADR）

> 格式：背景 → 决策 → 理由 → **代价/放弃了什么** → 状态。
> 争议未定的决策不允许进入路线图实施。

## ADR-1 检索栈收敛为「pgvector 单库 + 可选 ES」

**背景**：现状三套并存——Milvus+ES 混合检索（主用）、pgvector（备用）、内存 SimpleVectorStore（兜底）。向量总量目前为 3 篇 MD 文档 + 少量进化 Skill，<10^4 条。

**决策**：主路径收敛到 **PostgreSQL + pgvector**（HNSW 索引），关键词检索用 PG 全文检索（`tsvector` + 中文分词插件 zhparser，或降级为 pg_trgm）。**移除 Milvus 和 ES 依赖**。

**理由**：向量量级距离 Milvus 的收益区间（>10^7）差 3 个数量级；PG 已在栈内，少两个有状态服务 = 少两份备份/监控/故障域；Spring AI pgvector starter 官方维护。

**代价**：放弃 Milvus 的标量过滤性能和 ES 的 BM25 成熟度。若未来向量过千万，需一次迁移（Gateway 收口后迁移面可控）。

**状态**：已接受，路线图 Phase 1。

## ADR-2 线程池策略：有界队列 + Abort + 入口限流

**背景**：旧计划提出 chat 线程池用 CallerRunsPolicy「挤压触发限流」。

**决策**：聊天管道走响应式（Reactor）不设业务线程池；Agent 线程池队列有界 + `AbortPolicy`，过载在入口由限流器（Resilience4j/Sentinel）快速拒绝，返回明确的「系统繁忙」。

**理由**：CallerRuns 会让 Tomcat/SSE 线程亲自执行数十秒的 LLM 调用，几个积压任务即可占满 HTTP 线程池造成全站雪崩。过载保护必须发生在入口，而不是线程池兜底。

**代价**：高峰期部分 Agent 请求被快速拒绝，用户体验换取稳定性（配合前端重试提示）。

**状态**：已接受。

## ADR-3 Agent 任务持久化：任务表 + 扫描补偿，暂不引入 MQ

**背景**：现状 Agent 在内存线程池执行，进程重启任务静默丢失。

**决策**：新增 `agent_task` 表（状态机 PENDING→RUNNING→SUCCESS/FAILED/CANCELLED），提交即落库，执行器 CAS 抢占；启动时扫描超时 RUNNING 任务标记 FAILED 并支持用户侧重提。**不引入 MQ**。

**理由**：当前量级下 MQ 是过度设计；任务表 + 补偿已覆盖崩溃恢复、审计、成本核算三个需求。

**代价**：单机执行（多实例需分片或分布式锁）；轮询兜底体验一般——主路径改用 SSE 推送进度，轮询仅作断线恢复。

**状态**：已接受，路线图 Phase 2。

## ADR-4 消息内容加密：应用层 AES-GCM，密钥按租户派生

**背景**：旧计划提出 AES-256+Jasypt 全局密钥，Service 层解密。

**决策**：`messages.content` 应用层 AES-256-GCM 加密，数据密钥 = HKDF(主密钥, tenantId)，主密钥仅存环境变量/KMS；`content_hash` 用 HMAC-SHA256(盐) 防等值探测。**Embedding 前提**：进入检索库的内容必须是用户已同意贡献且经人工/门控审核的 Skill 文本，而非原始私信——原始私信永不向量化。

**理由**：全局单密钥下内部人员可解密全部用户私信，对情感类产品不可接受；按租户派生把爆炸半径限制在单租户。

**代价**：牺牲 SQL 层全文检索能力（对私信做关键词搜索需另行解密索引）；密钥轮换需要重加密迁移脚本。

**状态**：已接受，路线图 Phase 3。

## ADR-5 用户删除权级联到向量库

**背景**：旧计划称「软删会话但不删向量」。

**决策**：注销/删除请求级联：MySQL 软删 → 定期物理清除任务 → **同步删除该用户产生的所有向量和 Skill**。仅当用户在协议中明确同意「匿名贡献知识库」且内容经审核脱敏的 Skill 才豁免。

**理由**：《个保法》第 47 条删除权；向量是从私信衍生的个人信息。

**状态**：已接受（合规 P0）。

## ADR-6 情绪护栏：梯度响应，不做一刀切断言

**背景**：旧计划的「夜间+负面词+情感分三条件全满足则阻断不调 LLM」误伤核心场景（深夜倾诉恰是高价值用户）。

**决策**：三级梯度：
1. **L1 软提示**：检测到情绪激动信号，不改回复，System 注入「优先共情」指令；
2. **L2 降温**：仍调 LLM，回复前置一段关怀文案，并给出改写建议（「你从来不管我」→「我需要你多关注我」）；
3. **L3 硬阻断**：仅限明确自伤/伤人/违法关键词，返回转介资源，记录 `guardrail_event`。

规则外置可配置（DB 表，非硬编码正则），上线先灰度观察误报率，L3 关键词清单需人工复核。

**代价**：实现复杂度高于一刀切；需要误报率监控闭环。

**状态**：已接受，路线图 Phase 2。

## ADR-7 LLM 降级链：删除响应缓存与本地语料兜底

**背景**：旧计划含 `llm:cache:{promptHash}` 与「本地高频问答语料兜底」。

**决策**：降级链只保留三级——DeepSeek（指数退避重试 3 次）→ DashScope（主备切换）→ 诚实报错「服务暂不可用」。**删除响应缓存**（聊天 prompt 含全量历史，命中率趋零且语境错配风险高）；**删除本地语料兜底**（开放对话中预置话术=答非所问，伤害大于延迟）。

**状态**：已接受。

## ADR-8 删除未使用依赖，Agent 框架维持手写

**背景**：`spring-ai-alibaba-agent-framework` 已引入未使用；手写 ReAct 已稳定运行。

**决策**：删除该依赖与 Kryo 等未使用项。Agent 循环维持手写实现，理由：逻辑透明、可完全掌控护栏与状态持久化插入点；待其与 Spring AI Graph 能力（状态持久化、检查点）确有需求差距时再评估迁移。

**代价**：自维护 ReAct 循环的维护成本；放弃框架社区的现成特性。

**状态**：✅ **已落地（2026-08-20）**。采用 **spring-ai-alibaba-agent-framework 1.1.2.0 的 `ReactAgent`** 替换手写 ReAct 循环：
- 新执行核心 `infrastructure/ai/AgentLoopExecutor`：`ReactAgent.builder().model(llmGateway).tools(全量工具).saver(RedisSaver).compileConfig(recursionLimit=15)`；
- **checkpoint 分层**：RedisSaver（graph-core 内置，Redisson 独立客户端）存单次 run 执行断点；任务级可靠性仍由 MySQL `agent_task`（心跳+幂等+FAILED 重提）兜底；
- **保留**：LlmGateway 注入、agent_task 状态机（ChatService 完成回调驱动）、message 表对话记忆（窗口注入+落库）、SSE 桥接（文本分块模拟流式 + 🔧 工具调用可视化）；
- **删除**：手写 `BaseAgent/ReActAgent/ToolCallAgent/LoveManus/AgentState`（2026-08-20，同一 PR）；
- **版本**：spring-ai-alibaba-bom 1.1.2.0 引入（starter-dashscope 保持 1.1.2.2 混用，编译/上下文验证通过）；Redisson 3.24.0（netty 对齐 4.1.132.Final、rxjava 3.1.12，离线依赖对齐）。
- 功能口径不受影响：智能体 3 项能力已实现并进入 SRS（11 §3.3 FR-AGENT-01/02/03）。
- **修订（2026-08-25/26，见 ADR-19）**：业务编排图（OrchestrationGraph）落地后，入口职责从 ChatEntry 两条路径收编为单图；ReactAgent 自 AgentLoopExecutor **退役（2026-08-26 已删除该类）**，其图底座（StateGraph/RedisSaver/interceptors）内化为业务图的一部分，工具循环由自绘 AgentLlmNode⇄AgentToolNode 承担。本 ADR 的"采用 ReactAgent"结论已被 ADR-19 的"自绘业务图"取代。

## ADR-11 多模态：仅图片理解，通用文件解析不做

**背景**：用户提出识别图片/文件。核心场景是「聊天截图分析」（配图问"他这话什么意思"），而非文档解析。

**决策**：接入 DashScope `qwen-vl-max` 视觉模型（复用现有 DashScope starter，目前仅用其 Embedding）。LlmGateway 按消息模态路由：含图 → qwen-vl，纯文本 → DeepSeek。限制：单条消息 ≤4 张图、仅 JPG/PNG/WebP、服务端压缩至长边 2048px（视觉 token 昂贵，成本靠此控制）。**不做** PDF/Word 等通用文件解析——无核心场景支撑，徒增攻击面（PDF 漏洞、压缩炸弹）与成本；未来诊断功能需要聊天记录导出文件时，限定单一格式 + 大小上限 + 病毒扫描再评估。

**代价**：视觉 token 成本显著高于文本；两模型回复风格一致性需 Golden Set 增加含图用例覆盖。

**状态**：已接受，路线图 Phase 2（依赖 LlmGateway 先落地）。

## ADR-12 沙盘二次元人格：原创原型角色，规避既有 IP

**背景**：用户希望沙盘单独提供「二次元」风格人格。扮演现有动漫/游戏角色（名字、形象、标志性台词）有著作权与反不正当竞争风险，国内已有 AI 扮演知名角色的败诉判例。

**决策**：沙盘为**同一功能下的双通道**（`REALISTIC` 真人模拟 / `ANIME` 二次元预设），不单开产品入口，实现成本最低。角色库全部原创：以不受版权保护的**角色原型**（傲娇/天然呆/三无/元气等类型学标签）为基础，配自创名字与 AI 生成头像。三条硬规则：
1. AI 生成头像等图片加**显式标识**（《人工智能生成合成内容标识办法》，2025-09 施行）；
2. 护栏拦截「扮演 XX（知名角色名）」请求并引导至相近原型；生成图禁用「某画师风格」类 prompt；
3. 带陪伴属性的功能配**未成年人防沉迷与使用时长提醒**。

**代价**：放弃知名 IP 自带流量；原创角色库需持续运营投入（人设文案、头像生成、原型×场景组合测试）。

**状态**：已接受；沙盘归入**远期附录**（按数据决策立项，SRS §6）；立项前置 = ADR-9（人格一致性）与本 ADR 同时定稿。

## ADR-13 多租户降级保留：tenant-ready，冻结完备性投入

**背景**：租户体系（tenant_id 列、TenantContext、JWT 租户声明、TokenController）建于项目早期，动机偏架构学习与展示；实际产品是 C 端单租户形态，无任何 B 端客户。Phase 0 发现的四个安全漏洞全部与租户隔离相关——复杂度全付了，安全性没拿到，是"半成品租户"最坏的状态。

**决策**：**降级保留，不追加投入**。
- **保留**：tenant_id 列（固定 `default`）、TenantContext、JWT 租户声明——地基近乎零成本，保持 tenant-ready；
- **冻结**：MyBatis-Plus 租户插件、向量租户过滤等完备性工程（ADR-4 的按租户派生密钥在单租户下自然退化为单密钥，无需改动）；
- **删除**：`TokenController`（Phase 0 已上锁，Phase 1 移除；调试统一走 `/auth/login`）；
- **口径调整**：限流从租户级改为**用户级**；对抗测试与验收从"跨租户"改为"**跨用户（IDOR）**"——用户 A 不能看用户 B 的数据，这条与租户无关，永远是 P0。

**重启触发条件**（任一出现即重新立项，恢复 07 §3 的隔离收口清单）：
1. 真实 B 端客户要求数据/品牌隔离；
2. 白标（贴牌）运营需求；
3. 合规要求分人群隔离。
重启前先确认客户要的是"共享库行级隔离"还是"独立部署"——两者成本结构完全不同，别默认前者。

**代价**：若 B 端以行级隔离形态落地，隔离工程要在存量数据上补做（当前数据量小，成本可控）；展示/面试维度仅保留最小可论证范围——"做过、评估后冻结、能说清何时重启"本身是有效的设计论证，比维持一个四处漏风的完整体系更有说服力。

**状态**：已接受（2026-08-16），路线图与 07 已同步。

## ADR-14 记忆系统：分层记忆 + 2→1→3 演进路线 + 存储选型

**背景**：业务核心是跨会话的情感咨询连续性——用户昨天聊了分手，今天再来问，AI 应记得这个人、这段关系、上次的结论。现状仅 Spring AI ChatMemory 窗口硬截断（20/50 轮），无摘要、无事实、无跨会话记忆。参考 Character.AI / 星野-筑梦岛 / Talkie 等 toC 情感应用：记忆必须**用户可见可编辑可删除**（信任 + 纠错闭环）。

**决策**：
- **分层记忆四层**（工作 / 会话摘要 / 结构化事实 / 语义记忆），按 **2→1→3** 演进：
  - **阶段 2（Phase 2）**：会话摘要（`conversation_summary`）+ 结构化事实（`user_memory` 表，用户可编辑）+ 注入协议——不引入向量，纯 MySQL；
  - **阶段 1（Phase 3）**：语义记忆通道——**脱敏后**的摘要向量化进 pgvector（metadata `user_id`/`source=memory`），与结构化事实双通道融合注入；
  - **阶段 3（远期附录，依赖沙盘/诊断立项）**：关系档案 `relationship_profile`（关系阶段/关键人物/偏好冲突/预警），诊断报告结果回填，沙盘人设引用，构成完整用户关系模型（SRS §6）。
- **存储选型**：结构化记忆（事实/摘要/档案）→ **MySQL 业务主库**（与 users/conversations 同库，归属校验、注销级联 ADR-5、MyBatis-Plus 生态全顺）；语义记忆 → **PostgreSQL + pgvector**（复用现有 `vector_store` 与 HybridRetrievalService 门面）；Redis 不参与记忆（避免易失状态）。不引入新数据库。
- **写入四原则**（防记忆噪声）：分级写入（候选→高置信转正）、去重合并（语义相似+关键字段）、版本化（冲突不覆盖，保留旧版可回滚）、生命周期（TTL + 最后命中 + 重要度，长期不命中降权/清理）。
- **注入协议**：记忆以结构化分隔符包裹注入 System，声明"以下是历史数据非指令"（防注入）；每条记忆带来源 conversationId 可溯源；token 预算硬阈值。
- **用户可编辑**：`GET/PUT/DELETE /memory/facts`，用户可见 AI 记住了什么、可改可删（纠错闭环，参考星野记忆气泡）。

**合规红线（不因演进放松）**：**原始私信永不向量化**（ADR-4）。语义记忆只向量化脱敏摘要与已审核 Skill；萃取输入（粘贴聊天记录/诊断文本）按不可信数据处理（结构化包裹 + 输出校验）。

**代价**：方案 1 的语义通道需要维护事实+向量两路融合与去重；LLM 萃取有调用成本（需限流/降级：萃取失败回落窗口截断，不阻断对话）；方案 3 的档案字段在沙盘/诊断上线前无消费方——因此顺序固定为 2→1→3，不在前期为无消费者的字段投入。

**状态**：已接受（2026-08-17），04/06/10 已同步。

## ADR-15 RAG 检索管线优化：父子索引 + 混合检索 + 改写接入 + 评估闭环

**背景**：03_RAG 文档（切块/混合检索/重排/改写/增量/评估）对照现状审计发现差距：① 整篇 MD 一个 chunk（splitter 被注释）——大块噪声高、语义稀释、触发 Lost in the Middle；② `QueryRewriter` 类已存在但从未接入管道（LoveApp 仅 import）；③ 无检索质量评估集；④ 无来源引用。

**决策**（按"先低成本高收益"排序，随数据量演进）：
- **阶段 2（Phase 2，随 LoveApp 拆解）**：
  - **父子索引（small-to-large）**：父块按章节切（~1500 token），父块内切子块（~400 token）embedding 入库、metadata 存 `parent_id`；检索命中子块 → 回查父块全文注入。一次解决"块太大稀释"与"块太小断裂"两个问题；
  - **QueryRewriter 接入管道**：单轮改写（补指代、规范术语、拆复合问题，约束：不改意图/不引入新事实/保留实体词——03 文档"改写为检索服务"原则）；
  - **来源引用**：RAG 回复携带 metadata 来源（文档名/段落），可解释性。
- **阶段 3（Phase 3）**：pg_trgm 混合检索 + RRF（见 ADR-1 更新）；建检索质量回归集（Recall@K + 人工抽检，进 09）。
- **阶段 4+**：rerank 模型（bge-reranker 中文，召回 Top50→重排 Top5）；增量更新（content_hash 只重建变更）+ 索引版本化（蓝绿）——数据量/文档变更频率上来后触发。

**代价**：父子索引需要自定义 DocumentTransformer（Spring AI 无开箱实现）与向量表新增 `parent_id` 元数据；QueryRewriter 每轮多一次 LLM 调用（需控频/可关）；评估集维护成本。

**状态**：已接受（2026-08-17），06/09/10 已同步。

## ADR-16 图数据库：明确排除（当前业务形态不需要）

**背景**：评估是否需要引入知识图谱/图数据库承载关系数据。

**决策**：**不引入**。理由（2026-08-17 评审）：
- 业务关系为**单边稀疏型**：单用户关系网络 ≤10 节点（自己/对象/前任/家人），关系深度 ≤2 层，无"沿关系链多跳查询"的产品需求；

## ADR-17 模型调用抽象策略：对话走 Spring AI ChatModel，视觉走自建 VisionPort

**背景**：项目存在两种 LLM 调用形态——对话经 LlmGateway（Spring AI `ChatModel` 装饰器），视觉为手写 OpenAI 兼容调用（`VisionChatClient`，因外部端点 Media 编码不兼容而绕开 Spring AI）。需明确未来接入 Anthropic 等供应商时的抽象策略，避免重复抽象或抽象泄漏。

**决策**：
- **对话层不重复抽象**：Spring AI 的 `ChatModel` 已是统一抽象（OpenAI/Anthropic/DeepSeek/本地 vLLM 均为其实现）；接入 Anthropic = 加 `spring-ai-starter-model-anthropic`，将其 `ChatModel` 注入 LlmGateway 做主/备，业务层零改动。LlmGateway 承担路由/降级/计量。
- **视觉层新增 `VisionPort` 接口**（唯一手写部分）：`String chat(prompt, List<byte[]> images, String mime)`，`VisionChatClient`（OpenAI 兼容）为其当前实现；未来 Anthropic 视觉（`/v1/messages`）新增 `AnthropicVisionClient implements VisionPort`，业务层（ChatService）依赖接口不变。

**代价**：多一个接口的维护成本；视觉实现仍绑定 OpenAI 协议细节（data URL），但被接口隔离。

**状态**：已接受（2026-08-18）。

## ADR-18（提议）话术三级建议：结构化生成 + 伦理边界，借 ADR-6 L2 体系

**背景**：用户核心诉求 FR-CORE-01 是"不知道怎么说话"——沟通卡壳。现有聊天只给单条建议，用户没有可选的说话方案。路线图要求做法前"先立 ADR（实现路径/伦理边界）"，且该能力是"给用户的选择"而非操控工具，伦理边界必须先行。

**决策**：
1. **实现路径**：话术三级以**系统提示词规则**为唯一生成机制（`ChatExecutor.SYSTEM_PROMPT` 现有三牌指令，简单、零新增数据库/管道），SSE 输出按约定**结构化标记**（三牌各一段，附"对方可能反应"），**不做**模板库 DB 化管理（远期演进，spec 已列入 Out of Scope）。触发识别借 CapabilityRouter 的 `needTools` 关键词通道判断"沟通建议请求"（怎么回复/说什么/如何开口 等），命中后在 system prompt 追加激活指令。
2. **触发优先级（生态内排序）**：L3 硬阻断 > 情绪刹车片（L2，FR-CORE-02）> 话术三级。即：话术请求若含 PUA/操控/伤人意图，L3 直接拒绝，不生成三牌；深夜极端情绪先走刹车片冷静提示，不叠加三牌。
3. **结构化输出**：话术请求的 SSE 事件升级为结构化 JSON（`{"type":"advice","tiers":[...]}`），非话术回复保持纯文本。前端可据此渲染/让用户单牌编辑措辞（CAP-2），并回传用户选择（喂 CAP-6 指标）。结构化在 ChatExecutor 层将当前纯文本切片为三牌块实现，SSE 桥接保持兼容——向后兼容纯文本，新增 advice 事件是增量。
4. **伦理边界（不因自动化放松）**：
   - 三牌是**给用户的选项**，非操纵对方的话术；system prompt 明示"authentic 沟通，not control the other person"；
   - 涉及拿捏/操控/打压/PUA 的生成请求由 L3 护栏兜底拒绝（ADR-6）；
   - 每牌只描述"对方可能反应"（可能性，不保证结果），避免给用户确定性的操纵预期；
   - 不生成引导撒谎/伪装身份/软性操控的内容。

**理由**：成本最低（纯提示词 + 入口路由，无新表/无新模型调用）；天然借 ADR-6 护栏梯度兜底；话术是即时生成价值，无需沉淀数据即可用；结构化标记让前端与指标闭环成为可能。

**代价**：LLM 生成的三牌格式有波动（emoji/分段不严格一致），前端需容错解析；触发关键词是启发式，可能漏触发（没法术）或误触发（本非话术请求却给三牌，靠"先澄清问题"原则对冲）；放弃结构化学模板库的确定性——远期若数据验证价值再立项（ADR-16 触发条件）。

**状态**：✅ **已接受 + 已落地（2026-08-25）**，实施见 phase4-advice 三件套：
- `CapabilityRouter.isAdviceRequest`（关键词通道，独立于 needTools）+ `ChatEntry` 计 `advice.request`；
- `ChatExecutor` 5 参 execute：命中后追加激活段（显式声明优先于"先澄清问题"原则）+ 流尾按 🛡️/⚡/🌸 切片出结构化 tiers（`advice.activated`，切不出降级纯文本）；
- SSE 桥接：`event: advice` 命名事件（含 `type/tiers/content/reaction`），非话术请求流与旧版一致（增量协议，05 §3.1）；
- 护栏补 `V17` 操控意图 L3（怎么/如何+操控动词+直接接人），防御性查询不误伤；
- E2E 冒烟固化 7.9 段（三牌≥3 + advice 事件 + PUA 阻断 + 无误伤），15/15 全绿。

## ADR-19（提议）业务编排图：自绘 StateGraph 统一聊天入口，工具循环图内化

**背景**：入口三裂——`ChatEntry` 两条路径（普通→ChatExecutor / 工具意图→ReactAgent）+ 沙盘独立通道（`/sandbox/chat` 直连 ChatExecutor，不走统一入口、不带工具）；`RetrievalAugmentationAdvisor`（RAG advisor）只存在 QueryRewriter 类、未接线；ReactAgent 是框架黑盒（内部图不可见、业务语义节点无从插 hook）。用户要求 LangGraph 式业务编排：开始→简单问题判定→（沙盘/其他）分支→处理节点→统一检查节点→工具循环→END，且要"高级可观测、方便修改、加 hook"。

**决策**（best judgment，待 phase5-orchestration 三件套评审）：
1. **自绘业务 StateGraph（`OrchestrationGraph`）成为唯一聊天入口**（含沙盘），节点：`start → 简单判定 → 类型路由（沙盘/普通/Agent）→ 对应处理节点 → 统一检查节点 → 有工具?（是→工具执行→回处理节点）→ end`；条件边用 `addConditionalEdges`。
2. **工具循环图内自绘**：LLM 节点 ↔ 工具节点条件边循环，组件复用 agent-framework 的 `AgentLlmNode/AgentToolNode`（图底座与节点组件内化）；**ReactAgent 自 AgentLoopExecutor 退役（删除）**，其 RedisSaver checkpoint/interceptors 迁移为业务图的 CompileConfig 与节点拦截器。
3. **简单问题判定用规则**（扩展现有 CapabilityRouter 关键词通道，零 LLM 成本、可单测），误判由统一检查节点与 hook 观测兑冲。
4. **沙盘收编为图内模式节点**（人格 prompt + 沙盘记忆 + 动态情绪保留），并**接完整 RAG**（普通/沙盘节点挂 RetrievalAugmentationAdvisor + QueryRewriter，修复现状 gap）。
5. **可观测与 hook**：节点级拦截器（pre/post enter/exit、工具前后、错误、结束）+ 每节点耗时 metric + 图路径 tracing + 状态快照日志。
6. **兼容**：SSE 协议不变（`event: advice` 保留）；`agent_task` 状态机、`message` 表记忆、LlmGateway、护栏梯度全部保留为图内组件。

**代价**：重构面大（删除 ChatEntry 路由职责、沙盘独立通道与 ReactAgent，一个 Phase 完成符合 AGENTS.md 不并行原则）；自绘工具循环需重测工具消息流收敛性（终止工具、消息聚合、checkpoint 语义）；已封装的 ReactAgent 能力（终止调度/错误兜底）需图内等效重建或复用组件；规则判定简单问题有误判面（由检查节点承担）。

## ADR-20（提议）后台调度预算约束：后台任务不得与在线请求争抢 LLM 配额

**背景**：2026-09-01 Langfuse 全链路测评实测——20 分钟内后台调度产生 89 次 embedding + 6 次 chat LLM 调用（记忆萃取/技能反思调度器），同期真实用户请求仅 1 次；单轮 `memory-extraction` 任务 p50=39.5s、max=118.7s。三重后果：①LLM 成本与配额几乎全部被后台消耗（在线请求 429 的主要来源）；②调度 trace 刷屏（占 99%），把在线请求的有效监控数据挤出 Langfuse 查询窗口；③长时间占用线程池。根因：调度器的节奏（5min/30min）与批量上限（10/20）是编码期拍定的常量，与"每分钟允许消耗多少 LLM 配额"这一真实约束无任何关联，且彼此独立、无共享预算。

**决策**（best judgment，待 phase5-scheduler-throttle 三件套评审）：
1. **集中预算组件 `SchedulerBudget`**：调度器统一向它"问询"（能否执行、本轮允许处理几个、每次 LLM/embedding 调用前扣减），业务逻辑（萃取什么、反思什么）不变。
2. **可配置、有默认、可关停**：`app.scheduler.*`（master 开关/单调度器开关/节奏/批量/每分钟 LLM 预算/单轮时间预算），默认值对现有行为无回归；排查与压测时 `master-enabled=false` 一键静默。
3. **空转指数退避**：连续无候选 → 实际间隔 ×2（封顶 8 倍），出现候选立即复位。
4. **fail-open**：预算组件自身异常时放行并告警——后台节流绝不阻断既有功能。
5. **可观测**：每轮输出候选数/处理数/LLM 调用数/耗时（指标 + 日志），后台消耗可量化。

**被否方案**：a) 引入 MQ 削峰——单机部署徒增复杂度；b) 直接关停进化模块——功能有价值，错在无预算；c) 跨实例分布式限流——ADR-13 多租户冻结，单进程令牌桶足够。

**代价**：记忆/技能的后台沉淀速度变慢（高峰期可能延迟数轮），可通过调大 `llm-budget-per-minute` 补偿；预算配置引入新的运维面。

**状态**：提议（2026-09-01），实施见 `docs/phase5-scheduler-throttle/` 三件套。
