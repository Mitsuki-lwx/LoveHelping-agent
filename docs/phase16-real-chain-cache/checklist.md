## D. 被推翻的三个解释（每条都有对照实验）

- [x] **D1** ❌ **「advisor 注入顺序断了前缀」—— 证伪**
      对照实验 I/J/K：尾部追加记忆段命中 98.3%、空/有交替 99.8% → **尾部注入无害**
- [x] **D2** ❌ **「后端副本差异导致抖动」—— 证伪**
      `probe_cache_stability.py` 同一 prompt 连发 12 次，命中**恒定 138**，一次都没跳
- [x] **D3** ❌ **「prompt 长度门槛」—— 证伪**
      机制实验 1329 token 命中 98%+；而真实链路 141 那轮 prompt=2323（**更长**）却只有 6.1%
- [x] **D4** ✅ **最终定位：`system` 段每轮逐字相同**（4293 字符、SHA-256 完全一致），
      `context` 段（`assembleContext`）实测**恒为空** → 分叉不在 system 段
- [x] **D5** ⚠️ **我自己给出的解释里，有 3 个是错的**（顺序问题 / 副本差异 / 长度门槛），
      全部靠对照实验推翻 —— 与 ADR-47「该缺陷用户代价 0.885→0.346」同型：
      **拿一个相关数字当因果，是这个项目反复踩的坑**

## E. 附带发现与修复

- [x] **E1** 🔴 **主端点首字节超时（100% 复现）**：
      `llm_call{outcome="timeout",provider="primary"}` = 2~3 次/轮 E2E
- [x] **E1a** ✅ **根因已定位（2026-09-27 11:30 实测）**：
      新加日志打出 `[ADR-48] LLM 流式超时 provider=primary attempt=3 kind=FIRST_BYTE
      firstByteTimeoutMs=45000 emittedAny=false` → **不是内容太长卡住，是前 3 次尝试
      连第一个 token 都没吐**。与 cache 无关，是**上游可用性问题**。
      ⛔ 含义：`attempt-timeout=45s`（ADR-48 从 25s 提上来的）**仍然不够** —— 上游 45s 无响应。
- [x] **E2** 🔴 **超时零日志 —— 已修，且第一版修错了地方**
- [x] **E2a** ⛔ **踩坑：日志加在了 `takeUntilOther`(total-timeout) 上，覆盖不到真实故障**
      E2E 打出 `outcome="timeout"=2` 但 grep 不到任何日志 →
      真实发生地是 `streamAttempt` 里的 `.timeout(首值, 空值)`（`FluxTimeout$TimeoutMainSubscriber`）。
      **流式有三种 timeout，处置完全不同**：

      | timeout | 值 | 含义 | 日志/指标 |
      |---|---|---|---|
      | `FIRST_BYTE` | 45s | 模型没起步（上游慢/排队） | `llm.timeout.stream{kind=first_byte}` |
      | `STREAM_IDLE` | 15s | 起步后中途卡住（内容长/工具调用/思考） | `llm.timeout.stream{kind=stream_idle}` |
      | `TOTAL` | 90s | 整条流超硬上限 | `llm.timeout.total` |

- [x] **E3** ✅ 三种 timeout 现在都有日志 + 指标
- [x] **E4** ✅ **G2 已实测验证**：重跑 E2E，日志确实打出（见 E1a 的原文）
- [x] **E5** ⛔ **`attempt-timeout` 是否该再调高未决** —— 实测 45s 仍不够，
      但盲目调高会拖垮用户等待。需另立 ADR 权衡（要么调高、要么快速降级、要么排队）
- [x] **E6** 🔴 **E2E 从 22/22 掉到 20/22** —— 两项（三牌结构化输出 / 三牌 Unicode）
      **第 1 次请求 0 字 + 无 advice 事件**，重试才过。⛔ **未归因**，与首字节超时同源的可能性最大
      （`attempt=3` 说明重试全耗尽）
