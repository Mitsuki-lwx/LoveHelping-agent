# phase13 · 实测结果与结论

> 状态：已实施并验证（2026-09-24）。全量单测 **289/289**、真实 E2E **22/22**。
> **结论一句话：结构性修复确凿（向量通道知识块 2~17 → 60、记忆 0 泄漏），
> 但在既有 45 例测试集上质量指标无可见提升 —— 我原来的理由被实测否定。**

## S1 前置验证：NULL 陷阱是真的

| 行类型 | 条数 | `metadata->>'source'` |
| --- | --- | --- |
| 知识块 | 439 | **NULL（根本没有这个键）** |
| 用户记忆 | 461 | `'memory'` |

→ `metadata->>'source' <> 'memory'` 对知识块求值为 **NULL** → WHERE 里算 false →
**知识块会被一起滤光且不报错**。这正是当初不敢下推的原因；所以表达式用
`COALESCE(metadata->>'source','') NOT IN ('memory','evolution')`。

**顺带确认关键词通道同样要过滤**（它原本也没有）：`content LIKE` 命中里记忆占比不低 ——
「沟通」95/174 = 55%、「冷战」21/52 = 40%、「吵架」18/65 = 28%。

## S2 实现

| 项 | 做法 |
| --- | --- |
| 向量通道 | 原生 SQL：`WHERE <filter> ORDER BY embedding <=> ?::vector LIMIT k` |
| 关键词通道 | 同一 SQL 里加 `<filter> AND (content LIKE ...)` |
| 落点 | 两条查询抽到新组件 `KnowledgeSqlSearch`（**过滤条件从此只有一处**，不会再漂移） |
| 检索器 | 只留编排（RRF 融合、截断、toParent、日志）；**Java 层过滤保留为兜底**并注明"不再是唯一防线" |
| 数据 | **零迁移**（没给知识块补 `source`、没动入库代码）——避免"未来新增写入点忘了加"这类新风险 |

单选 B 而非 A（补字段）的理由：零数据迁移 + 过滤与取数在同一条 SQL（真下推）+ 与既有 `keywordSearch` 同风格。

## S3 SQL 层对照：结构性变化确凿

向量通道 top-60 的来源构成（真实 query，同一时刻）：

| query | 旧（不过滤） | 新（下推） |
| --- | --- | --- |
| 冷战筑墙怎么办 | memory=43 / knowledge=**17** | memory=0 / knowledge=**60** |
| 煤气灯效应怎么办 | 46 / 14 | 0 / 60 |
| 吵架了怎么和好 | 51 / 9 | 0 / 60 |
| 他总是否定我怎么办 | 43 / 17 | 0 / 60 |
| **怎么表达我的需求** | 58 / **2** | 0 / 60 |

关键词通道：「沟通」41 记忆/19 知识 → **0/60**；「吵架」18/42 → 0/47；
「煤气灯」本就是 0/6（无记忆命中）。

## S4 检索质量 A/B：**没有可见提升**（必须如实写）

**同口径、同期、同一 45 例、同一后端**，只换 `ParentChildDocumentRetriever` 的实现：

| 组 | Recall@5 | MRR@5 |
| --- | --- | --- |
| **修复前**（HEAD 版本） | 0.96 / 0.93 / 0.96 | 0.756 / 0.752 / 0.756 |
| **修复后**（下推） | 0.96 / 0.96 / 0.96 | **0.762 / 0.762 / 0.762** |

→ MRR 差 **+0.006**，**落在既有噪声带 0.012 以内** → **不能说"质量变好"**。
（唯一可提的细节：修复后三轮**完全一致**，修复前有 0.752~0.756 的小波动 ——
候选池成分更纯、排序不再依赖记忆的偶然名次；但这是"确定性"，不是"更好"。）

**纯向量对照**（关掉 hybrid，只留语义通道 —— 理论上最该受影响的配置）：

| 组 | MRR@5 |
| --- | --- |
| 修复前 | **0.770 / 0.770** |
| 修复后 | **0.770 / 0.769** |

**完全一致。** 连"语义通道单独工作"的场景都测不出差别。

## S5 为什么测不出：影响范围量化（**这否掉了我的理由**）

对 45 例逐条算"旧语义下过滤后还剩多少知识块"（= 该 query 会不会真的吃亏）：

```
过滤后 < 5 条（= 少于 topK）的 query 数 = 0 / 45
过滤后中位数 = 30，最小 = 9
```

→ **测试集里没有一条 query 会因为"过滤位置"而受损**：过滤后仍剩 9~60 条，
远超 `topK=5`（"够用"即可，不要求候选池大）。

我原来的论断是"这是这三轮里唯一还在影响答案质量的问题" ——
**被实测否定**：在既有测试集上它**不影响质量**；原因是 ADR-40 先把过滤**顺序**修好了，
关键词通道又能补料，两个补丁把语义通道的窟窿盖住了。

## S6 那这个修复值不值：**价值边界**要说清

**值的部分（有据）**：

1. **避免"名存实亡"**：语义通道本该提供语义召回，修复前它 90%+ 的位子被记忆占掉。
   测试集是**关键词友好**的（ground truth 文档标题大量含查询用词），所以掩盖了；
   一旦查询用词与文档不重叠（口语化、同义改写），关键词通道给不出候选 → 语义通道是唯一依靠。
   **实测佐证**：我随手用的口语化查询里就有过滤后只剩 **2 条**的（「怎么表达我的需求」）——
   这种 query 在旧实现下**候选直接少一半以上**，只是它不在 45 例里。
2. **候选更纯 → 更确定**（修复后三轮指标完全一致）。
3. **为后续简化提供前提**：修复后**纯向量 MRR 0.770 ≥ hybrid 0.762** →
   说明语义通道现在自己就够了，将来可以评估"hybrid 是否还有必要"（另一条线，需专门评测）。

**不值的部分（也要写）**：它在**当前测试集**上带不来任何指标提升；
如果只看 45 例的数字，这次改动是"白做功"。所以判据必须换成"旧实现下过滤后是否够 topK"。

## S7 未验证 / 局限

1. **未在"过滤后不足 topK"的查询集上做 A/B** —— 那才是这个修复的真正受益场景，
   本轮只证明了**存在**这类查询（口语化样例里 1/5），没测它们的占比与提升幅度。
   要做需要一批"关键词不友好"的真实查询（当前语料里没有）。
2. 同族未修点仍不动：`MemoryVectorStore.searchMemory`、`SkillRetriever.search`、
   `KnowledgeSearchTool` 兜底分支（各自上下文不同，另议）。
3. 多实例下 ANN 行为未测（本轮单实例）。
4. 关键词通道的过滤**未被单测守住"SQL 含 COALESCE"以外的行为**（如过滤后条数），
   只在 SQL 层对照里看过一次。

## S8 一次 E2E 失败：查清归因，并给"模型输出型断言"加一次**显式**重试

**现象**：实施后第一次真实 E2E **20/22**，两例失败属**同一个请求的两条断言**
（`三牌完整结构化输出 Accept=*/*`、`三牌 Unicode 无损且协议不混入正文 Accept=*/*`）。重跑 22/22。

**为什么"重跑绿了"不能算完**：这两条断言依赖**模型输出** —— `NormalChatNode` 从输出里找
`@@ADVICE@@`，找不到就不产 `ADVICE_TIERS` → SSE 无 advice 事件 → 两条同时失败。
而本次改动改的正是**检索**（该 advice 请求会走 RAG），所以必须排除
"我改了检索 → 模型不吐协议"这条因果。

**归因证据（内部对照，比"重跑一次"硬得多）**：

| 项 | 通过的那次（trace `34320f22…`） | 失败的那次（trace `d2a24718…`） |
| --- | --- | --- |
| prompt | 同一句 | 同一句 |
| 路由 | `route=normal path=[classify, normal, check]` | **完全相同** |
| 检索 | `hits=20`、`#1` 指向同一文件 | **完全相同** |
| 输出 | 429 字、三牌齐全、带盾字符 | **81 字、无任何协议** |
| 事件 | 含 `advice` | 只有 `message` |
| errors | 空 | **空**（不是异常、不是 5xx） |

两者的**检索与路由完全一致** ⇒ 差异**只能来自模型采样**，不是检索、不是路由、也不是本次改动。

**量化**：
- 历史 E2E 产物（`outputs/e2e-live-routerfix-*.json`，10 次运行）：该 case 失败 **1 次**；
- 本轮探针 `logs/probe_advice_flake.sh`（**改动后版本** × 8 次同一请求）：**8/8 正常**。

**局限（不夸大）**：这只说明"**无证据表明与本次改动有关**"，不等于"证明无关"——
我没跑"改动前 build 的同 N 次探针"。判断为不必跑的理由：上面的内部对照已把
"检索/路由"从嫌疑人里排除（它们在通过/失败的两次请求里**逐字段相同**），
而改动前 build 即使也 8/8 正常，也不增加任何分辨力。

**据此做的小改（`scripts/e2e_live.py`）**：该 case 允许**重试一次**，但**把重试暴露在输出里**
（打印 `RETRY …` 行、判据名带"（第2次尝试才通过）"），**不静默掩盖**。
取舍理由：~1/20 的模型采样缺失会让"22/22"这个信号失去意义（团队会开始忽略红），
但也不能用重试把真回归一起吃掉 —— 真回归是**稳定失败**，重试两次照样红。

**重跑结果**：改动后 **22/22**，且**没有出现 RETRY 行**（两条都是一次通过）。
