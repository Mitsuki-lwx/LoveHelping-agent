# phase13 · 把源过滤下推到 SQL：让知识检索的向量通道不再被用户记忆压制

> 承接 `docs/phase10-retrieval-source-filter`（ADR-40）。那一轮修的是**过滤顺序**（过滤必须在截断前），
> 本轮修的是**过滤位置**（从 Java 层下推到 SQL）。任务列表里这条一直挂着"未修的一半"。

## 背景（为什么还有一半没修）

ADR-40 修好后，`retrieve()` 的顺序变成「排序 → 过滤 → 截断」，**候选数量**恢复了。
但**语义通道仍被压制** —— 实测向量通道 top-N 的构成：

```
top-8 : memory=6   knowledge=2
top-24: memory=19  knowledge=5
top-60: memory=49  knowledge=11
```

原因：知识块与用户记忆**共用同一张 `vector_store` 表、同一个 ANN 索引**，而 461 行记忆
**全是本领域的对话摘要**，语义上天然贴近"恋爱/沟通"类问题。
所以"先取 top-60 再过滤"时，60 个位子里 49 个是记忆 —— 知识块只有 11 条，
现在主要靠**关键词通道**供料。

## 前置验证（本轮第一件事，结论决定方案）

风险一直写着："知识块 metadata **无 `source` 字段**，`source != 'memory'` 可能把知识块一起滤掉"。
**已实测确认这就是真的**：

| 行类型 | 条数 | `metadata->>'source'` |
| --- | --- | --- |
| 知识块 | 439 | **NULL（根本没有这个键）** |
| 用户记忆 | 461 | `'memory'` |

→ SQL 三值逻辑下 `metadata->>'source' != 'memory'` 对知识块求值为 **NULL** → WHERE 里算 false
→ **知识块会被静默滤光**。所以表达式必须处理 NULL（`COALESCE(...)` 或 `IS DISTINCT FROM`）。

## 方案选型

| 方案 | 做法 | 代价 | 判定 |
| --- | --- | --- | --- |
| A 补字段 | 给 439 个知识块写 `source='knowledge'`，入库代码同步，然后用白名单过滤 | **数据迁移** + 改 2 处入库代码 + 未来新增写入点忘了加就再漏 | 否 |
| **B 原生 SQL 下推** | 知识检索的向量通道改用自己的 SQL：`WHERE COALESCE(metadata->>'source','') NOT IN ('memory','evolution') ORDER BY embedding <=> ?::vector LIMIT k` | 改检索器一处；单测的 mock 从 `VectorStore` 换成 `JdbcTemplate` | **选它** |

选 B 的理由：**零数据迁移**（不碰用户数据与知识块）、过滤与取数**在同一条 SQL**（ANN 在过滤后的
子集上取 k 条，这才是真下推）、与同类的 `keywordSearch` **风格一致**（它本来就是原生 SQL）、
且 `COALESCE` 精确处理 NULL。

## 目标

1. 知识检索的两条路径（hybrid / 非 hybrid 兜底）都改为**过滤下推的 SQL**。
2. **关键词通道也要加同一条过滤** —— 本轮前置实测：`content LIKE` 的命中里记忆占比不低
   （「沟通」95/174 = 55%、「冷战」21/52 = 40%、「吵架」18/65 = 28%），
   它们会**先占据 RRF 名次、再被 Java 层丢掉** —— 与向量通道是同一个缺陷的同一条路径。
3. **Java 层的 `isKnowledgeDoc` 过滤保留**作为兜底，但注明"不再是唯一防线"。
4. 用实测证明：向量通道候选构成从 `49 记忆 / 11 知识` 变为 **0 记忆 / 全部知识**。
5. 测检索质量（45 例）—— **按 phase9 §S5 的噪声纪律：多轮取中位**，单轮只用于看大效应。

## 边界

**做**：检索器向量通道下推；单测（含对照实验）；45 例多轮对照；真实 E2E。

**不做**：
- **不改数据**（不给知识块补 `source`，不动入库代码）—— 那会引入"未来写入点漏加"的新风险类。
- 不动**记忆侧**的检索（`MemoryVectorStore.searchMemory` 走 `source=memory` 是它的正常工作方式）。
- 不动 `SkillRetriever.search` / `KnowledgeSearchTool` 兜底分支（同族问题，但各自有上下文，另立项）。
- 不改 `top-k` / `top-n` / RRF 常数 —— 只换过滤位置，不同时动两个变量。

## 风险

- **R1**：下推后向量通道返回的 60 条全是知识块（原先只有 11 条）→ **RRF 融合后的排序会变**，
  质量可能变好也可能变差（关键词通道的权重被稀释）。→ 必须多轮对照，不能只看"候选取到 60 条了"。
- **R2**：原生 SQL 绕开了 Spring AI 的 `VectorStore` 抽象 → 将来换向量库时要记得改这里。
  → 用注释标注，并且**保留 Java 层过滤兜底**。
- **R3**：单测原先 mock `VectorStore`，改造后会失去既有覆盖 → 必须同步改，不能删测试。
