# phase14 · 把 LLM 选择从「故障转移」升级为「可决策的路由」

> 承接 Harness 分层核查（`docs/02` §1.4）。核查结论里"Model routing 多模型调度 = 缺"这一项，
> 本轮做**能力补齐**，不做架构翻新。目标不是造一个好看的路由层，是补上"模型选择"这个位置的
> 治理与可观测，让它可以被决策、被度量、被回滚。

## 背景（为什么"缺"这件事要说准）

上一轮核查把"model routing"标成缺失。核实代码后，缺法要说准，否则会修错东西：

| 现状 | 证据 | 性质 |
| --- | --- | --- |
| 有 primary→fallback 切换 | `LlmGateway:97/110` | 这是**故障转移**（失败才切），不是路由（按任务选） |
| 有能力路由 | `CapabilityRouter`（needTools / isAdvice / isSimpleQuestion） | 选的是**哪个节点**，不是**哪个模型** |
| 视觉旁路网关 | `VisionChatClient:39-49` 手写 `RestClient` 直连 | ⛔ **无并发闸门 / 无熔断 / 无 token 计量** |
| embedding/rerank 各自独立 provider | `PgVectorVectorStoreConfig` / `rag/rerank` | 这部分是**硬编码按组件分**，不是策略 |

**所以真正的缺口是"治理没铺到 + 选择没有决策记录"，不是"路由策略不够聪明"。**
一个没有治理的路由 = 一个 switch 语句；一个没有决策记录的路由 = 事后无法回答"这次为什么走这个模型"。

## 与 phase10–13 的关系

复用已验证的两条既有机制，不新造轮子：

- **ADR-36 的三态语义** `off / shadow / enforce`（`shadow` 判+落库、**绝不改响应**）
- **ADR-37 的影子观测教训**：影子期量的是**真实误报率**，离线拿不到；Jev 用 `signal_score`/`signal_threshold` 两列落库

## 方案选型

| 方案 | 做法 | 代价 | 判定 |
| --- | --- | --- | --- |
| A 引入 LLM 做路由决策 | 先问模型"这个请求难不难/该用哪个模型" | 每次 +1 次 LLM 调用；决策不可复现（同输入可能不同输出）；违反项目"零 LLM 规则路由"既有原则（`CapabilityRouter` 全部是规则） | **否** |
| **B 规则型路由 + 三态开关** | 决策输入全是**请求时已存在**的量（节点类型、消息长度、mediaIds、熔断状态），纯规则、零 LLM、可复现；`shadow` 态只记录不改流量 | 规则要维护；策略好坏取决于我们对请求分级的判断 | **选它** |
| C 引入多模型混合调度（成本/延迟优化） | 按预算与 SLO 自动选最便宜的够用模型 | 需要**先有数据证明便宜模型够用**；本项目答案质量基线 0.885，任何改道都要重测 | **延后**，本轮只把地基铺好 |

**选 B 的理由**：B 的产出（决策记录 + 指标 + 三态开关 + 治理补齐）在 C 里是**前置依赖**——
没有决策记录就没法回答"换了模型之后掉分的是哪一类请求"。先做 B，C 才有判据。

## 任务拆分

### T1 路由决策层（纯规则，零 LLM）

- `ModelRoute` 决策记录（不可变）：走哪个模型、**为什么**、预期成本档、预期延迟档
- `ChatModelRouter`：`enabled=false` 时**完全走现有路径**（行为逐字不变，可回滚）
- 决策输入只用请求时**已存在**的量：图节点类型 / `CapabilitySet` / 消息长度 / `mediaIds` / provider 熔断态
- 决策结果落 span tag（`llm.route.*`）+ 指标（`llm.route{decision=...}`）

### T2 影子态（默认态）

- 默认 `off`，`shadow` 态**判 + 落两列**（`route_decision` / `route_reason`），**绝不改流量**
- 复用 ADR-36 的 Flyway 加列方式（V25）
- 跑真实流量，量"**多少请求会被改道、改到哪**"——这是开 `enforce` 的唯一前置判据

### T3 治理补齐：视觉旁路收口

- `VisionChatClient` 不改协议（ADR-11 的 base64 data URL 是实测验通的，不能动）
- 但要**纳入 LlmGateway 的治理口径**：至少拿到并发闸门 + 熔断 + 指标
- 这是**独立缺陷**，不依赖 `routing.enabled`——即使路由层永久关闭，治理也要修

### T4 效果验证（enforce 的准入条件）

- 影子数据先证明"改道集合"可接受
- `enforce` 前后跑 `retrieval_eval.py`（MRR/Recall）+ `answer_eval.py`（答案质量）
- ⚠️ **答案质量是硬门槛**：基线 **0.885**（ADR-47）。本项目核心价值就是答案质量，
  省钱的收益不能拿它去换。掉分即回滚，不找补。

## 明确不做（边界）

- ❌ 不引入 LLM 参与路由决策（见方案 A 否决理由）
- ❌ 不做沙箱（phase15）
- ❌ 不做多智能体协作（phase16）
- ❌ 不新增模型供应商（先证明现有主备两个够用；缺数据不拍脑袋加）
- ❌ 不改视觉请求的 wire 格式（ADR-11 已实测验通，改动等于自毁）

## 待确认项（需 Mitsuki 拍板，不默认猜）

1. **答案质量红线**：路由若引入更便宜的模型，答案质量掉多少可以接受？
   我的判断：**不接受任何下降**（基线 0.885 是 ADR-47 刚建立的，改道必须持平或更好）。
   若同意 → `enforce` 只允许在"影子数据证明质量持平"的请求子类上开。
2. **enforce 的粒度**：全局开，还是只对某几类请求开？我倾向**只对子类开**（如"简单问答"），
   全局开等于把所有请求都赌在"新选择更好"上，而这条我们没有证据。
3. **本轮是否只做 T1+T2+T3，把 T4 留给影子数据积累之后**？
   我倾向是——T4 需要真实流量与几天数据，本轮强行做只会拿到不可信的读数（同 ADR-37 的教训）。
