# Phase 6 收尾 · 长时混合负载稳定性 — 规格（spec）

> 配套：`tasks.md`（范围）、`checklist.md`（AC）
> 环境：本机单实例，MySQL 8 / PostgreSQL 16 + pgvector / Redis；mcp-server 独立进程（8125）；
> 上游 `https://open.bigmodel.cn/api/paas/v4` + dashscope 降级链。参数本轮**冻结**。

## 1. 被测对象与锚点

| 项 | 值 | 来源 |
| --- | --- | --- |
| 代码版本 | `387a929`（`feat(capacity): 容量口径对齐厂商上限 + 超容有界排队`） | git |
| 在途闸门 `app.online.max-inflight` | 24 | `application.yml` |
| 有界排队 `wait-ms` / `queue-capacity` | 3000ms / 24 | 同上（ADR-29） |
| 网关并发 `app.llm.max-concurrent-calls` | 24 | 同上 |
| 图线程池 `app.graph.executor` | core=24 / max=24 / queue=0 | 同上 |
| 厂商并发上限（实测） | ≈ 24（超额立即 429，不排队） | §8.8(1) |
| 每用户突发桶 | 8 令牌 / 1 在途·s（**防脚本**，非容量） | ADR-29 §4 |

**因此 soak 的负载点选在"在途 = 24"**：这是闸门与厂商上限的交汇处，也是最有意义的稳定点——
再往上会把超出的请求推进有界队列，队列深度本身就是被测指标之一。

## 2. 为什么"30 分钟"而不是"压到崩"

短时阶梯压测（`loadtest.py`）测的是**容量边界**，已经做过（§8.8）。
本任务测的是**持续性**：在稳态负载下，系统会不会**缓慢劣化**。三类只随时间显形的问题：

1. **准入额度泄漏**：`OnlineLoadTracker` 用公平信号量发放 permit，`exit()` 里有一道
   `if (availablePermits() < maxInFlight) release()` 的防御。只要有一个路径（异常/取消/断连）
   漏掉 `exit()`，permit 就会**永久少一个** → 可用容量单调下降，最终所有请求都在队列里等超时。
   短跑看不出来（少 1 个 permit 在 24 并发下几乎无感），长跑会显形为**拒绝率随时间上升**。
2. **连接/线程泄漏**：SSE 是长连接，若 `doFinally` 未覆盖某条异常路径，Hikari 连接或图线程不归还 →
   `hikaricp_connections_pending` 出现非零稳态、或 active 缓慢逼近 max。
3. **队列深度单调爬升**：若释放侧慢于获取侧，`online.queue.depth` 的稳态值会随时间抬升。

**判定原则：看"趋势"而不是"单点值"。** 所以采样必须落原始时间序列，判定用前后窗口对比，
不允许只看最后一个数。

## 3. 负载设计（混合，不是单一聊天）

单一端点跑 30 分钟证明不了"混合负载"。混合比按下表（每轮为一个"批次"，批次内并发发起）：

| 权重 | 场景 | 端点 | 说明 |
| --- | --- | --- | --- |
| 60% | 普通 SSE 聊天 | `/Love_app/chat/sse` | 触发 RAG 检索 + LLM 流式生成（主路径） |
| 15% | RAG 显式检索 | `/Love_app/chat/sse/rag` | 工具调用路径 |
| 10% | 三牌建议 | `/Love_app/chat/sse`（道歉类 prompt） | 结构化输出 + 后处理 |
| 10% | Agent 多步 | `/Love_app/chat/LoveManus` | 工具循环（MCP 进程参与） |
| 5% | 护栏负向 | `/Love_app/chat/sse`（PUA 类 prompt） | **零 LLM 规则拦截**，用于对照 |

- **连续 worker，不做批次同步**（关键设计）：批次的写法是"发 N 个请求 → 等全部结束 → 再发下一批"，
  并发上限永远等于 N，**有界队列根本不会被用到**，也就测不出队列漂移。
  改为**每个 worker 完成一个请求后立刻发下一个**，worker 数取 **32**：
  在途会稳定贴住闸门 24，剩余 8 个持续落在有界队列里 → `queue.depth` 长期非零，
  "队列深度是否随时间漂移"才成为可观测的量（对应 `spec §5` S3/S4）。
- **每 worker 独立用户**（独立 token）：避免落到"每用户突发桶"维度——
  那是防脚本机制，不是容量（§8.8(4) 的坑：单用户共用 token 会把全局容量测成每用户限流）。
- **每轮 30 分钟**，逐请求结果（分类/状态码/TTFT/耗时）全部落 JSONL。
- 负载结束后**继续采样 120s**（`--cool-down`），用于验证 permit 回收（S8）。

## 4. 采样设计

每 **15s** 一次，采自 `/api/actuator/prometheus`（Actuator 已 public，`/actuator/**` 在放行名单）：

| 指标 | Prometheus 名 | 关注点 |
| --- | --- | --- |
| 在途数 | `online_inflight_current` | 是否回落、是否超 24 |
| 队列深度 | `online_queue_depth` | **趋势**（核心判定） |
| Hikari 活跃/空闲/等待 | `hikaricp_connections_active` / `_idle` / `_pending` | pending 稳态必须为 0 |
| Hikari 超时累计 | `hikaricp_connections_timeout_total` | 必须为 0 |
| JVM 堆 | `jvm_memory_used_bytes{area="heap"}` | 稳态不单调增长 |
| JVM GC 次数/耗时 | `jvm_gc_pause_seconds_count` | 无 Full GC 风暴 |
| 准入事件计数 | `online_inflight_*`（entered/queued/queue_full/wait_timeout/rejected/interrupted） | 拒绝**分类**归因 |
| LLM 用量 | `llm_tokens_*`（若暴露） | 成本核算 |

同时按批记录（驱动脚本侧）：每请求 `ok / overloaded(4003) / rate_limited(429) / err`、TTFT 中位与 P95、HTTP 5xx 计数。

**注意**：Micrometer 的 `online.inflight.current` 是 Gauge，Prometheus 名形如 `online_inflight_current`
（点号→下划线）；`online.inflight.entered` 是 Counter，形如 `online_inflight_entered_total`。
脚本对两种命名都做兼容匹配，避免因命名假设导致采样为空（**空采样必须让整轮判定失败，不得静默通过**）。

## 5. 验收标准（判定规则，可逐条执行）

采样序列分两段：**预热段** = 前 5 分钟（丢弃，对齐 §8.8 的"预热轮"教训）；
**稳态段** = 第 5–30 分钟。

| # | 指标 | 判定 |
| --- | --- | --- |
| S1 | 5xx | **稳态段 5xx = 0**（任一 5xx 即失败） |
| S2 | 无说明的拒绝 | 拒绝必须为流内 `event:error`，且文案含"当前咨询较多"/"请求过于频繁"/`retryAfterSec`；**裸 400/500 拒绝**视为失败 |
| S3 | 队列深度趋势 | 稳态段 `queue.depth` **后 1/3 均值 ≤ 前 1/3 均值 + 2**（允许噪声，不允许单调爬升） |
| S4 | 队列深度峰值 | 稳态段峰值 ≤ `queue-capacity`(24)，且**不持续贴顶**（贴顶时长占比 < 20%） |
| S5 | Hikari pending | 稳态段 `hikaricp_connections_pending` 的 P95 = 0 |
| S6 | Hikari 超时 | `hikaricp_connections_timeout_total` 增量 = 0 |
| S7 | Hikari active | 稳态段峰值 < `maximum-pool-size`（不逼近上限），且负载停止后 60s 内回落到基线 ±2 |
| S8 | 在途归零 | 负载停止后 **≤ 60s** 内 `online_inflight_current` = 0（**permit 无泄漏**，核心断言） |
| S9 | 准入拒绝率 | ~~在途 = 24 的档位下，**闸门硬拒率 ≤ 20%**~~ → **已按 §5.2 拆为 S9a（额定档位设门禁）/ S9b（过载只断言可读有界）** |
| S10 | 厂商 429 | 单独计数并报告；若 > 0，说明闸门对齐被破坏 → 失败 |
| S11 | JVM 堆 | 稳态段每次大 GC 后堆回落（不单调增长）；无 `OutOfMemoryError` |
| S12 | 错误归因 | 稳态段 `err` 类（非拒绝的失败）比例 ≤ 1%；每一条 `err` 必须能在日志里找到原因 |
| S13 | 可复现 | 驱动脚本 + 参数 + 原始 JSONL + 汇总 JSON 全部落 `outputs/`，命令写入 `docs/09` §8.9 |

**失败处理**：任一条不通过 → 定位根因 → 修复（含单测）→ **重跑整轮 30 分钟**，
不允许"只重跑失败的那一段"。

## 5.1 S10 口径修订（2026-09-16，据实改写，非事后放宽）

**触发**：本轮实测 S10 不通过（上游降级 86.66%），但**闸门对齐并未被破坏**
（在途 p50 = max = 24，全程未越界）。定位后发现 **S10 的隐含前提不完整**：

> 原表述"若 429 > 0，说明闸门对齐被破坏"——把厂商限流**只当成一个"对齐就没事"的坎**。

**两轮直连探测（绕过应用）把变量分开**（脚本与原始数据见 `docs/09` §8.9(5b)）：

| 探测 | 变量 | 结果 |
| --- | --- | --- |
| A 严格串行（并发恒为 1） | 只改请求速率 | 30 / 60 / 120 RPM 目标下 **0 拒绝** → **"低 RPM 上限"被排除** |
| B 持续并发（完成即发下一个） | 只改并发 | 16 → **0.9%**、20 → **5.8%**、24 → **3.4%**、28 → **9.2%** 被拒（厂商码全为 `1302`） |

**结论**：厂商的 429 是**并发的函数**，**从并发 ~16 起就非零**，并随并发上升；
**24 这一档本身已带 ~3% 拒绝**，不存在"对齐到 24 就安全"的干净坎。
→ **闸门取 24 = 把工作点放进必然产生 429 的区间，零余量**；持续负载下 429 非零是**结构性必然**。

soak 的 429 比例（~25% 网关调用）比直连 24 并发（3.4–7%）高约 5–8 倍，
**已定位到主因（`docs/09` §8.9(5c)）——应用侧熔断策略缺乏比例性**：
`ProviderCircuit` 连续 5 次失败即打开 15s、半开只放一个探针，而 `retry.max-attempts=3`
的每次失败尝试都单独计入；按 10 秒粒度重扫可见 **429 成簇 + 20–40s 空洞（58% 的桶零厂商调用）**，
熔断占空比 24670 ÷ 15.5/s ≈ **86%**，与实测上游降级率 **86.66%** 几乎完全吻合。
⇒ **厂商侧 3–7% 只是背景噪声；86% 的可见降级是应用侧放大出来的**（环境只拿掉了兜底）。
另已排除：请求速率上限、token 速率上限、网关额度被突破（`llm.inflight` 峰值 21 < 24）、模型/端点不符。

**修订后的 S10 判据**（对后续轮次生效）：

| # | 指标 | 判定 |
| --- | --- | --- |
| S10a | 闸门对齐 | 稳态段 `online_inflight_current` 峰值 ≤ `max-inflight`（**对齐未被破坏**） |
| S10b | 闸门余量 | 直连同并发档位拒率必须可忽略（当前 24 档 **3.4–7% 不可忽略** → 需下调闸门或证明余量充足） |
| S10c | **熔断比例性** | **熔断占空比 ≈ 上游真实拒率**（两者不得出现数量级差）；当前 7% → 86%，**判失败** |
| S10d | 厂商 429 | 闸门留余量 且 降级链可用 且 熔断比例性成立 时 = 0；否则按上游归因单独报告，**不判应用失败**，但必须记录 |
| S10e | 降级链健康 | 主/备至少一条可用；两条同时不可用 ⇒ 判为**环境阻塞**，整轮结论标注"未验收" |

**本轮结论**：S10a 通过；S10b/S10c/S10d 不通过；S10e 不通过（dashscope 不可达）。
⇒ 本轮**不判"全部通过"**。**S10c 是本轮最有价值的发现**：它不是环境问题，而是应用侧可修复的缺陷，
修复优先级最高（见 ADR-31 建议 1）。原 S10 结果**保留在案**，不覆盖。

**先例**：与 `docs/09` §6.1 更正 2026-09-07"厂商无硬并发限流 ≥40"属同类操作——**更正错误前提，而非放宽标准**。

## 5.2 S9 口径修订（2026-09-19，据实改写，非事后放宽）

**触发**：S9 原表述是「**在途 = 24 的档位下**，闸门硬拒率 ≤ 20%」，
而 `soak.py` 的实现是「固定 32 worker 下 `rejected/total ≤ 0.20`」。
两者在 **ADR-32 之后不可能同时成立**。

**原口径的隐含前提**（写于 ADR-29、闸门为**固定值 24** 的时代）：

> 32 worker = 闸门 24 + 队列 8，因此在途稳定贴住 24，队列吸收尖峰，硬拒率自然很低。

该前提在 **ADR-32 引入 AIMD 自适应闸门**后失效：

| 时代 | 闸门 | 32 worker 的含义 | 硬拒率（实测） |
| --- | --- | --- | --- |
| ADR-29（固定 24） | 恒 24 | **恰好** 24 + 8 排队 = **不过订阅** | **3.07%**（`docs/09` §8.9(4)） |
| ADR-32（AIMD） | 随负载收缩（本轮收敛到 ~12） | **≈ 2.7 倍过订阅** | **67.6%**（`docs/09` §8.9(10)） |

即：**「在途 = 24」在 ADR-32 之后不再是可持续工作点，而是天花板**——
24 并发本身就会触发厂商 429（直连实测 24 档已有 3.4% 拒绝，见 §5.1 的探测表），
进而乘性收缩到 12。于是"用固定 32 worker 要求拒绝率 ≤ 20%"等于
**要求自适应机制不要生效**，与 ADR-32 直接冲突。

⚠️ **必须同时指出**：`docs/09` §8.9(4) 记录的 S9「3.07% ✅」**是 ADR-32 之前的基线轮**
（该轮 `online_inflight_current` p50 = max = **24**，闸门全程未收缩；上游降级 86.66%，
正是触发 ADR-32 的那次）。**ADR-32 之后未再跑过 30 分钟长压**，
故该"通过"**不构成对当前代码的验证**——这是一处此前未被显式指出的口径漏洞。

**修订后的判据**（对后续轮次生效）——按**过订阅倍数**分档，而不是固定 worker 数：

> 定义：`过订阅倍数 = 本轮 worker 数 ÷ 稳态段 llm_permits_limit 均值`

| # | 适用条件 | 判据 |
| --- | --- | --- |
| **S9a** | 过订阅倍数 **≤ 1.0**（额定档位） | 闸门硬拒率 **≤ 20%**；拒绝（若有）必须发生在**排队等待超时之后**，不得是立即硬拒 |
| **S9b** | 过订阅倍数 **> 1.0**（过载） | **不设拒绝率门禁**（高拒绝率是背压的设计行为）。只断言：①无 5xx ②无裸拒绝、文案可读且带 `retryAfterSec` ③**确实发生了背压**（`rejected > 0`，否则该轮并未真正过载，结论无意义） |

**为什么这么改**：

- **按倍数分档，而不是按 worker 数**：AIMD 的收敛值随负载变化，绝对 worker 数不含信息；
  倍数才表达"相对容量压了多少"。
- **S9b 不设拒绝率门禁**：过载下要求低拒绝率，等价于要求"别做背压"，
  而背压正是 ADR-32 的**设计目标**（把不可控的上游降级换成可控的本地可读限流）。
- **S9a 保留 20% 门禁**：它守的是另一个不变式——**额定负载下闸门不得误伤**，
  该判据仍然有效，必须继续守。

**先例**：与 §5.1（S10 口径修订）同款操作——**更正错误前提，而非放宽标准**。
**S9a 的门禁一个字没松**；S9b 是**新增**的、对另一个工况的断言。

**实现**：`scripts/soak.py` 的 `s9a_rated_reject_rate` / `s9b_overload_graceful`，
两者**互斥**，未适用的一条自动通过（`applies=false`）；`oversubscription` 同时写入汇总顶层。

**配套**：`soak.py` 新增 `--warmup-sec`（**默认 300，即正式门禁口径不变**），
供短程逻辑验证使用；正式验收必须用默认值，并保证稳态采样 ≥ 80 点（S13）。

### 5.2.1 本轮验证（2026-09-19，真实栈 + 真实 LLM，两轮**串行**）

**为什么两轮必须串行**：并行会互相争抢容量，使 `llm_permits_limit` 的收敛值被对方污染，
`过订阅倍数` 失去意义。

| 轮次 | workers | 过订阅倍数 | `llm_permits_limit` 均值→末值 | 请求总数 | 拒绝率 | 裸拒绝 | 5xx | 上游放大 | 判定 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **S9a 额定档位** | 8 | **0.33** | 24 → 24（**全程未收缩**） | 630 | **0.0%** | 0 | 0 | 0% | **S9a ✅**（S9b 不适用） |
| **S9b 过载** | 32 | **2.08** | 24 → **15.4 → 16** | 12095 | **85.06%** | **0** | **0** | **0.19%** | **S9b ✅**（S9a 不适用） |

产物：`outputs/s9a-rated-8w-20260919*`、`outputs/s9b-overload-32w-20260919*`。

**读法（关键）**：

1. **S9a 轮零拒绝**（630/630 全 `ok`，`ttft` p50 1567ms）→ 额定档位下闸门**不误伤**，判据成立。
   该轮 `llm_permits_limit` 全程 **24 未收缩**，反证"8 并发确实在厂商安全区内"。
2. **S9b 轮 85% 拒绝但 `bare_rejects = 0`、`http5xx = 0`** → 背压**可读且有界**：
   10288 次拒绝**每一条**都带可读文案与 `retryAfterSec`；队列无漂移（18.27 → 5.66 下降）、
   峰值 24 贴顶率仅 6%；负载停止后在途**归零**（permit 无泄漏）。
3. **上游只被放大到 0.19%**（23/12095）→ ADR-32 的成果在长时过载下**保持住了**：
   85% 的失败被**本地消化**成可读限流，而不是透传成上游降级。
4. **AIMD 确实在工作**：过载轮把上限从 24 收敛到 **15.4（均值）/ 16（末值）**，
   这解释了为何 32 worker 是 2.08 倍过订阅——**不是闸门坏了，是闸门按设计收紧了**。

**反向对照（证明判据不是恒真）**：把过载轮的 `llm_limit` 采样抹掉 → S9a/S9b **两条都判失败**
（证据缺失不得真空通过）；把额定轮的 worker 数改成 32（而请求仍是零拒绝的额定负载）→
S9b 判**失败**（"确实发生了背压"这一条不成立，即该轮并未真正过载、结论无意义）。两处均实测复现。

亦不作退出码门禁，见 §5.3）**。

   额定档位下闸门**不误伤**，判据成立。
2. **S9b 75% 拒绝但 `bare_rejects = 0`、`http5xx = 0`** → 背压**可读且有界**：

3. **上游只被放大到 0.35%**（84/24075）→ 75% 的失败被**本地消化**成可读限流，

4. ⚠️ **一处必须如实说明的观察：过载档下 `llm_permits_limit` 本身不收敛。**

   它只在额定档（S9a）才稳定在顶格。

## 5.3 退出码口径与产物重放（2026-09-20）

### 5.3.1 触发

跑 30 分钟正式轮时 `soak.py` 以**退出码 1** 结束，导致 `&&` 串行链中断、S9b 未启动。

### 5.3.2 定位

`main()` 末行的退出码取 `all_pass`，而 `all_pass` 把 `s10_vendor_429` 算了进去；
但**同一次运行**的 `app_side_pass` 明确**排除**了该项（§5.1 S10d：「厂商 429 … **不判应用失败**」）。
两者自相矛盾，后果是：一个 **0 拒收 / 0 5xx / 闸门余量充足**的额定档轮次，
只因 **0.17%（4/2411）** 的厂商 429 也返回 1。

**定性**：这是**代码未跟上已于 2026-09-16 生效的 §5.1 S10d**，不是新发现的产品缺陷，
也**不是**未记录的背离（`docs/09` §8.9 与 checklist 均已记载「S10 不通过 / `all_pass: false`」）。

### 5.3.3 处理

退出码改取 `app_side_pass`（`scripts/soak.py` main() 末行），依据写在该行注释里。
`s10_vendor_429` 仍在 `verdict` / `summary` 中**完整报告**，`all_pass` 字段**保留**供严格读者查看
—— **没有任何信息被隐藏，只是不再作为门禁**。

**遗留（不在本轮范围）**：§5.1 的 S10a–S10e 五条子判据**尚未在 `soak.py` 中实现**
（脚本只有粗粒度的 `s10_vendor_429`）。其中 **S10b（闸门余量）与 S10c（熔断比例性）是应用侧判据**，
目前**无脚本证据**。建议另立任务，不要混进 S9 的验收结论里。

### 5.3.4 产物重放（更正一处不一致）

**发现**：`outputs/s9a-rated-8w-20260919-summary.json` 里 `app_side_pass: false`，
与文档记载的「S9a ✅」**不一致**。定位为 2026-09-19 当时**三态 bug**（不适用分支被判 `false`）
留下的产物 —— 修复后**只做了回放验证，没有重新生成产物**。

**重放**：`summarize()` 是纯函数，已从原始 `-samples.jsonl` / `-requests.jsonl` 重算，
写入 `-summary.replayed.json`（**原件保留，不覆盖**）。差异**仅一处**：

| 字段 | 原件 | 重放 |
| --- | --- | --- |
| `s9b_overload_graceful.pass` | `false` | `true` |
| `app_side_pass` | `false` | `true` |

其余字段（含 `applies: false`、请求数、拒绝率、各项 `pass`）**逐字段一致** ——
这反证重放是忠实的，差异确实只来自该 bug 的修复。
`s9b-overload-32w-20260919` 重放**无任何变化**。

**教训**：改完判据逻辑，**必须重算已产出的汇总**，否则产物会与文档长期互相矛盾。
