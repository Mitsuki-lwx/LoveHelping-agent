# phase7-prod-sim · 生产模拟

> **完成情况（2026-09-20）**：T1–T7 全部完成。实测见 `spec.md` §S5，逐条自检见 `checklist.md`。
> 三句话结论：
> 1. **运营代价有数了**：`shadow` 使 TTFT +0.28s（p50）；Jev 故障时固定 **+3s**（= `timeout-ms`），
>    用户仍拿到正常回复、无 5xx、无拒绝。
> 2. **阈值 0.6 切高了**：在未参与标定的 hold-out 上只召回 **45%**（花园里是 100%），
>    0.3~0.4 可到 75~85% 且我的负向集全程 0 误伤。但**不能据此改值**（见下条）。
> 3. **上一轮的 `0/800` 是虚假精度，已撤回**：800 条去重后只有 20 条不同文本（483 条是"你好"）。
>    真实误报率仍未知，**只能靠生产流量**。
>
> 背景：`docs/phase7-jev-shadow` 的结论是"**暂不开 enforce，先在生产以 shadow 跑真实用户流量**"。
> 但那份观测是**离线**的：只调了判定函数，**没有跑应用**。所以有两类问题完全没碰过：
>
> 1. **运营代价**：`shadow`/`enforce` 给**每条用户消息**加一次**同步**外部调用（实测 Jev p50 ≈ 290ms）。
>    它串在首字延迟上、占着 Tomcat 线程，而且**绕过了 ADR-29/31/32 那套容量治理**
>    （`LlmGateway` 的闸门/熔断/自适应限流管不到它，它是独立 HttpClient）。
>    → 生产里它会不会把容量天花板压低？会不会被厂商限流？
> 2. **故障形态**：给主链路加了一个外部依赖。它慢/挂时用户还能不能拿到回复？延迟上界是多少？
>
> 本轮就是把这两件事**在生产配置下跑出来**，顺带把阈值运营点从"离线分布"推进到"生产基率下的拦截占比"。

## 目标

| # | 问题 | 判据 |
| --- | --- | --- |
| Q1 | `shadow` 相对 `off`，用户侧延迟涨多少？ | 同负载、同批次消息，**同并发**下比较 TTFT p50/p95 与总时长；并对比 4003/429/错误率 |
| Q2 | Jev 是新的并发瓶颈吗？ | 并发阶梯 8/16/24 下，**假 Jev 侧看到的最大并发**与调用速率；是否有 429/超时 |
| Q3 | Jev 慢 / 挂时，用户还能拿到回复吗？ | 注入 `slow`(30s) / `hang` / `error`：用户侧**必须仍拿到正常回复**（不升级、不 5xx），延迟上界 ≈ `timeout-ms` |
| Q4 | 生产基率下开 `enforce` 会拦掉多少？误拦多少？ | 拦截占比 = 基率×召回 + (1−基率)×误报；误报用**真实语料实测的上界**，不拍数 |

## 边界

**做**：

- 用 **`prod` profile** 跑（`SPRING_PROFILES_ACTIVE=prod`）：tracing 关、日志 INFO——
  这两项恰恰显著影响延迟，用 local（tracing on + DEBUG）测出来的数不算生产数。
  凭据仍从 gitignored 的 `target/classes/application-local.yml` 读，**不落进仓库**。
- 复现既有装置：`scripts/loadtest.py`（SSE + 并发阶梯）、`scripts/fake_llm.py` 的故障注入范式。
- 新增：`scripts/fake_jev.py`（假 Jev 上游，模式 ok/slow/hang/error + `/stats`）、
  `scripts/prod_traffic_sim.py`（生产流量模型）、`JevShadowCorpus` 增加明文语料入口。

**不做**：

- 不改产品行为：`mode` 默认仍是 `off`；本轮**只是测量**。
- 不为了跑得好看而调容量参数（`max-inflight` / `burst-capacity` 保持生产默认）。
- 不伪造"真实用户分布"：**危机基率是假设值**，一律明确标注并给区间。
- 不写死密钥。

## 风险

- **R1**：本机是单机、`mcp-server` 与 MySQL 同机 → 绝对数字不代表线上，**只看相对差与斜率**。
- **R2**：`burst-capacity=8` 是**每用户**维度；压测必须 `--users == 并发数`，否则测的是突发桶不是全局容量
  （`loadtest.py` 的文档里已写明这个坑）。
- **R3**：厂商 LLM 本身有波动 → 延迟对比必须**同批次、相邻时间**跑，且看 p50/p95 而不看单次。
- **R4**：Jev 有真实计费与限流，压测规模要克制（并发 ≤24、轮次有限），并把 429 单独计数。
