## S2 结论

1. **厂商侧在探测范围内没有限流**（三个方向都是 **0 个 429**）：
   rerank 到 **32** 全成功、embedding 到 **64** 全成功、mixed 到 **48** 全成功。
2. **`max-concurrent=16` 是安全的** —— 它低于任何观测到的边界，且留有余量。
3. **两者同时打不会更早触限**（mixed 48 仍全成功）→ 至少在瞬时并发维度上，
   embedding 与 rerank **不共享一个窄闸门**。
4. **rerank 的真实单次延迟是 p50 ≈ 1.2~2.0s**（20 条 / 7141 字符的真实形状）。
   ⚠️ 这比长期记忆里"热态 **0.39~0.43s**"高出一截 —— 那个数大概是**更短候选**下测的，
   不能代表生产形状（本项目的 `top-n=20` + `max-candidate-chars=1000` 就是当前形状）。
5. **加并发基本不劣化延迟**：rerank 各档 p50 在 1.2~2.0s 间波动（无明显趋势）；
   embedding 从 273ms 线性退化到 711ms（64 并发），**但零失败**。

## S3 对既有结论的**适用范围修正**

长期记忆与待办里有一条：**"提高吞吐天花板必须先提厂商配额（≈24 是上游硬限）"**。

本轮实测表明这句话**只对 LLM 通道成立**：

| 通道 | 观测到的厂商侧边界 | 来源 |
| --- | --- | --- |
| LLM（当时厂商） | **≈24**，超额**立即 429、不排队** | 2026-09-15 实测（本轮**未复核**） |
| 硅基流动 **rerank** | **≥32 无 429** | 本轮 |
| 硅基流动 **embedding** | **≥64 无 429** | 本轮 |
| 两者混合 | **≥48 无 429** | 本轮 |

→ 因此：**在 rerank / embedding 这两条路上，厂商不是瓶颈**；
真正的天花板在应用侧（整机闸门 `max-concurrent-calls=24`）与 **LLM 通道**。

⚠️ 这是**适用范围修正，不是推翻** —— 那个 24 是对 LLM 通道、且针对当时厂商测的，仍然有效；
它只是**不能外推**到硅基流动的 embedding/rerank。

## S4 一个装置坑（值得记）

首版脚本直接从本地配置搜 `api-key:` → 拿到的是**别家厂商**的 key（该 yml 里 dashscope / openai
也各有一条），请求发得出去但服务端回 **401（`code 30014` Token 校验失败）**。
从表面看很容易读成"被限流/被拒"，实际是**拿错了凭据**。

→ 修法：**先定位到 `siliconflow:` 块再取 `api-key`**；且优先读环境变量
（复用已验证的 `scripts/prod_env_from_local.py`）。
📌 通用规矩：**"401/403"要先怀疑凭据取错，而不是先怀疑限流**。

## S5 未验证 / 局限（**报忧**）

1. **只测了瞬时并发（burst），没有测时间窗配额** —— 厂商常另有"每分钟/每日请求数"限制，
   本轮完全没碰。**这是最大的局限**：生产是持续流量，不是脉冲。
2. **只测了一个 key、一个时间段**。配额可能随账号等级变化，也可能被当日累计用量影响。
3. **LLM 通道未复核**：那个"≈24"是 2026-09-15 的读数，厂商换过、配额可能已变 → 仍挂未验证。
4. **48 并发时那次 30s 读超时未归因**（服务端排队？链路？）—— 只观测到 1 次，未复现。
5. **未测更高的档位**（embedding 到 64 仍全成功，说明上限更高，但没继续探）。
6. 探测用的是**本机**网络；生产机房的链路与 TLS 行为可能不同。
