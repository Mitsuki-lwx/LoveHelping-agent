# phase12 · 上游厂商并发上限探测

> **性质**：延续 `docs/phase11-rerank-capacity` 的**验证型任务**（不是新功能开发），
> 装置与结果一并交付。任务/验收/结论见本目录三件套。

## 起因

ADR-41 把 `app.rag.rerank.max-concurrent` 从 2 提到 16。有两个问题当时答不了：

1. **16 安全吗？** —— 应用侧压测答不了：应用有整机闸门（`max-concurrent-calls=24`），
   到不了厂商真实的限流点，**探不到天花板**。
2. **还能再高吗？** —— 长期待办里挂着"提高吞吐天花板必须先提厂商配额（≈24 是上游硬限）"，
   但那个"24"是 **2026-09-15 对 LLM 通道**测的，且换过厂商之后没复核过。

所以要绕过应用、**直接对厂商 API 打并发阶梯**。

## 目标

1. 探出硅基流动上 **rerank / embedding** 两个端点的并发拐点（以及是否触发 429）。
2. 探**两者同时打**（共用同一个 key）时是否更早触发（生产里一次检索就是先 embedding 再 rerank）。
3. 用**真实 payload 形状**测，否则延迟数字没意义：
   rerank = 1 query + 20 条真实知识块（每条截到 `max-candidate-chars=1000`）；
   embedding = 1 条 query。

## 边界

**做**：三张阶梯表（rerank / embedding / mixed）+ 拐点判读 + 对既有结论的适用范围修正。

**不做**：
- **不改任何生产配置**（本轮只探测，不改 `max-concurrent`，也不动整机闸门）。
- 不测 LLM 通道（贵、慢，且与本轮问题无直接关系）→ 只标注"未复核"。
- 不测**时间窗配额**（如"每分钟 N 次"）——本轮只测瞬时并发（burst）。这是明确局限。

## 关键设计（决定结论可信度）

| 设计 | 为什么 |
| --- | --- |
| 超时用 **30s**（生产是 5s） | 目的是**区分"被限流"与"我自己超时了"**；用生产超时会把网络抖动误判成限流 |
| **429 与其他失败分开计数** | 429 才是限流（处置=提配额/降并发）；超时/连接错误是链路问题（处置=查链路） |
| 每档跑 **2 波**、每波同时发 level 个 | 单波可能是巧合；两波看稳定性 |
| 显式**绕过代理**（`ProxyHandler({})`） | 本机有代理时 urllib 可能走代理导致连接超时，污染判读 |
| key **先从环境变量读**，回退时才解析 yml | 见下：yml 里多个厂商都有 `api-key`，盲搜会拿错 |
