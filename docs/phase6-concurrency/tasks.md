# Phase 6 · 高并发性能工程 — 任务拆分（tasks）

> 立项：2026-09-15（承接 docs/09 §6.1 立项条目）
> 前置阅读：`docs/09-测试策略.md` §6（性能验收标准）、§8.5（F6 故障注入）、`docs/03` ADR-23（并发韧性）

## 1. 目标

在**不更换 LLM 厂商、不引入消息队列**的前提下，让服务在高并发下的行为**可预测、可解释、可验收**：
明确真实容量上限、统一三层阈值的口径、并把"超额时的用户体验"从"无说明的硬拒"变成**有明确语义与等待提示**的受控降级。

## 2. 本轮已完成的前置测量（2026-09-15）

| 测量 | 结论 |
|---|---|
| 厂商并发上限（直连上游阶梯探测） | **≈ 24**（≤16 全通；32 → 7/32 得 429；64 → 38/64；96 → 73/96）。**超额是立即 429，不排队** |
| 应用侧多用户实测（8/24/32/48） | 闸门精确：32 → 24 放行 / 8 拒；48 → 24 放行 / 24 拒；**全程零厂商 429** |
| 三层阈值现状 | 闸门 24 / 网关并发 24 / 图线程池 24 → **与厂商上限恰好一致** |
| 每用户突发桶（8 令牌、1/s 回填） | **仅在同一用户"同时并发"时触发**；顺序请求永不耗尽，**不构成全局容量瓶颈** |

## 3. 范围

### 做
1. **统一容量口径**：把"同时在线用户数""同时在途模型请求数"两个概念在文档与配置中区分清楚，给出可复算的换算关系。
2. **超容行为定义与实现**：按用户确认的选项（硬拒 / 有界排队 / 提配额）实现，并补齐用户可读的提示与重试建议。
3. **三层阈值的可配置化与一致性校验**：启动时校验 `gate` ≤ `llm.max-concurrent-calls`，避免"闸门放进来但网关排队"的隐性叠加。
4. **压测工具修正**：`scripts/loadtest.py` 当前**所有线程共用一个 token**（测的是每用户突发桶，不是全局容量），修正为可指定用户数，并保留单用户模式用于突发验证。
5. **验收数据落档**：把厂商上限、阶梯曲线、延迟分布写进 `docs/09`，作为后续回归基线。

### 不做
- 不更换/不叠加 LLM 厂商（另立任务）。
- 不引入 MQ、不做跨实例容量协调（ADR-23 既定：单机不冒充跨实例容量）。
- 不改检索、提示词、业务编排逻辑；不调 rerank（已实测负收益，默认关）。
- 不做多租户维度扩建（ADR-13 冻结）。

## 4. 待用户确认（阻塞项，见 spec §6）

1. **容量目标口径**：期望支撑的"同时在线用户数"是多少？（需先定义"在途占比"假设）
2. **超容行为**：硬拒绝 / 有界排队等待 / 提升厂商配额——选哪个？
3. **验收线是否修订**：`docs/09` §6 现为「P95 首 token < 1.5s、错误率 < 1%」，实测在 >20 并发下不达标，需按新口径重写。

## 6. 风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 排队掩盖真实过载 | 队列变长会推高 TTFT，用户感知为"卡" | 有界队列 + 等待上限 + 超时明确拒绝；导出队列深度指标 |
| 阈值调高反而更差 | 超过厂商上限会触发 429 → 重试 → 拥塞加剧 | 启动校验 gate ≤ 24，除非厂商配额已提升 |
| 压测数据不可复现 | 冷启动（JIT/首次调用）污染首档 | 固定丢弃预热轮 + 记录实例启动时长 |
