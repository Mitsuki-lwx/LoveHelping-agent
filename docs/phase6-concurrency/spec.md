## 1. 现状事实（测量结果）

### 1.1 厂商并发上限 ≈ 24（直连探测，绕过应用）

阶梯并发打 `POST /chat/completions`（`max_tokens=8`）：

| 并发 | 成功 | 429 | 其他错误 | 超时 | 延迟中位 | 墙钟 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 1 | 0 | 0 | 0 | 0.81s | 1s |
| 4 | 4 | 0 | 0 | 0 | 0.52s | 1s |
| 8 | 8 | 0 | 0 | 0 | 0.77s | 1s |
| 16 | 16 | 0 | 0 | 0 | 0.93s | 2s |
| 32 | 25 | **7** | 0 | 0 | 0.67s | 2s |
| 64 | 24 | **38** | 0 | 2 | 1.14s | 30s |
| 96 | 23 | **73** | 0 | 0 | 0.57s | 2s |

**结论**：有效并发上限约 **24**；超出部分被**立即 429**（不排队）。这是**当前容量的硬天花板**，与应用实现无关。

### 1.2 应用侧（多用户，每用户独立 token，`/Love_app/chat/sse`，真实检索 + 真实 LLM）

| 并发 | ok | 4003 过载拒 | 429 限流拒 | 错误 | TTFT 中位 | TTFT P95 | 墙钟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 8 | 8 | 0 | 0 | 0 | 2.23s ※ | 3.05s | 4s |
| 24 | 24 | 0 | 0 | 0 | 1.28s | **1.61s** | 5s |
| 32 | 24 | **8** | 0 | 0 | 1.50s | 2.99s | 5s |
| 48 | 24 | **24** | 0 | 0 | 0.26s ※※ | 2.61s | 4s |

- ※ 首档含冷启动（JIT + 首次调用），故高于第二档 → **压测必须丢弃预热轮**。
- ※※ 中位被 24 个快速拒绝（0.26s 返回）拉低，不代表成功请求的延迟。
- **全程零厂商 429**：闸门 24 恰好卡在厂商上限，未把压力透传到上游。

### 1.3 三层阈值现状

| 层 | 配置 | 语义 | 拒绝表现 |
| --- | --- | --- | --- |
| 每用户突发桶 | `app.rate-limit.burst-capacity=8`，`refill-per-second=1.0` | **按用户**（Redis key `rate:user:{pseudonym}:burst`，Lua 原子） | HTTP 200 + 流内 `event:error`「请求过于频繁」，`code=429` |
| 全局在途闸门 | `app.online.max-inflight=24` | **全局**（`OnlineLoadTracker` 的 AtomicInteger） | 流内 `event:error`「当前咨询较多」/ `code=4003` |
| 网关并发 | `app.llm.max-concurrent-calls=24` | 全局（LlmGateway 信号量） | 内部排队/拒绝 |

> **重要更正（2026-09-15）**：此前记录的"`burstCapacity=8` 令牌桶**先于** `max-inflight=24` 闸门生效"
> 是**测量假象**——`scripts/loadtest.py` 所有并发线程共用同一 token，测到的是"单用户突发桶"。
> 两者是**不同维度**（每用户 vs 全局），不存在固定先后；多用户负载下突发桶不参与全局容量决策。

### 1.4 突发桶的真实触发条件

单人**顺序**连发 12 次**未触发限流**（每次请求 2–3s，桶按 1/s 回填，消耗慢于回填）。
只有**同一用户同时并发**（双击、前端重试风暴、脚本）才会瞬时耗尽 8 个令牌。
→ 该阈值应视为**防重放/防脚本**，而非容量手段。

## 2. 核心问题

1. **吞吐天花板由厂商决定（≈24 在途）**，应用侧三层阈值已对齐，没有可"调高"的余地——调高只会把压力透传成厂商 429，再被重试放大。
2. **超额即硬拒，且没有等待窗口**：25 个用户同时提问，第 25 个立刻被告知"当前咨询较多"，而不是"稍等 1–2 秒"。
3. **容量口径不清**：`docs/09` §6 的验收线（P95 首 token < 1.5s、错误率 < 1%）实测在 >20 并发下不达标（32 并发拒绝率 25%），需要按"在途并发"而非"在线用户"重写口径。

## 3. 技术方案（待用户选定后实施）

### 3.1 口径定义（先统一词汇）

| 词 | 定义 | 本次实测值 |
| --- | --- | --- |
| 同时在线 | 打开对话页/会话未过期 | 上限由会话存储与内存决定，非瓶颈 |
| **同时在途** | 已发请求、尚未拿到完整回答 | **硬上限 24**（厂商） |
| 在途占比 | 在途 / 在线（取决于用户阅读与输入耗时） | 聊天场景经验值 20–30%，**需按产品实际校准** |

换算：`可支撑同时在线 ≈ 24 ÷ 在途占比`。按 25% 计 ≈ **96 人在线**；按 20% ≈ 120 人。

### 3.2 超容行为（**已选定：B 有界排队**，2026-09-15）

| 选项 | 行为 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 保持硬拒（改造前） | 立即 4003 + 文案 | 最省资源、延迟可预测 | 尖峰体验差；拒绝率随超额线性上升 |
| **B. 有界排队（✅ 已实施）** | 在途满时进入有界队列（`queue-capacity`，默认 24），最多等 `wait-ms`（默认 3000ms）；到点仍无额度才拒，并返回可读的等待建议 | 削平短尖峰，拒绝率大幅下降（实测 32 并发 8 拒 → **0 拒**） | 等待期间占用容器线程；TTFT 含排队时间（实测 48 并发 P95 4.3s） |
| C. 提厂商配额 | 申请更高并发档位 | 直接提升天花板 | 有成本、需厂商侧操作，非代码可解 |

**实施要点（已落地）**：复用 `OnlineLoadTracker` 的准入点，改为"**公平信号量 + 有界等待**"；
沿用 `SseBridge` 的流内错误通道；**等待发生在准入阶段（订阅线程），不占用图线程池**
（core=max=24, queue=0），因此不存在队列↔线程池互相占满的死锁。
`wait-ms=0` 可一键退化为改造前的立即拒绝行为（保留回退开关）。

### 3.3 阈值可配置化与启动校验（已完成）

- `CapacityGuard` 启动时校验 `app.online.max-inflight ≤ app.llm.max-concurrent-calls`，违反则**启动失败**并给出可读原因
  （避免"闸门放行、网关排队"的隐性二次排队，那种情况下用户只会感到"莫名变慢"而不是收到过载提示）。
- 启动日志输出容量摘要：`capacity: gate=24 gateway=24 queue=24 waitMs=3000 | vendor concurrency <= 24 (measured 2026-09-15, glm-4-flash)`。
- 网关并发高于实测厂商上限时打 WARN（允许已提升配额的情况，但不静默）。
- 每用户突发桶维持 `8/1s`（定位为**防脚本/防重放**，非容量手段）。

### 3.4 压测工具修正（已完成）

`scripts/loadtest.py`：新增 `--users N`（N 个独立用户，测**全局容量**）/ `--warmup N`（预热轮不计入统计）/ 拒绝分类（过载 4003 与限流 429 分开统计）/ 模式标注；
并修掉过时的硬编码 `GATE_LIMIT_HINT = 8`（实际闸门为 24）。

## 4. 验收标准（已按用户在途口径重写）

用户确认：**不追求具体在线人数数字**，目标是"**不崩 + 拒绝有可读说明**"。因此验收线按**在途并发**分档：

| 档位 | 要求 |
| --- | --- |
| 在途 ≤ 24（= 闸门 = 厂商上限） | 拒绝数 = 0；P95 首 token < 1.5s；厂商 429 = 0 |
| 在途 25–48（= 闸门 + 队列容量，有界排队工作区） | **拒绝率 ≤ 20%**（改造前为 50%）；无一进入队列者被无说明拒绝；P95 首 token 允许升高（含排队等待） |
| 在途 > 48（超出 闸门+队列） | 立即拒绝（`queue_full`）属**正确行为**，不是故障；拒绝必须带可读文案与 `retryAfterSec` |
| 任意档位 | **不得出现 5xx**；不得出现"无说明的拒绝"；SSE 拒绝须为流内 `event:error`（HTTP 200） |

回归锚点（2026-09-15 实测，见 §8）：24 并发 → 24 ok / 0 拒 / 厂商 429=0。

## 8. 实施与实测结果（2026-09-15）

改造前（`wait-ms=0`，立即拒绝）→ 改造后（`wait-ms=3000`，`queue-capacity=24`）：

| 并发 | 改造前 ok / 拒 | 改造后 ok / 拒 | 说明 |
| --- | --- | --- | --- |
| 32 | 24 / **8** | **32 / 0** | 8 个超额请求短暂排队后全部被放行 |
| 48 | 24 / **24** | **47 / 1**（另一次 40 / 8） | 排队吸收尖峰；拒绝率从 50% 降到 2%~17% |
| 64 | — | 48 / 16 | 24 在途 + 24 排队 = 48，超出者 `queue_full` 立即拒绝（设计如此） |

- 全档位**零 5xx、零厂商 429**。
- 48 并发时 TTFT 中位升至 1.85s、P95 4.31s（含排队等待）——这是 B 方案的既定代价，换来拒绝率大幅下降。
- 48 并发两次测量为 47/1 与 40/8，差异来自"请求耗时 vs 等待预算"的时序波动：若在途请求平均耗时接近 `wait-ms`，会有更多人等到超时。
  需更激进削峰时可调大 `ONLINE_WAIT_MS`（代价是更高的等待延迟）。

**代码与验证**：`OnlineLoadTracker`（公平信号量 + `admit()`）、`CapacityGuard`、`ChatEntry`（可读拒绝文案 + 等待时长/队列深度进 payload）、`scripts/loadtest.py`。
单测 **170/170**（新增 10：闸门排队 6 + 容量校验 4）；真实 E2E **22/22**；Langfuse 平台复验 **11/11**。
