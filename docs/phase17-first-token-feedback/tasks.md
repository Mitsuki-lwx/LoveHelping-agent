# phase17 · 首字节反馈与快速失败

> 起因（用户原话）：「首 token 不能太长就行，timeout 主要是看用户体验，
> 如果是 90，要有办法让用户感觉起来没有等太久，先修好一个完善的版本先」

## 1. 目标

把「等 LLM」从**静默等待**变成**有反馈的等待**，并让失败**快速暴露**而不是死等。

## 2. 问题现状（实测，phase16 发现）

| 事实 | 证据 |
|---|---|
| 主端点前 3 次尝试连首 token 都没吐 | `[ADR-48] LLM 流式超时 provider=primary attempt=3 kind=FIRST_BYTE firstByteTimeoutMs=45000 emittedAny=false` |
| `attempt-timeout=45s` × 3 次重试 = 最坏 135s 静默 | ADR-48 把它从 25s 提到 45s，**实测仍不够** |
| SSE 连接在首字节前**完全静默** | `SseBridge:19-24` 订阅后直接 `emitter.send(text)`，上游不吐就什么都不发 |
| 两条 SSE 路径都这样 | `SseBridge.emitter()`（`/chat/sse_emitter`）与 `AiController.chatSseServer()`（`/chat/sse`） |

**用户看到的是白屏 45~135 秒** —— 不是「等得久」，是「不知道系统在干什么」。

## 3. 做什么

| # | 任务 |
|---|---|
| T1 | SSE 建连后**立即**发一条占位事件（`status`），不等首 token |
| T2 | 占位事件带**阶段语义**（检索中 / 组织回答中），不是笼统的"加载中" |
| T3 | `attempt-timeout` 45s → **可配的更短值**，让快速失败快速降级到 fallback |
| T4 | 占位事件**不能污染正文**（前端会把未知事件当正文渲染的话会显示脏文本）|
| T5 | 两条 SSE 路径一致 |
| T6 | 单元测试 + 真实 E2E 验证「白屏时间」缩短 |

## 4. 不做什么

- ⛔ 不改 `LlmGateway` 的重试/降级语义（ADR-23 不变式：网关是唯一重试所有者）
- ⛔ 不引入新的超时类型，只调整现有值的配置
- ⛔ 不动前端（前端如何渲染占位事件是另一件事，本次只保证**事件发得出去且不污染正文**）
- ⛔ 不承诺"90s 变快" —— **目标是用户感知，不是物理延迟**

## 5. 关键决策点

**Q1：占位事件用什么 event 名？**
现有事件：`message`（默认，前端 `onmessage` 消费正文）、`advice`、`error`。
占位事件必须**新开一个名字**，否则会被当成正文插进对话。

**Q2：占位事件发几条？**
一条（建连即发）还是多条（阶段推进）？多条更友好但需要知道阶段 —— 而阶段信息在图里，
SSE 层拿不到。**先发一条**，阶段语义靠文案表达。

**Q3：`attempt-timeout` 调到多少？**
- 调太低 → 正常慢请求被误杀，白白降级到更弱的模型
- 调太高 → 快速失败失效
⛔ **不能拍脑袋**。需要先量：正常请求的首字节延迟分布是多少。
→ 列为 T3 的前置：**先量再调**。
