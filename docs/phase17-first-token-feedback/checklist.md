# ⚠️ 结论修订（2026-09-27 12:20）—— 上面 F 段「核心目标未达成」作废

## 判决实验：`logs/probe_sse_path_ab.sh`（修正量具后重跑）

| 路径 | 首帧（第1/2/3 轮） | 中位 |
|---|---|---|
| A `/chat/sse`（`Flux<ServerSentEvent>`，**主路径**） | 1.509 / 0.060 / 0.037s | **0.06s** |
| B `/chat/sse_emitter`（`SseEmitter`） | 0.026 / 0.006 / 0.004s | **0.01s** |

**两条都 ≤1s → 占位事件一直是有效的，白屏已在 0.06s 消除。主路径不需要改返回类型。**

## 之前的 11~13s / 36s 是量具缺陷，不是产品行为

`scripts/probe_sse_path_ab.py` 原用 `resp.read(4096)`。
Python 的 `HTTPResponse.read(amt)` 会**尽量读满 amt 才返回**；
SSE 响应总共只有几百字节 → 永远读不满 → **一直阻塞到流结束才返回**。
于是我记的「首帧时刻」其实是**整条响应结束时刻**。

- [x] **G1** 改用 `resp.read1(4096)`（有多少给多少，不等补满）
- [x] **G2** 判据预先写死再跑（≤1s / A 慢 B 快 / 都慢），避免事后找理由

## 第二个量具缺陷：chatId 跨轮复用

原探针把 URL 写进 dict 字面量 → 两条 f-string **构造时一次性求值**
→ 同一 arm 的 REPEAT 轮共用一个 threadId → RedisSaver 按 threadId 恢复 checkpoint
→ `GRAPH_PATH` 逐轮累积成 `[classify,normal,check]` / ×2 / ×3。

⛔ 我当时把它读成「**图在自转**，一次提问为什么要 classify 三次」——**那是探针 bug，不是产品缺陷**。
图定义无回边（`OrchestrationGraph:108-127`），每轮确实只跑 3 个节点、只做 1 次 RAG。
- [x] **G3** chatId 改为每轮唯一

## ⛔ 但翻出比白屏更糟的真缺陷：占位被当成正文渲染

后端 0.06s 发出 `event:status`，前端 `front/src/api/index.js:74-81`
是**手写 fetch 流解析，只认 `data:` 行、不区分 `event:` 名**：

```js
if (!line.startsWith('data:')) continue
if (data) onMessage?.(data)      // ← status 的 data 也走这里
```

`LoveChat.vue:381` 是 `messages.value[aiMsgIdx].content += data`
→ 用户在气泡里看到 `{"stage":"thinking","text":"让我想想…"}` 这坨 JSON。

⛔ 我当初的设计前提「独立 event 名 → 未监听会被丢弃 → 前端不改也不会坏」**是错的**：
只有原生 `EventSource` 丢未监听 event，手写解析不会。

**所以「用户体感零改善」的真实原因不是首帧慢，是占位帧变成了脏文本。**
