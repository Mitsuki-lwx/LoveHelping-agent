# phase17 · spec

## 1. 问题定性

**不是「超时太长」，是「首字节前完全静默」。**

现状两条 SSE 路径都在订阅后**直接等上游第一个 token**：

```java
// SseBridge:19-24
subscription.update(flux.subscribe(text -> {
    emitter.send(text);   // ← 上游不吐，这里就什么都不发
}, ...));
```

上游首字节超时 = **连接建立后 N 秒内客户端收到 0 字节**。用户看到的是白屏，
不是"等了 N 秒"。这两件事的体感差距远大于 N 本身。

⛔ 实测口径必须说清：`curl` 测到的「首字节时间」在这里**等于白屏时间**，
因为服务端确实一个字节都没发。**先量后改，别用"感觉很快"当依据。**

## 2. 方案

### 2.1 SSE 建连即发占位事件（核心改动）

```
[客户端] ──GET /chat/sse──>
[服务端] ──event: status──> {"stage":"thinking","text":"让我想想…"}   ← 立即（~0ms）
[服务端] ──(等待 RAG + LLM 首 token)──>
[服务端] ──data: <正文>──>  ...
```

**为什么这是最有效的手段**：它把「未知长度的白屏」变成「已知内容的等待」。
用户看到"正在思考"和盯着空白 45 秒，是两种完全不同的体验。

### 2.2 事件命名

⛔ **不能用默认 `data` 事件** —— 前端 `onmessage` 会把内容当正文插进对话气泡，
造成「脏文本」。必须用**独立 event 名** `status`：

```
event: status
data: {"stage":"thinking","text":"让我想想…"}
```

现有事件契约（不得破坏）：

| event | 用途 | 前端消费方式 |
|---|---|---|
| （无）= `message` | 正文分块 | `onmessage` |
| `advice` | 三牌结构化 JSON | `addEventListener('advice')` |
| `error` | 失败 | `addEventListener('error')` |
| **`status`**（新） | **状态提示，非正文** | **需前端新增监听；未监听时静默忽略** |

✅ 关键性质：**前端不改也不会坏** —— 未监听的 event 会被浏览器丢弃，
不进 `onmessage`。这是向后兼容的。

### 2.3 阶段语义

阶段信息在图里（`GraphObservability.GRAPH_TRACE`），SSE 层拿不到。
⛔ 本次**只发一条**占位（建连即发），不假装能推阶段。

文案必须诚实 —— 不能说"正在分析你的问题"这种暗示已在做实际工作的话，
因为此刻可能还在建连接。文案：**"让我想想…"**。

### 2.4 两条路径都要改

| 端点 | 桥接 | 改法 |
|---|---|---|
| `GET /chat/sse` | `AiController.chatSseServer()` 返回 `Flux<ServerSentEvent>` | 用 `Flux.concat` 前置一个 `status` 事件 |
| `GET /chat/sse_emitter` | `SseBridge.emitter()` 返回 `SseEmitter` | 订阅前先 `emitter.send(status 事件)` |

⛔ `SseBridge.emitter()` 是 static 工具方法，被多处复用；
`chatSse`（非 SSE 端点）也走它。**改它会影响所有调用方** → 必须确认复用点。

### 2.5 `attempt-timeout`：先量再调

⛔ **不拍脑袋调**。需要量：正常请求的**首字节延迟分布**（p50/p90/p99）。

当前无此埋点（phase16 只记了「超时了」，没记「正常多久」）→ **先补埋点**。

调值判据：
- 新值应 ≈ **正常首字节 p99 的 1.5~2 倍**
- 低于此 → 正常慢请求被误杀，白白降级到更弱的模型（**更差的用户体验**）
- 高于此 → 快速失败失效，退回现状

**降级要快于失败**：首字节失败后应立即走 fallback，而不是等满
`retry.maxAttempts` 次。这个语义**已由 ADR-23 决定（网关是唯一重试所有者）**，
本 phase 只调**时间维度**，不改**次数语义**。

## 3. 明确不做

- ⛔ 不动重试/降级的**次数与顺序**（ADR-23 不变式）
- ⛔ 不引入新的 timeout 类型（phase16 已把三种分清，再加只会更乱）
- ⛔ 不改前端代码（但**必须**在文档里写清前端要监听 `status`）
- ⛔ 不承诺降低物理延迟 —— **目标是感知**

## 4. 风险

| 风险 | 缓解 |
|---|---|
| 占位事件被当正文显示 | 独立 event 名，未监听的 event 浏览器自动丢弃 |
| 前端未适配 → 用户仍白屏 | 与现状持平（不更差）；需前端配合才有收益 → 显式标注 |
| `SseBridge` 复用点被误伤 | 改前先枚举所有调用方 |
| 调低 `attempt-timeout` → 误杀正常慢请求 | **先量 p99**，按 1.5~2 倍定值 |
