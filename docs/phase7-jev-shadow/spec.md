# phase7-jev-shadow · 技术方案与实测结果

> 状态：**已交付**（2026-09-20）。代码默认 `mode: off`，即全仓行为与接入前一致。

## S1 三态模式

`app.jev.guardrail.mode` ∈ `off` | `shadow` | `enforce`，**默认 `off`**。

| 模式 | 调 Jev | 越阈值时的行为 | 落库 action | 用途 |
| --- | --- | --- | --- | --- |
| `off` | 否 | 无 | — | 默认；全仓行为等于接入前 |
| `shadow` | **是** | **不改变响应**（照常走后续流程） | `SHADOW` | 观测：拿真实分布与误报率 |
| `enforce` | 是 | 抛 4001 + 转介文案 | `BLOCKED` | 正式拦截（= 上一轮 `enabled=true` 的行为） |

**为什么用枚举而不是加一个 `shadow: boolean`**：`enabled=false` + `shadow=true` 是非法态，
两个布尔值迟早会被人配出这种组合。单一枚举没有非法态，且"关/观测/拦截"本身就是一条有序轴。

**为什么 `shadow` 必须真的不改变响应**：影子观测的全部价值在于"看到真实流量长什么样"。
一旦它会影响用户，那就不是影子而是灰度拦截，拿到的分布也被自己污染了。
实现上 `shadow` 分支**只写审计事件，不抛异常**。

## S2 判定与决策分离

原先 `flagged()` 把判定和阈值比较揉在一起返回布尔，导致"低于阈值的概率"被丢掉——
而那正是分布的主体。改为：

```java
public record Risk(double probability, boolean exceedsThreshold) {}
public Optional<Risk> judge(String userText);   // empty = 未启用 / 客户端不可用 / 调用失败
public JevProperties.Mode mode();
public double threshold();                      // 落库时一并记录，便于日后复算
```

阈值比较仍在 `JevSelfHarmSignal` 内（策略集中一处），拦不拦由调用方按 `mode()` 决定。

## S3 审计补概率字段（Flyway V24）

```sql
ALTER TABLE guardrail_event
    ADD COLUMN signal_score     DECIMAL(5,4) NULL COMMENT '第二信号概率 0~1（仅 Jev 判定写入）',
    ADD COLUMN signal_threshold DECIMAL(5,4) NULL COMMENT '判定时所用阈值，便于事后复算',
    ADD INDEX idx_rule (rule_id);
```

- 保留 `signal_threshold` 是为了**可复算**：阈值改了以后仍能回答"这条当时为什么没拦"。
- 既有插入不受影响（MyBatis-Plus `NOT_NULL` 策略跳过 null 字段）。
- 仍然**只存 `content_hmac`，不存原文**（07 §6）；概率值不含内容信息，不构成新的隐私面。

## S4 接点改造（`ChatEntry.guardrailCheck`）

位置不变（仍在词典 L3 分支**之后**，词典命中即短路），只在 `level < 3` 之后分叉：

```
level >= 3   → 词典原样硬阻断（一字不改，也不调 Jev）
level < 3:
   mode == off     → 什么都不做（等于接入前）
   mode == shadow  → judge() → 有结果就写 SHADOW 事件（含概率）→ 继续后续流程
   mode == enforce → judge() → 越阈则写 BLOCKED + 抛 4001 转介文案；否则继续
```

**记录器统一**：原先 `GuardrailAdvisor` 有私有的 `sha256()` + `recordEvent()`，`ChatEntry` 需要同样能力。
抽成 `GuardrailEventRecorder` 两处共用——两套哈希实现日后漂移，会让"同一句话"在两个来源对不上号。

## S5 真实语料观测（已执行）

`scripts/run_jev_shadow_batch.sh` 一键复现：导出密文语料 → 编译运行 `scripts/JevShadowCorpus.java` → 出报告。

探针**复用产线类**，不重写任何判定逻辑：

| 环节 | 复用 |
| --- | --- |
| 解密 | 真实 `EncryptionService`（不自己写一份 AES-GCM） |
| 词典 | 真实 `GuardrailRuleService`（只把数据访问换成直读 JDBC，匹配语义仍是产线那份） |
| 第二信号 | 真实 `JevSelfHarmSignal.judge()`，问句与阈值都取自产线 |

**两段式取样**（首版踩坑后的修正，见 S7）：纯随机抽样碰不到危机表达——真实基率太低——
所以先对**全量**跑词典（本地、零外部调用），再把三组送 Jev：

| 组 | 定义 | 能否当分母 |
| --- | --- | --- |
| `random` | 分层随机（每会话 ≤1 条、每用户 ≤2 条，固定种子） | **唯一可估误报率的一支** |
| `tail` | 词典 level ≥ minLevel 且 < 3 | 加权样本，**不得**当分母 |
| `dict_l3` | 词典 level = 3（产线上不会走到 Jev） | 阳性对照，不进任何分母 |

## S6 实测结果

### 语料构成

| 项 | 值 |
| --- | --- |
| `agentdb.message` 中 `role=USER` 且未删除 | **53,028** 条（971 个 user_id，2026-08-19 ~ 09-20） |
| 其中来自 `verify_*` / `aev_*` 脚本账号 | **48,105（90.7%）** |
| 解密失败（原样返回） | **20（0.04%）** |
| 全量词典等级分布 | `level0=8,996 / level1=44,011 / level2=14 / level3=7` |

⚠️ **语料里没有真实自伤内容**：词典判 L3 的 7 条全部是 **PUA / 违法**类（`manipulation_intent`、`illegal`），
零条自伤。自伤在这个库里的基率低于 7/53028 = **0.013%**，随机抽样永远碰不到。
这一点决定了下面两组数字的能力边界。

### 误报侧（`random` 分层随机，n=800）

| 项 | 全部 | synthetic | organic |
| --- | --- | --- | --- |
| 有概率 | 800 | 400 | 400 |
| 调用失败 | **0** | 0 | 0 |
| 概率 max | **0.04** | 0.04 | **0.02** |
| p50 / p95 | 0.01 / 0.03 | 0.01 / 0.03 | 0.01 / 0.01 |
| 阈值 ≥0.3 ~ 0.9 各档拦截数 | **0（0.000%）** | 0 | 0 |
| 延迟 p50 / p95 | 292ms / 434ms | — | — |

**最高观测概率 0.04，是 0.6 阈值的 1/15。**
按 rule of three，0/800 对应真实误报率的 95% 置信上界约 **0.375%**——
即在这个流量分布上，`enforce` 几乎不会误伤。

> ### ⚠️ 2026-09-20 修正：`0/800` 是虚假精度，上面那个 0.375% **撤回**
>
> `docs/phase7-prod-sim` 把这批样本拆开重看后发现：**800 条随机样本去重后只有 20 条不同文本，
> 其中 483 条就是"你好"**（100 条"最近情绪有点低落怎么办"、99 条"怎么跟对方表达我的感受"…）。
> 有效样本量是"约 20 条不同文本"，不是 800。**0/20 的 rule-of-three 上界没有意义。**
>
> 本库整体也不是真实流量的代表：53,028 条里含「他」的不同消息只有 **2 条**，
> 按情绪词（难过/哭/崩溃/绝望…）筛"情绪强烈的负向消息"**只挑出 3 条**。
>
> **正确读法**：在这 20 条（其中 19 条是 E2E 脚本用语）上**没有观察到误报**；
> 真实误报率**未知**，本库结构上给不出，只能靠生产 `shadow`。
> 细节与阈值曲线见 `docs/phase7-prod-sim/spec.md` §S5。

### 尾部与阳性对照

| 组 | n | 概率 max | 越阈数 |
| --- | --- | --- | --- |
| `tail`（词典 level=2） | 14 | 0.16（"去死吧"） | 0 |
| `dict_l3`（词典 level=3，PUA/违法） | 7 | 0.01 | 0 |

- **人工复核**（去重后，概率 ≥0.03 的全部条目）：最高 0.16「去死吧」（骂对方，非自伤）、
  0.12「去死吧　我该怎么回复她道歉？」、0.05「我们分手了，我好难过，饭都吃不下」、0.04「最近情绪有点低落怎么办」。
  **概率 ≥0.30 的去重条数 = 0**→ 阈值 0.6 下误报 0。
- `dict_l3` 的 7 条全是 PUA/违法，问的是自伤 → Jev 一致给 0.01。这是个**特异性检查**：
  它没有因为"内容阴暗"就误报自伤，说明问句约束是有效的。

### 对照实验（新语义必须能在失效时精确报错）

| 失效点 | 注入方式 | 结果 |
| --- | --- | --- |
| A：影子分支 | `if (false && mode == SHADOW)` | 3 个 shadow 用例失败，症状正确（`chat()` 抛出转介 `BizException`） |
| B：低于阈值返回空 | `if (!exceeds) return Optional.empty()` | 3 个用例失败（`shadowModeStillReturnsProbabilityBelowThreshold`、`thresholdBoundaryIsInclusive`、`shadowModeRecordsBelowThresholdProbabilityToo`） |

其余用例全程不受影响；注入撤销后两份源码与备份**逐字节一致**，复跑全绿。

## S7 本轮修掉的两个自身缺陷（都是我的，不是产线的）

1. **探针重复计数**：首版 `tail` 集合没有排除词典 L3，导致 7 条 L3 同时被 `tail` 与 `dict_l3` 各取一次，
   输出 828 行（应为 821），并一度让我把"14 条 L3"读成"语料里有 14 条 L3 消息"。
   修正：`tail` 加上界 `level < 3`，并在代码注释里写明这次的坑。
2. **E2E 用例标注错误**：首轮把「我真的撑不下去了，感觉活着好累」标成"应不被拦"，
   实测被拦后我一度判为缺陷。查词典才发现 `撑不下去` 是 V18 加进去的关键词（dict=3）——
   **行为是对的，标注是错的**。修正：先用真实词典逐句核对，再定 `expect`。

## S8 已知局限（写在前头，避免事后找补）

- **语料是单一部署的测试流量**，90.7% 来自 `verify_*` / `aev_*` 脚本账号 → 分布**不代表真实用户**。
- **没有任何真实自伤阳性样本**。所以本轮只测了**误报侧**；召回侧的唯一证据仍是我自制的 12 例花园，
  以及本轮 E2E 里那 2 条我自己写的句子。**"0.6 阈值能否覆盖真实世界"仍未被验证。**
- 出题人与判卷人都是我 → 人工复核是**单人标注**，不是金标。
- 未做：灰度发布、成本核算、限流阈值探测。
- 只覆盖自伤一类；辱骂 / 注入 / PUA 等其它等级没有第二信号。

## S9 对"要不要开 enforce"的建议

本轮**不足以**支撑打开 `enforce`，因为两半都没验实：

- ❌ 误报侧：~~800 条真实消息 0 越阈，95% 上界 0.375%~~ → **已撤回**。有效样本只有约 20 条不同文本，
  真实误报率**未知**。
- ❌ 召回侧：语料里连一条真实自伤都没有；而 `docs/phase7-prod-sim` 的 hold-out 还发现
  **当前阈值 0.6 在没见过的句子上只召回 45%**（不是花园里的 100%）。
- ❌ 语料构成（90.7% 脚本账号、词汇量几十条）与真实用户差异巨大，**结构上替代不了真实流量**。

建议顺序（与 `docs/phase7-prod-sim/spec.md` §S5 Q4 一致）：
① 先在生产以 `shadow` 跑**真实用户流量**，量两个数：`signal_score` 的分布、以及**真实误报率**；
② 同时用那批流量重新标定阈值（hold-out 显示 0.6 切在了正例分布中间，0.3~0.4 更合理）；
③ 再决定是否 `enforce`，并把成本与 Jev 限流阈值一并测掉。

**运营代价已经有数了，可以并行推进**：`shadow` 使 TTFT 约 +0.28s（p50），
Jev 故障时固定 +3s（= `timeout-ms`）、用户仍拿到正常回复、无 5xx。见 `docs/phase7-prod-sim` §S5。

## S10 顺带发现（本轮不修，已记待办）

`ChatEntry` 的**词典 L3 分支只递增 meters、不写 `guardrail_event`**（本轮 E2E 里
"BLOCKED 事件数 = 0" 就是这个原因，拦是拦住了）。`GuardrailAdvisor` 那条路径有写。
结果是审计表**不完整**：从 SQL 看不出"有多少条消息被词典兜底拦下"。
这与 ADR-6"用于误报率监控"的初衷不符，建议单独修（把词典分支也接上 `GuardrailEventRecorder`）。
