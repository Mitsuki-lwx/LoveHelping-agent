# Jev（TypeSafe AI）做路由 —— 可行性探针（tasks）

> 立档 2026-09-20。用户要求："试一下用 Jev 做路由"。**这是一次探针，不是功能交付**；
> 结论为"可用/不可用/有条件可用"即收工，改产线代码需另立 ADR。

## 背景

本项目现在的路由是**四条独立的正则规则**（`CapabilityRouter`）：

| 方法 | 判什么 | 去向 |
| --- | --- | --- |
| `isOffTopic` | 域外（代码/作业/论文/简历…） | `OffTopicNode` 固定引导，零 LLM |
| `isSimpleQuestion` | 问候/寒暄/短情绪句 | 最短路径 |
| `isAdviceRequest` | 话术请求 | 话术三级 |
| `needTools` | 要工具（搜索/天气/规划/图片） | Agent 多步循环 |

规则的问题（仓库已有记录）：`isOffTopic` 是**为了 glm-flash 压不住域外话题而写的确定性兜底**，
穷举式正则必然漏；`isAdviceRequest` 的注释自己承认"可能漏触发/误触发"。

## 目标

1. 用 Jev 的 `choice` 类型，**一次调用同时给出路由与风险判定**，与现有规则逐例对照。
2. 量出：准确率、延迟、成本、失败模式。
3. 给出带依据的建议：能不能用、怎么用（替换 / 兜底 / 并行校验）。

## 非目标

- **不改产线代码**（`CapabilityRouter` 一行不动），只出证据与建议。
- 不做流式/生产化封装、不引入 SDK 依赖、不写进 `pom.xml`。
- 不评估 Jev 做"生成"（它只做结构化判定，不是对话模型）。

## 边界

- API Key **只经环境变量**注入，**不得写入任何入库文件**（AGENTS.md §3，CI 有 gitleaks）。
- 判据：以**人工标签**为准，不拿规则输出当标准答案（否则是用被测对象当尺子）。
- 外部服务不可用/限流时**显式声明未验证**，不默认通过。
