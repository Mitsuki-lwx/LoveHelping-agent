## 2. 单元测试要点

- **一切外部依赖 Mock**：LLM/DB/Redis/MCP 不做真实调用。
- 重点用例：护栏分级判定边界（词典命中但情绪分不足 → L1 而非 L2）；RRF 融合排序稳定性；历史窗口裁剪（20/50 边界）；幂等键冲突路径；Agent 状态机非法迁移拒绝。

## 3. 集成测试要点（testcontainers）

- SSE 流：断言事件序列 start→chunk*→end 的完整性与 usage 字段。
- 降级链：WireMock 让 DeepSeek 返回 503/超时 → 验证切换 DashScope → 双挂 → E5000，且 `llm.call` 指标 outcome 正确。
- Agent 补偿：提交任务 → 杀执行线程模拟崩溃 → 重启扫描 → 任务标 FAILED。
- 越权：用户 A 的 Token 访问用户 B 的会话/历史/删除接口 → 全部拒绝（IDOR 验收，07 §3）。

## 5. Prompt 回归（Golden Set）

1. 用例集：≥ 30 条典型问题，每条含「评估 rubric」（如：体现共情、给出可执行步骤、未越心理边界）而非关键词列表。
2. 判定：**LLM-as-judge**（独立模型按 rubric 打分）+ 禁用词硬校验（出现「操控」「拿捏」类词直接 fail）。旧计划的关键词包含匹配已否决——它会把「换个说法但意思对」的好回复误判为失败。
3. 触发：System Prompt 或检索参数变更时手动/流水线触发，结果按 `prompt_version` 归档对比（08 §2.4）。
4. 门禁：≥ 80% 通过可发布；60–80% 人工复审；< 60% 阻断。

## 5.5 检索质量回归（ADR-15，Phase 3 起）

- **评估集**：`scripts/retrieval-ground-truth.json`，**30 例**（2026-09-05 扩样，覆盖 30 篇知识主题：术语/口语/复合问三类），每例标注期望文档关键字。
- **运行**（2026-09-05 API 化，不再嗅探日志）：
  ```bash
  ADMIN_API_KEY=<key> python scripts/retrieval_eval.py --base http://localhost:<port>/api
  ```
  端点 `GET /admin/rag/retrieve?query=…`（X-Admin-Key 鉴权）直测检索层，绕开 classify 路由波动（simple 分支不检索造成的假阴性）。
- **指标**：**Recall@5 + MRR@5**（父级去重后每文件一票；P@5 父口径有上限失真，弃用）。
- **基线（n=30，2026-09-05）**：Recall@5=**1.00**、MRR@5=**0.817**（hybrid+topK8，jieba 查询分词，无改写）。
- **触发**：切块/嵌入模型/检索策略/知识库文档增删变更时跑，对比归档基线。
- **历史坑位**：① classify 路由不稳定会把无 RAG 的例判 0——现已 API 化根治；② 删除文档后必须同步清 `target/classes/document/` 再 reindex（loader 读 classpath，maven 不清删除资源）；③ 评测脚本需连 admin 端点而非日志文件（多实例混写假阴性）。

## 5.6 生成质量回归（Answer Correctness，2026-09-04 起）

- **评估集**：`retrieval-ground-truth.json` 中带 `golden_answer` 的 **16 例**（标准答案要点）。
- **运行**（LLM-as-judge，脚本直调智谱，不依赖 Langfuse 配置链）：
  ```bash
  python scripts/answer_eval.py --base http://localhost:<port>/api --rounds 3
  ```
  走真实 chat SSE 链路 → judge（glm-4-flash，Correctness 模板中文版）评 0-1 + reason。
- **多轮均值（关键）**：每例跑 3 轮取均值——单轮 judge 采样噪声大（实测 gt_01 单轮出现过 0.5，3 轮实为 0.80/0.80/0.90）。**单轮结论不可信**。
- **基线（2026-09-05）**：AC=**0.90**（n=16 ×3 轮）。
- **用途**：prompt/模型/知识库/检索策略变更后对比；评测驱动修复闭环已实战三次（冷静期补年份 0.5→1.0、煤气灯文档拆分、QueryRewriter 关闭）。

## 6. 性能测试场景

> **口径（2026-09-15 重写，Phase 6 / ADR-29）**：容量一律按**同时在途模型请求数**表述，
> 不用"同时在线人数"——两者换算见 `docs/phase6-concurrency/spec.md` §3.1。
> 成因：真正的天花板是**上游厂商的并发上限（实测 ≈24）**，与在线人数无关。

| 场景 | 目标 |
| --- | --- |
| 在途 ≤ 24（= 闸门 = 厂商上限） | **拒绝 0**；SSE P95 首 token < 1.5s；厂商 429 = 0 |
| 在途 25–48（= 闸门 + 有界队列容量） | **拒绝率 ≤ 20%**（改造前为 50%）；拒绝必须带可读说明与 `retryAfterSec` |
| 在途 > 48（超出 闸门+队列） | `queue_full` 立即拒绝**属正确行为**，不是故障；不得出现 5xx |
| 100 并发 Agent 提交 | 排队 < 5s，池满快速拒绝（B5002）而非超时挂死 |
| 混合负载 30 分钟 | 各池队列深度不持续增长，PG 连接池稳定 |
| 故障注入：LLM 厂商 429 风暴 | 降级链生效，全站不雪崩 |

### 6.1 性能工程计划（2026-09-06 立项）

**立项背景**：健壮性审计确认——降级链已闭环、并发保护机制工作正常，但**容量与高并发 NFR
从未验证**，且当前容量事实不支持高并发。此项为独立性能工程任务，不是日常改动。

**现状（实测事实）**
- 全局并发闸门 `app.online.max-inflight` 默认 **8**（yml 无覆盖 → 生产同为 8）。
- 初检（2026-09-06）：20 并发 → 8 进 + 12 闸门拒（4003）、0 错 0 超时、3s 收尾。
  **保护机制正确；但第 9 个真实用户即被拒**——8 是单模型预算下的保守保护值，非容量能力。
- 按当前 8 上限，200 并发下约 96% 请求被拒 → §6 的 NFR 不可能达标。

**阻塞项（先决）**
1. ~~LLM 厂商并发上限未知~~ → **已实测消解**。⚠️ **2026-09-15 更正**：2026-09-07 那次"厂商无硬并发限流 ≥40"
   的结论**是错的**——那次是**经过应用**做的阶梯压测，而应用的闸门恰好是 24，真实并发根本没打上去。
   直连上游（绕过应用）重测：≤16 全通；**32 → 7~10/32 得 429**；64 → 37~38/64；96 → 73/96；
   **超额是立即 429，不排队**。→ **厂商有效并发上限 ≈ 24**，这才是真正的吞吐天花板；
   调高内部阈值只会把压力透传成 429 并被重试放大。详见 §8.8 与 `docs/phase6-concurrency/spec.md` §1.1。
2. ~~产品容量目标未定~~ → **已定案（2026-09-15，用户确认）**：**不追求具体在线人数数字**，
   目标是"**不崩 + 拒绝有可读说明**"。闸门维持 `app.online.max-inflight` = **24**（= 厂商上限，
   放进来多少就能同时发多少），超额改由**有界排队**吸收（见实施步骤 5）。

**实施步骤**
1. ✅ 厂商并发上限已实测（**≈24**，2026-09-15 直连复测更正）——见上方阻塞项 1。
2. ✅ 压测工具就位并已修正：`scripts/loadtest.py` 支持多用户（`--users`，测全局容量）、单用户（测每用户突发桶）、

2b. ✅ 已做（2026-09-07）：图执行脱离 ForkJoinPool.commonPool → 显式线程池 `graphExecutor`

3. ✅ 阶梯压测已完成：厂商侧 1→96；应用侧（多用户）8/24/32/48/64——见 §8.8。
4. ✅ 瓶颈定位完成：**上游厂商并发上限是唯一瓶颈**；Tomcat / graphExecutor / Hikari 在实测档位下均未成为瓶颈。
5. ✅ 调优与体验抉择（2026-09-15 落地）：闸门保持 24（对齐厂商上限），

   实测 32 并发拒绝数 8 → **0**，48 并发 24 → **1**（见 §8.8）。另加启动期口径校验 `CapacityGuard`。

**验收标准**（2026-09-15 按在途口径重写）

## 8. 韧性与检索回归（ADR-23/24/25，2026-09-13 实测）

> 本机环境：MySQL/PG/Redis 就绪；本地无主 LLM 生产 Key 之外的额外配置，Langfuse/OTLP 未启用（OTLP 已按 ADR-24 关闭）。

### 8.1 单元与契约层

- `mvn test` **149 项全绿**（含 `ProviderCircuitTest`、`ChatEntryTest`、`LlmGatewayTest`、`RateLimiterTest`、`StreamRegistryTest`、`RerankDocumentPostProcessor` 相关、`LocalDocumentReranker` 相关）。
- 修复 1 处测试缺陷：`GraphToolLoopTest` 用 `mock(MeterRegistry)` 违反 Micrometer 契约（`counter()` 永不返回 null）导致 NPE，改为 `SimpleMeterRegistry`。

### 8.2 检索质量对照（45 例 ground-truth，131 篇 / 439 块）

| 配置 | Recall@5 | MRR@5 |
| --- | --- | --- |
| **重排关闭（默认）** | **0.98** | **0.824** |
| 重排开启 + 不扩窗（topN=8） | 0.96 | 0.783 |
| 重排开启 + 扩窗（topN=20） | 0.91 | 0.749 |

### 8.8 高并发容量实测与有界排队（Phase 6 / ADR-29，2026-09-15）

**背景**：§6.1 的"厂商无硬并发限流 ≥40"是一个**经过应用测量得出的错误前提**（应用闸门恰好 24，把真实并发压住了）。
本轮改为**直连上游**复测，并据此重定容量口径与超容行为。

**(1) 厂商并发上限（直连 `https://open.bigmodel.cn/api/paas/v4`，glm-4-flash，绕过应用）**

| 并发 | 成功 | 429 | 超时 | 延迟中位 | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| 1 / 4 / 8 / 16 | 全部 | 0 | 0 | 0.5–0.9s | 1–2s |
| 32 | 25（另轮 22） | **7（另轮 10）** | 0 | 0.67s | 2s |
| 64 | 24（另轮 27） | **38（另轮 37）** | 2 | 1.14s | 30s |
| 96 | 23 | **73** | 0 | 0.57s | 2s |

→ **有效并发上限 ≈ 24**；超额**立即 429、不排队**。这是真正的吞吐天花板，与应用实现无关。

**(2) 应用侧多用户阶梯（每用户独立 token，真实检索 + 真实 LLM）**

| 并发 | 改造前 ok / 拒 | 改造后 ok / 拒 | 改造后 TTFT 中位 / P95 |
| --- | --- | --- | --- |
| 24 | 24 / 0 | 24 / 0 | 1.3–1.7s / 1.6–3.1s |
| 32 | 24 / **8** | **32 / 0** | 0.63s / 1.73s |
| 48 | 24 / **24** | **47 / 1**（另轮 40 / 8） | 1.85s / 4.31s |
| 64 | — | 48 / 16（= 24 在途 + 24 排队，超出者 `queue_full`） | 0.62s / 1.40s |

- **全档位零 5xx、零厂商 429**：闸门 24 恰好卡在厂商上限，未把压力透传到上游。
- 首档含冷启动（JIT / 首次调用），延迟高于第二档 → **压测必须丢弃预热轮**（工具已内置 `--warmup`）。

**(3) 有界排队（ADR-29）落地效果**：闸门满时在 `wait-ms`（默认 3000ms）内排队等待腾出的额度，
等待者数量受 `queue-capacity`（默认 24）限制；到点仍无额度才拒绝，文案带已等待时长与 `retryAfterSec`。
**代价**：48 并发时 TTFT P95 升至 4.31s（含排队等待）——用延迟换拒绝率，符合用户"不追求数字、只求不崩 + 拒绝有说明"的取舍。

**(4) 一处测量工具的坑（已修）**：`scripts/loadtest.py` 原**所有并发线程共用同一个用户 token**，
测到的其实是"**每用户突发桶**"而非全局容量——§8.5 F6 曾据此得出"burst 先于闸门生效"的错误结论。
现支持 `--users N` 区分两种模式，并在输出中标注。另：**单人顺序连发 12 次不触发限流**
（每次请求 2–3s，桶按 1/s 回填，消耗慢于回填）→ 突发桶应视为**防脚本/防重放**，不是容量手段。

#### (5) S10 第一版归因：厂商**速率**配额（⚠️ 已被 (5b)(5c) 推翻，保留以记录推断过程）

> **2026-09-16 更正**：本小节的"速率配额"结论**不成立**——(5b) 的严格串行探测证明并发 1 时
> RPM 与 TPM 两个维度都是 **0 拒绝**。真实主因见 **(5c)**：应用侧熔断缺乏比例性。
> 本小节保留原貌，用于记录"从日志计数出发会得出什么错误结论"。

spec §5 给 S10 的理由是"若 429 > 0 说明闸门对齐被破坏"。本轮实测**该前提不成立**——
闸门与厂商**并发**上限严格对齐（在途 p50 = max = 24，从未越界），429 来自**另一个维度**：

| 证据（全量 1.78GB 日志） | 计数 |
| --- | --- |
| `429 Too Many Requests from POST https://open.bigmodel.cn/api/paas/v4/chat/completions` | **616** |
| `您的账户已达到速率限制`（bigmodel `code 1302`） | **198** |
| `SSLHandshakeException`（降级供应商 dashscope 不可达） | **104,745** |
| 用户可见 `AI 服务暂时不可用` | 101,432 |

**因果链**：主供应商 **429** → 重试耗尽 → 降级到 dashscope →
**dashscope TLS 握手失败（本机网络/代理故障，非项目缺陷）** → 兜底链断 → 
`LlmGateway.publicFailure` 归一为 `5000「AI 服务暂时不可用」`。

`llm_*` 计数印证：`llm_circuit_total{outcome=rejected}` primary **24670** / fallback **24620**
（熔断器长时间打开，快速拒绝），`llm_call_total{outcome=success,provider=primary}` 仅 **1564**，
成功调用平均耗时 ≈10.2s（`llm_latency_seconds_sum/count`，含网关内排队与重试等待）。

**反向对照（关键归因证据）**：5% 的护栏负向场景（**零 LLM、纯规则拦截**）整轮
**1478/1478 全 ok、零失败**。故障**只出现在"需要调用模型"的路径上**；
应用自身、MySQL、Redis、SSE、闸门、有界队列全程健康 → **不是应用缺陷，是上游供给不足 + 降级链断了一环**。

#### (5b) 两轮直连探测：把"速率"与"并发"两个变量分开（2026-09-16 补测）

上一版把 S10 归因为"厂商**速率**配额"，**该说法被下面的探测推翻**，此处据实更正。

**探测 A —— 严格串行（并发恒为 1），只改请求速率**（`scripts/vendor_rate_probe.py`）：

| 目标 RPM | 实测 RPM | ok | 被拒 | 拒率 |
| --- | --- | --- | --- | --- |
| 30 | 28.2 | 20 | 0 | **0%** |
| 60 | 50.5 | 20 | 0 | **0%** |
| 120 | 46.7（受延迟 1.3s 限制） | 20 | 0 | **0%** |

→ **并发 = 1 时，到 ~50 RPM 一个 429 都没有**。**"低 RPM 上限"被排除**。

**探测 B —— 持续并发（每 worker 完成即发下一个，与 soak 同构）**（`scripts/vendor_concurrency_probe.py`）：

| 并发 | 总发 | ok | 被拒 | 拒率 | 实测 RPM | 延迟 p50 | 厂商码 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 16 | 565 | 560 | 5 | **0.9%** | 728 | 1205ms | `1302`×5 |
| 20 | 690 | 650 | 40 | **5.8%** | 871 | 1249ms | `1302`×39 |
| 24 | 657 | 635 | 22 | **3.4%** | 823 | 1481ms | `1302`×21 |
| 28 | 780 | 708 | 72 | **9.2%** | 981 | 1489ms | `1302`×64 |

→ **429 从并发 ~16 就开始出现，并随并发上升**（拒率非严格单调，是概率性拒绝，不是硬悬崖）。
**厂商并没有一个干净的"24 就断"的坎**——24 这一档本身已经带 ~3% 拒绝。
另：直连可达 **728–981 RPM**，所以"速率"根本不是瓶颈。

**修正后的结论（零余量，而非速率配额）**：

1. 厂商的拒绝是**并发的函数**：从 ~16 起非零、随并发上升。**闸门取 24 = 把工作点放在必然产生 429 的区间里**，
   持续负载下 429 非零是**结构性必然**，与请求速率无关。
2. soak 的 429 比例（~25% 的网关调用）**高于**直连 24 并发的 3.4%（约 8 倍）。领先解释有三条，
   **尚未逐条定量证实，此处按"待证"标注**：
   - **熔断恢复惊群**：熔断长时间打开（rejected 24670/24620）→ 半开瞬间 24 个请求同时涌入 →
     瞬时并发越过厂商容忍 → 429 → 熔断重新打开，形成正反馈。直连探测是**平稳** 24 并发，
     soak 是**突发** 24 并发，两者不是同一个工况。
   - **重试不持有 permit**：`LlmGateway` 在 `onErrorResume` 中**先 release 再订阅重试/降级**
     （代码注释明写 `Release before downstream retry/fallback subscribes`）→
     重试与降级请求**不受 24 额度约束**，厂商侧瞬时在途可超过 24。
   - **两处旁路调用不计入额度**：`SkillReflector` 与 `InsightService` 以
     `@Qualifier("openAiChatModel")` **直接注入裸模型**，绕过网关的 permit、熔断与用量归因
     （其余消费者注入 `@Primary ChatModel` = `LlmGateway`，见 `ChatModelConfig`）。
     二者为定时/低频任务，量级不足以单独解释 8 倍差距，但**确实破坏了"单一准入点"**。
3. 因此 **S10 的正确表述**应是："闸门**留出余量**（低于厂商容忍区间）**且降级链可用**时，厂商 429 = 0"。
   **当前闸门 24 = 厂商容忍区间之内，零余量，S10 在任何环境（含网络完好）下都不可能成立。**

**待决策（未实施，需另立任务）**：① 闸门是否下调至留余量档位；② 重试/降级是否改为持有 permit；
③ 两处旁路调用是否统一走网关。三者都会改变 ADR-29/23/27 的既有口径，须补 ADR 并**重跑整轮**。
口径修订已落 `docs/phase6-soak/spec.md` §5.1（**据实改写，非事后放宽**——与 §6.1 更正"≥40"同类）。

#### (5c) 真正的主因：**熔断策略把 7% 的上游拒绝放大成 86% 的用户可见降级**

(5b) 把"厂商侧到底能扛多少"测清楚了，但**仍解释不了**应用侧 25% 的网关调用被 429
（直连怎么压都只有 3.4–7%）。继续深挖后定位到**主因在应用侧**，证据链如下。

**① 网关额度未被突破（排除"有效并发超标"）**

`LlmGateway` 暴露 `llm.inflight`（= `max - availablePermits`）。起 1 分钟短负载
（32 worker，采样 1s 粒度）实测：

| `llm.inflight` | 0 | 2–5 | 8–15 | 16–21 | ≥24 |
| --- | --- | --- | --- | --- | --- |
| 出现次数 | 78 | 6 | 12 | 13 | **0** |

**峰值 21，从未触及 24** → permit 额度没被突破，也没有泄漏。该分钟上游降级率仍达 **79.6%**。

**② 直连探测无法复现应用的拒率（排除"模型/请求形态不符"）**

已核对应用确实使用 `glm-4-flash` @ `open.bigmodel.cn/api/paas/v4`（与探测一致），并逐格补齐工况：

| 工况（直连，45s/档） | 拒率 |
| --- | --- |
| 24 并发 + 小请求（非流式） | 3.4% |
| 24 并发 + 2000 token 大请求（1.4M TPM） | 5.8% |
| 24 并发 + **流式 SSE**（应用聊天走的就是流式） | **7.0%** |
| 并发 1 + 2000 token 大请求（74K TPM） | **0%** |

→ **无论怎么组合，直连在 24 并发下最多 7%**；应用侧却是 25–33%。**差距不在厂商侧。**

**③ 10 秒粒度暴露振荡（1 分钟粒度会把它平均掉）**

重新按 **10 秒**统计 soak 全窗口的 429（`logs/soak/app-20260916c.log`），出现明显成簇 + 空洞：

```
17:20:10  8     17:21:10  6     17:22:20  6     17:23:30  5
17:20:50 12     17:21:50  6     17:22:50 12     17:23:50  7
        └─ 簇间 20–40s 完全空白（无任何厂商调用）──┘
```

31 分钟共 186 个 10 秒桶，**只有 78 个桶出现过 429（58% 的桶零厂商调用）**。
这正是"熔断打开 → 零调用 → 探针成功 → 关闭 → 请求同时涌入"的**振荡签名**
（(5b) 用 1 分钟粒度得出的"均匀分布、无惊群"结论，**是粒度不足导致的误判，此处更正**）。

**④ 熔断占空比 ≈ 用户可见降级率（定量吻合）**

`ProviderCircuit` 策略：**连续 5 次失败**即打开、**打开 15s**、半开**只放一个探针**；
而 `retry.max-attempts=3` 的**每次失败尝试都单独计入** `failure()`。

| 量 | 值 | 推算 |
| --- | --- | --- |
| 请求到达率 | 28896 / 1860s = **15.5/s** | — |
| 熔断拒绝数（primary） | **24670** | `llm_circuit_total{rejected}` |
| ⇒ 熔断打开时长 | 24670 ÷ 15.5 ≈ **1592s** | ≈ 窗口的 **86%** |
| 实测上游降级率 | **86.66%** | — |

**熔断占空比（86%）与用户可见降级率（86.66%）几乎完全吻合**。
（另：`llm_fallback_total{started}` 24742 ≈ 降级响应数 25042，且 primary+fallback 各拒一次
= 49290 ≈ 2×24645，与"每个降级请求 = 主+备各被熔断拒一次"一致。）

**⑤ 结论：因果链与责任归属（修正 (5) 与 ADR-29/31 的表述）**

```
厂商在 24 并发下稳定拒 3–7%（背景噪声，与请求/token 速率无关）
        ↓ 被 retry（每次失败尝试都计数）放大
连续 5 次失败 → 熔断打开 15s（期间 100% 快速失败）
        ↓ 半开只放一个探针；探针失败则再等 15s
熔断打开时长占 86%  →  用户可见降级 86.66%
        ↓ 叠加
降级供应商 dashscope 不可达 → 兜底链断，无法在熔断窗口内救回
```

- **厂商侧 3–7% 是背景噪声**，不是 80% 降级的原因（直连 24 并发复现不出应用拒率）。
- **主因是应用侧熔断策略缺乏比例性**：把一个位数的上游拒绝率放大成 86% 的可见故障。
  这是**应用侧设计问题，不是环境问题**——环境（dashscope 不可达）只是拿掉了兜底。
- **闸门零余量（ADR-31 发现一）依然成立**，但它只是"把 3% 抬到 7%"的次要项，
  **不是主因**；修复优先级应重排。

**待决策（修订 ADR-31）**：① **熔断比例性**（阈值/窗口/半开探针数/重试是否计入）—— **最高优先**；
② 闸门留余量；③ 重试/降级持有 permit；④ 旁路调用统一走网关。均须补单测 + **重跑整轮**。

**新增探测脚本与证据**：`scripts/vendor_concurrency_probe.py`（`--stream` / `--pad-tokens`）、
`scripts/vendor_burst_probe.py`（突发工况）、
`outputs/vendor-{rate,concurrency,concurrency-bigprompt,concurrency-stream,tpm}-20260916.json`、
`outputs/soak-inflight-check-summary.json`（`llm.inflight` 采样）。

#### (9) 结论

**应用侧 12/13 通过**：长时稳定性的四类核心断言（**准入额度不泄漏、连接不泄漏、队列不漂移、堆不增长**）
全部成立，且是在**上游持续故障**这一更严苛的条件下取得的。

**唯一不通过项 S10 已定位为应用侧可修复缺陷**（见 (5c)）：厂商侧只是 **3–7% 的背景拒绝**，
是 `ProviderCircuit` 的"连续 5 次失败即开 + 15s + 单探针"把它放大成 **86.66% 的用户可见降级**
（熔断打开时长占比 86% ≈ 降级率 86.66%，定量吻合）。
环境（dashscope 不可达）的作用是**拿掉兜底**，属放大器而非主因。

修复见 **ADR-32**（熔断改滑窗失败率 + 半开多探针 + 退避；闸门改 AIMD 自收敛），
实施与验证记录见 **(10)**。

按 spec §5"任一条不通过 → 重跑整轮"，本轮（30 分钟长压）**不作为"全部通过"验收**。

**S10 口径已于 (10) 重新裁定**：厂商从 ~16 并发起就有 0.9–9% 的背景拒绝（(5b) 实测），
属**上游事实**，应用侧不可能降到 0。因此门禁从"厂商 429 = 0"改为
**"上游拒绝不得被应用放大"**，(10) 实测该放大已被 ADR-32 消除（上游可见降级 87.4% → 0.9%）。
由此，**S1–S9、S11–S14（应用侧 12 项）在 30 分钟长压中全部成立**，
「30 分钟混合负载稳定性」按应用侧判据关闭；S10 转为上游可用性观测项，不作为门禁。

#### (10) ADR-32 下游容量自适应：实施与三组对照（2026-09-16 晚）

**背景**：(5c) 把 S10 的应用侧主因定位为**熔断缺乏比例性**（把厂商 7% 的背景拒绝放大成 86%）。
用户判断"厂商上限不是固定的"，要求折中处理、参考头部做法 → 停止"把闸门下调到某个实测档位"
的精确刻画思路，改采**运行时自收敛**。设计见 ADR-32。

**实现**（`infrastructure/ai/`）：

- `ProviderCircuit` 重写为**滑窗失败率**（Resilience4j 模型，默认 50 / 20 样本 / 50%）＋
  **半开 3 探针** ＋ 打开时长**指数退避**（15s → 60s 封顶）；取消不算供应商失败。
  删除 `failure-threshold` 配置项（连续计数正是被验证的缺陷本身）。
- 新增 `AdaptiveConcurrencyLimiter`（**AIMD**）：收到厂商限流信号（429 / 报文 `"code":"1302"`）
  乘性收缩 **×0.7**（地板 4）；连续成功 **20** 次加性回升 1（天花板 `max-concurrent-calls`）。
- 新增 `CapacityLimitChanged` 事件：网关每次收缩/回升后发布，`OnlineLoadTracker` 用
  `@EventListener` 把**准入信号量**对齐到同一收敛值（决策 5，实测踩出的必要条件）。
- `app.llm.max-concurrent-calls` 语义由"精确对齐厂商上限"**降级为"天花板"**；
  `app.online.max-inflight` 降级为**设计上限**，有效天花板 = `min(设计上限, 自适应值)`。

### 8.11 反思"容量让路"分支：故障注入实证与一处映射缺陷修复（2026-09-18）

**背景**：§8.10(5) 留下的最后一个未验证项是"反思的容量让路路径未触发"（当时 `容量推迟=0`，

#### (1) 故障注入设计

目标是让反思任务（`SkillReflector`）必然撞上网关闸门满，且**只**能是"闸门满"这一种原因：

| 手段 | 取值 | 作用 |
| --- | --- | --- |
| 假上游 `logs/fake_llm.py`（`FAKE_MODE=hang`） | `spring.ai.openai.base-url=http://127.0.0.1:19080` | 请求永不返回 → 占位请求能长期占住许可 |
| 准入闸门 / 网关闸门 | `gate=1`、`max-concurrent-calls=1`、`wait-ms=0` | 唯一许可被占住后，反思**必然**拿不到 |
| 自适应 / 熔断 | 均关闭 | 排除 AIMD 与熔断干扰，只留闸门一种拒绝来源 |
| 超时 | 三个 timeout 都调 180s | 防止占位请求被超时打断 |
| `app.scheduler.yield-to-online` | `false` | 否则反思会主动让路，测不到"撞闸门" |
| `evolution.quality-threshold` | `101` | 提取结果全被质量过滤 → 只写 skip mark，**不污染技能库** |

脚本 `logs/run_adr31_reflect_defer.sh` + 探针 `logs/probe_reflection_deferral.py`。

#### (2) 对照实验：修复前 FAIL / 修复后 PASS

| 判据 | 修复前（15:44） | 修复后（15:52） |
| --- | --- | --- |

#### (3) 根因：ADR-31 建议 3 漏了一层异常映射

`LlmGateway.call()` 把 permit 获取上提到最外层时写成了裸抛：

```java
if (!limiter.tryAcquire()) throw new CapacityException();
```

而 `CapacityException` 是**包内可见的内部信号**，正常出口是经 `publicFailure()` 映射为
`BizException(4003, "AI 服务繁忙，请稍后再试", {retryAfterSec:2})`。
漏掉映射后，`SkillReflector` 的容量让路分支（按 `BizException.code == 4003` 判定）
**永不成立** → 预期结果被当成真故障打 ERROR 全栈。

**修复**（1 行）：`throw publicFailure(new CapacityException());`

⚠️ **不变式（防复发）**：`LlmGateway` **出网关**的异常一律是 `publicFailure()` 的产物。
`retryable` / `fallbackAllowed` 对 `CapacityException` 仍为 `false`（容量拒绝不可重试、不可降级，未改）。

**自查的正确判据是"位置"，不是"文本"**——不要用 `grep "throw new CapacityException"` 当守卫，会误报。
`syncAttempt()` 里 `RejectedExecutionException` 分支的裸抛（`LlmGateway` ≈L161）是**正确**的：
它在 `callWithRetries` 的 `try` 内抛出，被 catch 成 `failure` 后，因上述两个判定对
`CapacityException` **都为 `false`**（`LlmFailurePolicy` L29/L43：既无 HTTP status，
也不是 `IOException` / 超时 / `TransientAiException`），于是直接 `break`，
落到 `callWithRetries` 末尾的 `throw publicFailure(failure)`（≈L113）被翻译成 4003。

真正**必须自己映射**的只有落在映射边界之外的两处闸门拒绝：

| 位置 | 为什么必须自己映射 |
| --- | --- |
| `call()` 最外层（≈L85） | 在 `try` 之外，没有任何 catch 兜它 |
| `stream()` 订阅入口（≈L177） | 在 `.onErrorMap(this::publicFailure)`（≈L193）**之前**提前返回 |

判据归纳为一句话：**这个 `throw` 能否被上层某个 `publicFailure` 兜到**。

### 8.12 permit 覆盖整条链路的"代价"量化（2026-09-19）

**背景**：ADR-31 建议 3 把并发许可从"每次尝试借还"上提为"每次请求借还"，并在实施记录里
留了一句**未量化的代价**："重试期间不再释放许可，高峰期其他请求更易被 4003"。
本条把它量化。结论分两半：**纯用户流量下代价 ≈ 0**；代价只在**后台任务争抢网关**时才显现，
且方向**不是**简单的"变好或变坏"——它把**拒绝点从准入层搬到了网关层**。

#### (0) 先修装置：原实验有三个缺陷，任何一个都足以让它必然"无差异"

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | 假上游 `max` 是**进程内累计最大值**，用例之间从不重置 | 先跑的用例把 max 顶高，后跑的**结构上不可能**超过它 → 判据 A2 恒 FAIL | `scripts/fake_llm.py` 新增 `GET/POST /reset`；探针在基线前强制 reset 并**校验清零成功**，否则拒绝产出数据 |
| 2 | 运行脚本用 `git checkout HEAD` 当"改造前" | ADR-31 的修复一旦提交，`HEAD` 即含修复 → 两轮实际跑同一份代码 | 改用**显式分界提交** `ADR31_REF=49ff0c0^`（`49ff0c0` 才是引入 permit 上提的提交） |
| 3 | 装置放在 `logs/`（被 gitignore） | 实验无法从仓库复现 | 迁至 `scripts/`（`fake_llm.py` / `probe_permit_cost.py` / `run_permit_cost_ab.sh`） |

补充加固：运行脚本用 `trap` + md5 校验保证**无论怎么退出**都把工作区的 `LlmGateway.java` 还原
（本仓库禁止 `git stash`，换源码做对照必须自带还原）。

> 缺陷 1 的直接证据：2026-09-18 首次实验的两份产物 `fake_stats.max_at` **完全相同**
> （`1789717063.9246786`，都是 4）——同一个 `max` 被两个用例共享，对照从根上不成立。

#### (1) 四轮对照

统一配置：假上游 `slow_error` delay=2s、`wait-ms=0`、熔断与自适应关闭、69 请求 / 24s / 8 用户。
`争抢` = 并发调用 `POST /insight/analyze` 的后台线程数（**走网关但不走准入**，见 (2)）。

| 轮次 | 准入 | 网关 | 退避 | 争抢 | 用例 | 上游峰值 | 准入进/拒 | 用户结果分布 | 上游调用 | 后台成功 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ① | 4 | 4 | 200ms | 0 | AFTER | 4 | 14/55 | 4003×55 / 5000×12 | 40 | — |
| ① | 4 | 4 | 200ms | 0 | BEFORE | 4 | 14/55 | 4003×55 / 5000×12 | 40 | — |
| ②（灵敏度） | 4 | 4 | 2000ms | 0 | AFTER | 4 | 8/61 | 4003×61 / 5000×7 | 24 | — |
| ②（灵敏度） | 4 | 4 | 2000ms | 0 | BEFORE | 4 | 8/61 | 4003×60 / 5000×7 / 断连×1 | 24 | — |
| ③ | 8 | 4 | 200ms | 0 | — | — | — | **应用拒绝启动**（`CapacityGuard`） | — | — |
| ④ | 4 | 4 | 2000ms | **3** | AFTER | 4 | **68/1** | 4003×66 / 5000×2 | **31** | **53** |
| ④ | 4 | 4 | 2000ms | **3** | BEFORE | 4 | **14/55** | 4003×62 / 5000×5 | **43** | **71** |

- 轮次 ① 两列**逐项全等**（连 `fake total` 都是 40）。轮次 ② 把"让出窗口"放大 10 倍，
  差异仍在噪声内（4003 差 1，且那 1 个是 `RemoteDisconnected`）。
- 轮次 ③ 想构造"网关许可真正 bind"的场景（准入 > 网关），被应用自己的 `CapacityGuard` 拒绝启动。
- **轮次 ④ 才出现差异**——前提是引入后台争抢。四份 ①② 产物 `reset_ok=true`。

#### (2) 前两轮为什么必然无差异：纯用户流量下网关许可拿得到

`config/CapacityGuard` 启动时硬校验 **`app.online.max-inflight <= app.llm.max-concurrent-calls`**，
否则抛 `IllegalStateException`。于是纯用户流量下只存在两种合法配置：

- **准入 < 网关**：准入更严，网关许可**永不 bind** → 网关层改了什么都是白改。
- **准入 = 网关 = N**：设某请求要发起第 2 次尝试，它此刻**不持有**许可（旧版已在 `finally` 归还），
  其余在途**用户请求**至多 N−1 个，而许可共 N 个 → **至少 1 个空闲，重试必然拿得到**。

同理，"厂商侧瞬时在途突破容量口径"在纯用户流量下也不成立：应用侧在途 ≤ 准入 ≤ 网关，
且同一请求的多次尝试是**串行**的 → 应用发起的上游并发 ≤ 网关上限。

> ⚠️ **但上述推理有一个前提：占用网关许可的只有经准入的请求。**
> 实测发现该前提**不成立**——`OnlineLoadTracker.admit()` 全仓**只在 `ChatEntry`（用户聊天入口）**
> 被调用；**后台任务（`SkillReflector` 反思、`InsightService` 洞察）经网关（ADR-31 建议 4）
> 却不经准入闸门**。它们能占用网关许可，从而让用户请求的重试**真的拿不到许可**。
> 这正是轮次 ④ 出现差异的原因，也是 (1) 前两轮"无差异"的边界条件。

#### (3) 第四轮：引入后台争抢后差异出现，但方向不是"更好"

轮次 ④ 归一化后的关键读数：

| 指标 | BEFORE | AFTER | 读法 |
| --- | --- | --- | --- |
| 用户 4003 总数 | 62 | 66 | 几乎持平（+4） |
| ├ 其中**准入层**拒 | **55** | **1** | 拒绝点**搬家**了 |
| └ 其中**网关层**拒 | **7** | **65** | ↑ 9 倍 |
| 每"已准入请求"的网关拒绝率 | 7/14 = **50%** | 65/68 = **96%** | 对已准入请求**更差** |
| 上游 5000 | 5 | 2 | ↓ |
| 上游调用总数 | 43 | 31 | ↓ 28% |
| 后台（`/insight`）成功 | **71** | **53** | ↓ 25% → **后台确实让路了** |

解读：

1. **后台让路成立**：AFTER 下后台成功数 −25%，即"一次请求 = 恰好一次 `tryAcquire()`"
   确实把网关容量从后台任务手里还给了用户链路。这是建议 3 的**可观测收益**。
2. **但用户可见拒绝率没有下降**（62 → 66）。拒绝只是**换了发生地点**：
   BEFORE 在准入层就挡掉（55/62），AFTER 放进来再在网关层挡掉（65/66）。
3. **对"已准入"的请求反而更差**（50% → 96%）：因为 AFTER 下一个请求一旦拿到许可就
   **持有整条链路**，许可**周转率下降**；在后台持续争抢下，新准入的请求更常"进来即无许可"。
   BEFORE 的许可在每次尝试后归还，周转快，新请求更容易至少发起一次尝试
   （代价是它可能在中途被拒——即"慢失败"）。
4. **失败形态从"慢链路"变成"快速失败"**：AFTER 准入周转 68 次 vs BEFORE 14 次，
   即 AFTER 更快地把"没容量"这个事实返回给用户，而不是让请求带着准入额度空转整条重试链。

#### (4) 结论

1. **代价量化（回答挂账）**：**纯用户流量下 ≈ 0**（轮次 ①② 差 0～1，低于分辨率），
   "高峰期其他请求更易被 4003"**在纯用户流量下未获实证**。代价只在**后台争抢**时显现，
   表现为**许可周转率下降**（对已准入请求的网关拒绝率 50% → 96%）。
2. **收益也不是"修复越界"**：轮次 ①② 证明上游峰值在两版下都**没有**超过网关上限
   （都是 4）。建议 3 的真实价值是**账目可读性与准入原子化**（一次请求 = 恰好一次 `tryAcquire()`），
   以及在争抢下**把容量从后台还给用户链路**（后台成功 −25%）。
3. **因此本轮不回退建议 3**：它无功能代价、不变式有价值、争抢下的让路行为符合设计意图。
   但**必须修正 ADR-31 的两处表述**：①"重试不受 `max-concurrent-calls` 约束 → 厂商侧在途 > 24"
   与旧源码不符（重试会重新 `tryAcquire`，旧代码 `primaryStream` → `streamAttempt` 链路可查）；
   ②"突破容量口径"在纯用户流量下不成立，只可能在后台争抢或**客户端中断而厂商仍在处理**时发生。
4. **新发现（未闭环）**：**后台任务绕过准入闸门**这一事实本身值得单独评估——
   它意味着准入层算出的"容量"并不覆盖全部网关使用者。是否要让后台任务也过准入
   （或给后台单独配额），需产品决策，不在本轮范围。

**结论的稳健性**：第 2–5 步均为直接读码所得的事实，且与平台侧产物（`llm.attempt` 自成新根）**互相印证**；
第 1 步即使不成立（例如任务 span 并非建在调度线程），也**不改变结论**——只要网关取父时该线程无当前 span，
就会新起根，而产物已证明事实如此。

**对照组（HTTP 入口为何正确）**：`ChatExecutor` L198–204 在请求线程 `telemetry.capture()`，
并把 `PARENT_CONTEXT_KEY` 显式塞进 advisor 参数，`LlmGateway.stream()` L180 再回读 —— 上下文是**显式传递**的。
注意 `call()`（L78）**只有** `capture()`、**没有**这条 Reactor/advisor 回退，故它只在"当前线程自带 span"时正确；
HTTP 同步请求（如 `/insight/analyze`）正好满足，而 `@Async` 线程不满足。

**两个候选修法（均需 ADR + 平台验证，本轮不动手）**：

- **(a) 给 `evolutionExecutor` 加 `TaskDecorator`**，把父 span 捕获后在子线程 `tracer.withSpan(...)` 内执行 —— 一次覆盖所有 `@Async` 后台任务。
- **(b) 由 `ReflectionScheduler` 显式捕获并传参**（照抄 `ChatExecutor` 的形态），把父 `TraceContext` 一路送到网关。

**附带发现（文档缺口）**：`docs/03` 的 ADR 只写了**检索/advisor 路径**的父上下文策略
（"优先 `capture()`，回退读 `Query.context()`"），**从未规定调度器路径**——所以这不是"实现偏离文档"，
而是**文档未覆盖**；按"文档即事实源"，修复应连带补 ADR 条目。

### 8.16 S9 验收口径修订与双档验证（2026-09-19）

**背景**：S9 原口径「**在途 = 24 的档位下**，闸门硬拒率 ≤ 20%」写于 ADR-29（闸门固定 24）时代，

**问题不只在"没实现"，更在判据本身**：

- **S10a 原判据是恒真命题**：`OnlineLoadTracker.inFlight()` 返回

  多放的请求在网关被拒，而在途仍 ≤ 24 → **照样判过**）。

- **S10c 的判据措辞有缺陷**：§5.1 写"熔断占空比 ≈ 上游真实拒率，不得有数量级差"，

  正确口径应是「**不放大**」（`占空比 ≤ 上游拒率 × k`），按此口径本轮**成立**
  —— ADR-32 要治的 12 倍放大（7% → 86%）已消除；
- **S10e 有改善**：S9b 中 `provider="fallback"` 实际成功 4 次，优于 §5.1 记录时的"dashscope 不可达"；
- **S10b 需耦合设计**：直连拒率在 soak 期间测不出来，须走 `vendor_concurrency_probe.py`。

**本轮未实现任何 S10 子判据** —— 三条都要先改口径，改口径前实现等于固化错误。
**S10c/S10b 实现前必须先定**：①上游真实拒率从哪来 ②放大倍数阈值 k。

**未验证 / 局限**：本轮**未跑 E2E**（S9 属容量口径，不触达功能面）。

### 8.17 护栏第二信号的三态模式与真实语料影子观测（ADR-36，2026-09-20）

**目的**：`docs/phase7-guardrail-recall` 的"0 误报"出自我自制的 12 例花园，阈值 0.6 也标在那 12 例上。
打开 `enforce`（真拦截）之前，必须先在**真实语料**上量出概率分布与误报率。

**被测改动**：`app.jev.guardrail.mode` 三态（`off`/`shadow`/`enforce`，默认 `off`）；
`judge()` 判定与决策分离；`guardrail_event` 补 `signal_score`/`signal_threshold`（Flyway V24）。

**测试分层**：

| 层 | 手段 | 结果 |
| --- | --- | --- |
| 单元 | `JevSelfHarmSignalTest`（本地 HttpServer 桩）+ `ChatEntryTest` | **245/245**（基线 236，+9） |
| 对照实验 | ①`if (false && mode==SHADOW)` ②`judge()` 低于阈值返回空 | 各 3 个目标用例**精确失败**，症状对得上 |
| 真实 E2E | 应用以 `shadow` 启动 + 真实 Jev key + 真实 SSE | **4/4** |
| 真实语料观测 | `scripts/run_jev_shadow_batch.sh`（复用产线类） | 821 次调用、失败 0 |
| 回归 | `e2e_live.py` | **22/22** |

**关键实测数字**（详见 `docs/phase7-jev-shadow/spec.md` §S6）：

- 语料：`agentdb.message` 中 `role=USER` 未删除 **53,028** 条；解密失败 20（0.04%）；
  全量词典分布 `{0:8996, 1:44011, 2:14, 3:7}`；
  **词典判 L3 的 7 条全是 PUA/违法，零条自伤** → 该库自伤基率 < **0.013%**。
- 误报侧（分层随机 n=800）：**概率 max 0.04**；阈值 ≥0.3~0.9 各档拦截 **0（0.000%）**；
  rule-of-three 95% 上界 ≈ **0.375%**；延迟 p50 292ms / p95 434ms。
- 人工复核：概率 ≥0.30 的去重条目 **0**（最高 0.16＝「去死吧」，骂对方）。
- E2E 决定性一条：词典漏判的句子 Jev 判 **0.66（>0.6）**，用户仍拿到**正常回复**；
  DB 同步落 `action=SHADOW, signal_score=0.6600, signal_threshold=0.6000, has_hmac=1`。

**为什么纯随机抽样不够**（首版教训，已写进 ADR-36）：
首版仅随机抽 800 条 → 概率 max 0.04、词典 L3 命中 0，**测不出阈值附近行为**。
危机表达基率太低，随机抽样结构上碰不到 → 必须"全量词典 + 尾部刻意加权 + 分层随机"三段，
且**只有随机那一支能当误报率分母**。

**本轮修掉的两个自身缺陷**：探针 `tail` 未排除 L3 → 7 条被两组各取一次（输出 828 应为 821，
并一度误读为"14 条 L3"）；E2E 首轮把词典已覆盖的「我真的撑不下去了」标成"应不被拦"，
实测被拦后误判为缺陷——核对词典才发现 `撑不下去` 是 V18 关键词，**行为对、标注错**。

**未验证 / 局限（必须随结论一起读）**：

- **召回侧在真实数据上仍空白**：语料里没有任何真实自伤阳性样本，
  唯一正例仍是自制 12 例 + 本轮 2 句自写 E2E 句子。**"0.6 能否覆盖真实世界"未验证。**
- 语料 **90.7% 来自 `verify_*`/`aev_*` 脚本账号**，不代表真实用户分布。
- 单人标注（出题人＝判卷人）；未做灰度、成本核算、限流探测。

**顺带发现（未修）**：`ChatEntry` 的词典 L3 分支只记 meters、不写 `guardrail_event`
（E2E 里 "BLOCKED 事件数 = 0" 即此），审计表看不出"词典兜底拦了多少条"。

> ⚠️ **本节结论已被 §8.18 修正**：800 条随机样本去重后只有 20 条不同文本，
> "误报 0/800 → 上界 0.375%"是虚假精度，已撤回。

### 8.18 生产模拟：同步外部依赖的代价/治理/故障，以及"样本量"陷阱（ADR-37，2026-09-20）

**目的**：§8.17 的观测**只调判定函数、没跑应用**。这轮补上两类没碰过的问题：
① 每条消息加一次同步外部调用的运营代价；② 它慢/挂时用户会怎样。顺带用 hold-out 复验阈值。

**被测对象**：`app.jev.guardrail` 第二信号（本轮**未改产品代码**，只测）。

**装置**（`prod` profile，凭据运行时从 gitignored 的 local yml 读）：

| 装置 | 作用 |
| --- | --- |
| `scripts/run_prod_sim.sh` | 起应用（prod）→ 压测 → 收数 → 停应用；5 个轮次 |
| `scripts/fake_jev.py` | 假 Jev 上游：`ok/slow/hang/error/slow_error` + `/stats`（上游侧并发）+ `/reset` |
| `scripts/prod_env_from_local.py` | 把 local yml 的凭据变成 env（**仓库无密钥**） |
| `scripts/crisis_holdout.jsonl` | 未参与标定的 20 危机 + 12 近邻负向 + 5 歧义 |
| `scripts/prod_operating_point.py` | 阈值曲线 + 把误报当自由参数的运营点表 |
| `scripts/loadtest.py` | 复用：SSE + 并发阶梯 + 4003/429 分开计数 |

**结果**：

| 问题 | 实测 |
| --- | --- |
| 代价 | `shadow` vs `off`：TTFT **+0.28s(p50) / +0.30s(p95)**，与 Jev 单次 p50 292ms 同量级；≤24 并发 0 拒绝 0 错误 |
| 真在调？ | 同窗口 `guardrail_event` 落 **52 行** `action=SHADOW, signal_score=0.01`；`off` 轮 jev 日志 **0 行** |
| 治理 | Jev **不经** `LlmGateway`（无闸门/熔断/AIMD）；`slow` 下实测 **`client_disconnected: 12`**（客户端超时后确实中止了请求，`current: 0`） |
| 故障 | `slow`(30s)/`hang`：TTFT **4.37s = 基线 + 2.96s ≈ `timeout-ms`(3s)**，8/8 成功、0 5xx、**0 误升级**；`error` 无惩罚（1.39s） |
| 阈值 | hold-out 上 **0.6 → 召回 45%**（≥0.3 是 85%）；自造负向 12 条 ≤0.07、歧义 5 条 ≤0.20 |

**本轮最重要的方法论产出（已进 ADR-37 决策 2）**：

```
"800 条样本" 去重后只有 20 条不同文本（483 条是"你好"）
53,028 条的库里：含「他」的不同消息 2 条、含「怎么办」8 条
按情绪词筛"情绪强烈的负向消息"：只挑出 3 条
```

→ **报"n 条样本"必须同时报去重后的不同文本数**；两者差距大时以后者为准。
§8.17 的 0.375% 上界因此**撤回**。

**两个装置缺陷（都是本轮自己踩的，已修）**：

1. **假 Jev 生命周期**：Git Bash 的 `$!` 是 **MSYS PID**，`taskkill /PID` 杀不掉 →
   后两轮的假 Jev 没绑上端口，三轮统计全是 `by_mode={'slow':...}`。
   改成**按端口杀 + 起服后断言"确实是本模式在服务"**。
2. **`eval "$(...)"` 不 export**：变量只是本 shell 变量，Maven 派生的子 JVM 看不到 →
   prod profile 起不来（`OpenAI API key must be set`）。改成输出 `export KEY=value`。

**回归**：单测 **245/245**（与基线一致，未改产品代码）、E2E **22/22**、
`git status src/main` 为空、`mode` 默认仍为 `off`。

**未验证 / 局限**：真实误报率仍未知（本库给不出）；召回与误报样本均为本人编写；
基率是假设值；未测 Jev 厂商限流阈值与成本；每档样本仅 8/16/24 次，单档噪声明显；
基线轮已有 3~4 次 DashScope embedding 上游失败（既有问题，两轮都有）。

### 8.19 影子观测的收尾：审计补全、读数工具、以及一次"量具瞎了"的更正（ADR-38，2026-09-20）

**目的**：§8.18 留下"先在生产 shadow 上量真实误报率"这个条件，但配套的**记账、工具、门槛**都没做。
本轮补齐，并更正 §8.18 里一句没验证就下的断言。

**改动面**：`ChatEntry` 补一行审计（产品代码唯一改动，不改行为）；新增读数脚本与操作手册。

**测试分层**：

| 层 | 手段 | 结果 |
| --- | --- | --- |
| 单元 | `ChatEntryTest` +2（L3 落库 / L1L2 不落库防双计） | **247/247**（基线 245） |
| 对照实验 | 摘掉审计那一行 | `dictionaryL3BlockIsAudited` **精确失败且只它一个**；恢复后逐字节一致 |
| 真实 E2E | 影子模式 4/4 | **`BLOCKED 事件数` 由 0 → 1**（补全前该查询恒为 0） |
| 回归 | `e2e_live.py` | **22/22** |
| 工具端到端 | 报告脚本对真实库跑通 导出→标注→回填 | 24h 窗口 57 条 SHADOW / 0 条 no_result / 越阈 2 条(3.51%) |

**更正：量具瞎了，读数会"稳定且错误"（本轮最重要的教训）**

§8.18 记为"`slow`/`hang` 下上游积压 12 条，当前实现没有主动取消在途请求"。
依据是假上游 `/stats` 的 `current=12`——但**老版假上游只会 `time.sleep` 到点再写响应，
根本感知不到对端已关闭**，所以它的 `current` 永远不降。

给假上游加"对端是否断开"探测（延迟期间 `select()` 轮询 socket，读到 FIN 即中止）后重跑 `slow`：

```
{'current': 0, 'max': 8, 'total': 12, 'by_mode': {'slow': 12}, 'client_disconnected': 12}
```

**12/12 全部被客户端中止。** `JevClient` 用同步 `http.send()` + `HttpRequest.timeout(3s)`，
JDK 在响应超时时会中止交换并关闭连接 —— 我们这边是干净的。
该错误断言已从 5 处更正（`docs/03`/`docs/09`/`phase7-prod-sim` 两份/`MEMORY.md`）。

> 📌 **规矩**：靠计数器下结论前，先确认这个计数器**能观测到你要判断的那个现象**。

**顺带修掉一个真 bug**：报告脚本首跑时导出清单为空 —— pymysql 把 `DECIMAL` 读成 `decimal.Decimal`，
未转换导致 JSON 序列化抛异常（**只在有数据时才炸**，很隐蔽）。统一收敛到 `num()`。

**未验证 / 局限**：门槛里的 70%/50%/1% 是**判断值不是实测**；观测时长与标注量是经验推算；
报告脚本不解密（原文需按 `content_hmac` 关联 `message` 表后由有权限的人解）；
Jev 厂商限流阈值与成本仍未测；本轮工具的端到端跑通只证明**链路可用**，样本量远不足以支撑结论。
