## 2. 单元测试要点

- **一切外部依赖 Mock**：LLM/DB/Redis/MCP 不做真实调用。
- 重点用例：护栏分级判定边界（词典命中但情绪分不足 → L1 而非 L2）；RRF 融合排序稳定性；历史窗口裁剪（20/50 边界）；幂等键冲突路径；Agent 状态机非法迁移拒绝。

## 3. 集成测试要点（testcontainers）

- SSE 流：断言事件序列 start→chunk*→end 的完整性与 usage 字段。
- 降级链：WireMock 让 DeepSeek 返回 503/超时 → 验证切换 DashScope → 双挂 → E5000，且 `llm.call` 指标 outcome 正确。
- Agent 补偿：提交任务 → 杀执行线程模拟崩溃 → 重启扫描 → 任务标 FAILED。
- 越权：用户 A 的 Token 访问用户 B 的会话/历史/删除接口 → 全部拒绝（IDOR 验收，07 §3）。

## 5. Prompt 回归（Golden Set）

1. 用例集：≥ 30 条典型问题，每条含「评估 rubric」（如：体现共情、给出可执行步骤、未越心理边界）而非关键词列表。
2. 判定：**LLM-as-judge**（独立模型按 rubric 打分）+ 禁用词硬校验（出现「操控」「拿捏」类词直接 fail）。旧计划的关键词包含匹配已否决——它会把「换个说法但意思对」的好回复误判为失败。
3. 触发：System Prompt 或检索参数变更时手动/流水线触发，结果按 `prompt_version` 归档对比（08 §2.4）。
4. 门禁：≥ 80% 通过可发布；60–80% 人工复审；< 60% 阻断。

## 5.5 检索质量回归（ADR-15，Phase 3 起）

- **评估集**：`scripts/retrieval-ground-truth.json`，**30 例**（2026-09-05 扩样，覆盖 30 篇知识主题：术语/口语/复合问三类），每例标注期望文档关键字。
- **运行**（2026-09-05 API 化，不再嗅探日志）：
  ```bash
  ADMIN_API_KEY=<key> python scripts/retrieval_eval.py --base http://localhost:<port>/api
  ```
  端点 `GET /admin/rag/retrieve?query=…`（X-Admin-Key 鉴权）直测检索层，绕开 classify 路由波动（simple 分支不检索造成的假阴性）。
- **指标**：**Recall@5 + MRR@5**（父级去重后每文件一票；P@5 父口径有上限失真，弃用）。
- **基线（n=30，2026-09-05）**：Recall@5=**1.00**、MRR@5=**0.817**（hybrid+topK8，jieba 查询分词，无改写）。
- **触发**：切块/嵌入模型/检索策略/知识库文档增删变更时跑，对比归档基线。
- **历史坑位**：① classify 路由不稳定会把无 RAG 的例判 0——现已 API 化根治；② 删除文档后必须同步清 `target/classes/document/` 再 reindex（loader 读 classpath，maven 不清删除资源）；③ 评测脚本需连 admin 端点而非日志文件（多实例混写假阴性）。

## 5.6 生成质量回归（Answer Correctness，2026-09-04 起）

- **评估集**：`retrieval-ground-truth.json` 中带 `golden_answer` 的 **16 例**（标准答案要点）。
- **运行**（LLM-as-judge，脚本直调智谱，不依赖 Langfuse 配置链）：
  ```bash
  python scripts/answer_eval.py --base http://localhost:<port>/api --rounds 3
  ```
  走真实 chat SSE 链路 → judge（glm-4-flash，Correctness 模板中文版）评 0-1 + reason。
- **多轮均值（关键）**：每例跑 3 轮取均值——单轮 judge 采样噪声大（实测 gt_01 单轮出现过 0.5，3 轮实为 0.80/0.80/0.90）。**单轮结论不可信**。
- **基线（2026-09-05）**：AC=**0.90**（n=16 ×3 轮）。
- **用途**：prompt/模型/知识库/检索策略变更后对比；评测驱动修复闭环已实战三次（冷静期补年份 0.5→1.0、煤气灯文档拆分、QueryRewriter 关闭）。

## 6. 性能测试场景

> **口径（2026-09-15 重写，Phase 6 / ADR-29）**：容量一律按**同时在途模型请求数**表述，
> 不用"同时在线人数"——两者换算见 `docs/phase6-concurrency/spec.md` §3.1。
> 成因：真正的天花板是**上游厂商的并发上限（实测 ≈24）**，与在线人数无关。

| 场景 | 目标 |
| --- | --- |
| 在途 ≤ 24（= 闸门 = 厂商上限） | **拒绝 0**；SSE P95 首 token < 1.5s；厂商 429 = 0 |
| 在途 25–48（= 闸门 + 有界队列容量） | **拒绝率 ≤ 20%**（改造前为 50%）；拒绝必须带可读说明与 `retryAfterSec` |
| 在途 > 48（超出 闸门+队列） | `queue_full` 立即拒绝**属正确行为**，不是故障；不得出现 5xx |
| 100 并发 Agent 提交 | 排队 < 5s，池满快速拒绝（B5002）而非超时挂死 |
| 混合负载 30 分钟 | 各池队列深度不持续增长，PG 连接池稳定 |
| 故障注入：LLM 厂商 429 风暴 | 降级链生效，全站不雪崩 |

### 6.1 性能工程计划（2026-09-06 立项）

**立项背景**：健壮性审计确认——降级链已闭环、并发保护机制工作正常，但**容量与高并发 NFR
从未验证**，且当前容量事实不支持高并发。此项为独立性能工程任务，不是日常改动。

**现状（实测事实）**
- 全局并发闸门 `app.online.max-inflight` 默认 **8**（yml 无覆盖 → 生产同为 8）。
- 初检（2026-09-06）：20 并发 → 8 进 + 12 闸门拒（4003）、0 错 0 超时、3s 收尾。
  **保护机制正确；但第 9 个真实用户即被拒**——8 是单模型预算下的保守保护值，非容量能力。
- 按当前 8 上限，200 并发下约 96% 请求被拒 → §6 的 NFR 不可能达标。

**阻塞项（先决）**
1. ~~LLM 厂商并发上限未知~~ → **已实测消解**。⚠️ **2026-09-15 更正**：2026-09-07 那次"厂商无硬并发限流 ≥40"
   的结论**是错的**——那次是**经过应用**做的阶梯压测，而应用的闸门恰好是 24，真实并发根本没打上去。
   直连上游（绕过应用）重测：≤16 全通；**32 → 7~10/32 得 429**；64 → 37~38/64；96 → 73/96；
   **超额是立即 429，不排队**。→ **厂商有效并发上限 ≈ 24**，这才是真正的吞吐天花板；
   调高内部阈值只会把压力透传成 429 并被重试放大。详见 §8.8 与 `docs/phase6-concurrency/spec.md` §1.1。
2. ~~产品容量目标未定~~ → **已定案（2026-09-15，用户确认）**：**不追求具体在线人数数字**，
   目标是"**不崩 + 拒绝有可读说明**"。闸门维持 `app.online.max-inflight` = **24**（= 厂商上限，
   放进来多少就能同时发多少），超额改由**有界排队**吸收（见实施步骤 5）。

**实施步骤**
1. ✅ 厂商并发上限已实测（**≈24**，2026-09-15 直连复测更正）——见上方阻塞项 1。
2. ✅ 压测工具就位并已修正：`scripts/loadtest.py` 支持多用户（`--users`，测全局容量）、单用户（测每用户突发桶）、
   `--warmup` 预热轮、过载/限流分类统计。
2b. ✅ 已做（2026-09-07）：图执行脱离 ForkJoinPool.commonPool → 显式线程池 `graphExecutor`
   （`app.graph.executor.*`，core=24/max=24/queue=0，与闸门对齐）。
3. ✅ 阶梯压测已完成：厂商侧 1→96；应用侧（多用户）8/24/32/48/64——见 §8.8。
4. ✅ 瓶颈定位完成：**上游厂商并发上限是唯一瓶颈**；Tomcat / graphExecutor / Hikari 在实测档位下均未成为瓶颈。
5. ✅ 调优与体验抉择（2026-09-15 落地）：闸门保持 24（对齐厂商上限），
   **超限由"快速拒绝"改为"有界排队"**（`app.online.wait-ms` 默认 3000 / `app.online.queue-capacity` 默认 24）——
   实测 32 并发拒绝数 8 → **0**，48 并发 24 → **1**（见 §8.8）。另加启动期口径校验 `CapacityGuard`。
6. ⏳ 30 分钟混合负载稳定性：**尚未执行**（需专门的长时压测窗口，属独立任务）。

**验收标准**（2026-09-15 按在途口径重写）
- 在途 ≤ 24：拒绝 0、厂商 429 = 0、SSE P95 首 token < 1.5s。
- 在途 25–48：拒绝率 ≤ 20%（改造前 50%）——闸门拒**计入**拒绝率，但有界排队应把大部分尖峰吸收掉。
- 任意档位：**不得出现 5xx**；拒绝必须带可读文案与 `retryAfterSec`（"无说明的拒绝"视为不合格）。
- 30 分钟混合负载：连接数与队列深度不持续增长（⏳ 未执行）。

## 7. E2E 冒烟清单（手动执行版，Phase 1 脚本化）

**前置**：MySQL/Redis 已启动；`DEEPSEEK_API_KEY`、`DASHSCOPE_API_KEY` 已注入；应用以 `local` profile 启动（`http://localhost:8088/api`）。

### 7.1 认证链路

```bash
# 注册（首次）→ 返回 token
curl -s -X POST http://localhost:8088/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"smoke_user","password":"Passw0rd!"}'
# 登录 → 记录 token
curl -s -X POST http://localhost:8088/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"smoke_user","password":"Passw0rd!"}'
# 身份确认 → 应返回当前用户信息
curl -s http://localhost:8088/api/auth/me -H "Authorization: Bearer $TOKEN"
```

### 7.7 记忆系统（ADR-14，Phase 2 起纳入冒烟）

```bash
# 1) 制造一段对话（7.2 已产生 smoke_* 会话）→ 等待萃取（异步，轮询 /memory/facts 最多 60s）
curl -s "$BASE_URL/memory/facts" -H "Authorization: Bearer $TOKEN"
# 2) 跨会话召回：新会话（新 chatId）发起包含历史事实的问题，回复应体现记忆
```

## 8. 韧性与检索回归（ADR-23/24/25，2026-09-13 实测）

### 8.1 单元与契约层

- `mvn test` **149 项全绿**（含 `ProviderCircuitTest`、`ChatEntryTest`、`LlmGatewayTest`、`RateLimiterTest`、`StreamRegistryTest`、`RerankDocumentPostProcessor` 相关、`LocalDocumentReranker` 相关）。

### 8.2 检索质量对照（45 例 ground-truth，131 篇 / 439 块）

| 配置 | Recall@5 | MRR@5 |
| --- | --- | --- |
| **重排关闭（默认）** | **0.98** | **0.824** |
| 重排开启 + 不扩窗（topN=8） | 0.96 | 0.783 |
| 重排开启 + 扩窗（topN=20） | 0.91 | 0.749 |

**结论**：`mode=local` 在当前模型/配置下为**负收益**，默认关闭是正确值（详见 ADR-25 状态）。评测入口 `/admin/rag/retrieve?rerank=true` 复用生产 `RerankDocumentPostProcessor`，使检索评测可覆盖重排路径。

### 8.8 高并发容量实测与有界排队（Phase 6 / ADR-29，2026-09-15）

**背景**：§6.1 的"厂商无硬并发限流 ≥40"是一个**经过应用测量得出的错误前提**（应用闸门恰好 24，把真实并发压住了）。
本轮改为**直连上游**复测，并据此重定容量口径与超容行为。

**(1) 厂商并发上限（直连 `https://open.bigmodel.cn/api/paas/v4`，glm-4-flash，绕过应用）**

| 并发 | 成功 | 429 | 超时 | 延迟中位 | 墙钟 |
| --- | --- | --- | --- | --- | --- |
| 1 / 4 / 8 / 16 | 全部 | 0 | 0 | 0.5–0.9s | 1–2s |
| 32 | 25（另轮 22） | **7（另轮 10）** | 0 | 0.67s | 2s |
| 64 | 24（另轮 27） | **38（另轮 37）** | 2 | 1.14s | 30s |
| 96 | 23 | **73** | 0 | 0.57s | 2s |

→ **有效并发上限 ≈ 24**；超额**立即 429、不排队**。这是真正的吞吐天花板，与应用实现无关。

**(2) 应用侧多用户阶梯（每用户独立 token，真实检索 + 真实 LLM）**

| 并发 | 改造前 ok / 拒 | 改造后 ok / 拒 | 改造后 TTFT 中位 / P95 |
| --- | --- | --- | --- |
| 24 | 24 / 0 | 24 / 0 | 1.3–1.7s / 1.6–3.1s |
| 32 | 24 / **8** | **32 / 0** | 0.63s / 1.73s |
| 48 | 24 / **24** | **47 / 1**（另轮 40 / 8） | 1.85s / 4.31s |
| 64 | — | 48 / 16（= 24 在途 + 24 排队，超出者 `queue_full`） | 0.62s / 1.40s |

- **全档位零 5xx、零厂商 429**：闸门 24 恰好卡在厂商上限，未把压力透传到上游。
- 首档含冷启动（JIT / 首次调用），延迟高于第二档 → **压测必须丢弃预热轮**（工具已内置 `--warmup`）。

**(3) 有界排队（ADR-29）落地效果**：闸门满时在 `wait-ms`（默认 3000ms）内排队等待腾出的额度，
等待者数量受 `queue-capacity`（默认 24）限制；到点仍无额度才拒绝，文案带已等待时长与 `retryAfterSec`。
**代价**：48 并发时 TTFT P95 升至 4.31s（含排队等待）——用延迟换拒绝率，符合用户"不追求数字、只求不崩 + 拒绝有说明"的取舍。

**(4) 一处测量工具的坑（已修）**：`scripts/loadtest.py` 原**所有并发线程共用同一个用户 token**，
测到的其实是"**每用户突发桶**"而非全局容量——§8.5 F6 曾据此得出"burst 先于闸门生效"的错误结论。
现支持 `--users N` 区分两种模式，并在输出中标注。另：**单人顺序连发 12 次不触发限流**
（每次请求 2–3s，桶按 1/s 回填，消耗慢于回填）→ 突发桶应视为**防脚本/防重放**，不是容量手段。

**本轮验证**：单测 170/170（新增 10）；真实 E2E 22/22（`outputs/e2e-live-p6.json`）；
Langfuse 平台复验 11/11（`outputs/verified-langfuse-p6.json`）。

**未验收**：30 分钟混合负载稳定性（需专门长时窗口，独立任务）。
