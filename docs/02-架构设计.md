### 1.4 Harness 七层现状核查（2026-09-26 实测，按代码逐层核对）

原始设计见 `archive/升级方案-实施计划.txt`（"把现有代码的逻辑抽象成 7 层接口"）与 `archive/升级方案-实施计划-精简版.txt`。
下表是**按当前代码实际情况**填的，不是复述设计稿——两者并不一致。

| # | 层 | 设计稿说法 | 代码实际位置 | 状态 |
| --- | --- | --- | --- | --- |
| ① | 治理 governance | 无 → TenantContext + JWT 配额接口 | `harness/governance/`（6 类）+ `tenant/` + `audit/` | ✅ **超预期**：护栏规则外置 DB、advisor 链已挂、双向检查、自伤信号 |
| ② | 验证 validation | 无 → 评估接口空壳 | **无独立接口层**，能力分散：`admin/AdminController` 的 golden-set 评测端点（复用生产重排组件）+ Python 侧 `scripts/retrieval_eval.py`、`answer_eval.py` 等 62 脚本 | ⚠️ **换了实现路径**：接口层没做，能力做在"管理端点 + 脚本"两处且已跑出真数据（MRR / 答案质量 A/B） |
| ③ | 工具 tool | ToolRegistry 接口 → 适配器包装 | `tools/`（8 工具）+ `infrastructure/orchestration/tools/`（ToolResolver/AgentToolPolicy/ToolCapability）+ `mcp-server/` | ✅ **超预期**：白名单、能力解析、MCP 客户端与本地工具统一 |
| ④ | 编排 orchestration | AgentLoop 接口 → 适配器包 BaseAgent | `infrastructure/orchestration/` + `graph/`（8 node，ADR-19 自绘 StateGraph）+ `ChatEntry`/`ChatExecutor`/`AgentRegistry` | ✅ **路线换了**：不是接口+适配器，是自绘状态图；能力等价且入口已收敛 |
| ⑤ | 上下文 context | ChatMemory 接口 → 包装 FileChatMemory | `memory/`（9 类：MessageChatMemory/MemoryExtractor/MemoryVectorStore/Desensitizer…） | ✅ **超预期**：三层记忆 + 脱敏 + 向量记忆 + 定时萃取 |
| ⑥ | 可观测 observability | 预留接口 | `harness/observability/ObservabilityConfig` + `infrastructure/observability/` + Langfuse/Prometheus/Sentry | ✅ 已接，且有 ADR-44 的 span 边界治理 |
| ⑦ | 执行 execution | 无 → 沙箱太重，只做状态持久化接口 | `GraphCheckpointConfig` + `StreamRegistry` + 停止/续跑；**无沙箱** | ⚠️ **半落地**：状态持久化有，隔离沙箱按设计稿就没做 |

**核查结论（不夸大）**：

1. 用户指出的"原本就做了七层"**成立**——设计稿确实这么规划，且 6/7 层有对应实现。
2. 但**不能说"七层完整落地"**：② 验证层的独立接口层不存在（能力挪到了管理端点 + Python 脚本），⑦ 执行层按原设计就没做沙箱。
3. **物理分层没有 7 个包**：只有 `harness/governance` 和 `harness/observability` 两个子包，其余五层散在 `tenant/` `memory/` `tools/` `infrastructure/orchestration/`。设计稿说的"7 层接口 + 适配器"这层壳**从未建立**，各层是按业务需要自然长出来的。
4. 因此对外表述应写"**覆盖 Harness 核心层次**"（治理/编排/上下文/工具/可观测），**不要写"完整实现七层架构"**——后者与代码不符。

## 2. 目标架构（To-Be）

```
                    ┌──────────────── Controller 层（薄）────────────────┐
                    │  ChatApi · AgentApi · MemoryApi · AuthApi · VoteApi │
                    └───────┬───────────────────────────────┬────────────┘
                            │ 统一鉴权/限流/trace 过滤器      │
                   ┌────────▼─────────┐            ┌────────▼─────────┐
                   │  ChatPipeline     │            │  AgentRuntime     │
                   │  （管道 A：秒级）  │            │  （管道 B：分钟级）│
                   │  Guard→Memory→   │            │  ReAct 循环+工具   │
                   │  RAG→Skill→LLM   │            │  任务持久化+补偿   │
                   └────────┬─────────┘            └────────┬─────────┘
                            │            ChatKernel（共享）  │
                    ┌───────▼──────────────────────────────▼────────┐
                    │ LlmGateway（多厂商路由/重试/降级/成本计量）      │
                    │ RetrievalGateway（统一混合检索，单实现）        │
                    │ MemoryGateway（会话/消息/摘要）                 │
                    │ SkillGateway（进化模块读写）                    │
                    └───────┬──────────────┬──────────────┬──────────┘
                        MySQL(+pgvector)  Redis        mcp-server(独立进程)
                                            外部: DeepSeek 官方(LLM 主链；降级链当前未配置目标，见 ADR-51)
```

> **LLM 链现状（ADR-51，2026-09-27）**：
> `DeepSeek 官方 https://api.deepseek.com` + `deepseek-flash`（**唯一在用的级**）。
> 两个降级级默认**全部关闭**——不是"不需要容灾"，而是两个目标**实测都不可用**：
> `DashScope qwen-plus`（域名本机不可达，属"假备用"）、`bigmodel glm-4-flash`（实测 400）。
> 保留假备用比没有备用更糟：它让链路看起来有三层、实际只有一层，还让每次主链故障
> 白等一次上游超时，并污染指标与排障判据。
>
> **⚠️ 架构能力仍在，别误读为"砍成单级"**（这是本节的要点）：
> - `LlmGateway` 的降级目标是 `@Autowired(required=false)` 注入的，**谁没注册就自动跳过**；
>   链的遍历在同步路径是 `for (Tier t : degradeTiers())`、流式路径是
>   `degradingStream(..., List<Tier> tiers, int tierIndex)` 的**递归**——两者都**不写死级数**。
> - 每级各有**独立熔断器**；`LlmGateway` 是**唯一重试所有者**（ADR-23），每级只尝试一次
>   （降级不是重试）。这些不变量与链长无关。
> - **换模型**：主链换供应商/模型只改 yml（`OPENAI_BASE_URL` / `OPENAI_MODEL`），**零代码**。
> - **加一级**：写一个 `@Bean` 注册进去即可；但 `degradeTiers()` 目前是 2 个**具名槽位**
>   （`fallback` / `lastResort`，构造器同名参数），**加第 3 级要改这两个签名**——已知限制。
> - **已知限制**：`app.llm.fallback-enabled` 是**降级总闸**（`canDegradeTo` 只看它），
>   与 `last-resort-enabled`（只管 bean 是否注册）**语义不对称**，故当前**无法单独启用某一级**。
>
> **历史链形（ADR-48，已被 ADR-51 取代，原文保留）**：
> `OpenRouter stealth/space-bunny-alpha`（primary）→ `DashScope qwen-plus`（fallback）
> → `bigmodel glm-4-flash`（last-resort）。详见 `03-技术决策记录.md` ADR-48 / ADR-51。
>
> ⛔ 已知例外：`VisionChatClient` 绕过网关直连供应商（无闸门/熔断/计量），独立缺陷未修。

> **Phase 2 状态（2026-08-20）**：管道 A（ChatPipeline）已由 ChatService 统一 ChatClient 落地；
> 管道 B（AgentRuntime）任务持久化 + 心跳补偿已落地（ADR-3），**执行循环已切换为
> spring-ai-alibaba ReactAgent**（ADR-8，2026-08-20，AgentLoopExecutor）；
> 恋爱辅助能力（话术三级/情绪刹车片）为 SRS 待立项项（11 §3.2），不在当前管道图内。

### 2.1 分层规则

- **Controller 只做**：参数校验、身份透传、SSE 桥接。不出现业务分支。
- **Pipeline/Runtime 编排**：以显式的步骤对象组合（每个步骤是独立 Bean，可单测），取代 LoveApp 的方法重载爆炸。
- **Gateway 收口所有外部依赖**：LLM、检索、存储各自一个门面，上层永远不直接触碰 SDK。这是降级链、成本计量、Mock 测试的唯一插入点。
- **两管道资源隔离**：聊天走响应式流，不占专用线程池；Agent 用有界队列线程池 + Abort + 任务表，绝不 CallerRuns（理由见 03 ADR-2）。

### 2.2 部署形态

- 单体优先：主应用 + mcp-server 两个进程。微服务化**不在路线图内**（团队规模与流量不支持）。
- mcp-server 独立部署为 Streamable HTTP（2026-08-17 已落地，MCP 规范中 SSE 已弃用），主应用经 `/mcp` 连接，便于独立扩缩容与故障隔离。
