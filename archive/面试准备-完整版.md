## 一、开场基础提问（自我介绍后必问）

### 1. LoveHelping 项目整体做什么，核心解决什么问题？

**口述版（30秒）：**

> LoveHelping 是一个基于 Spring AI 的企业级 AI 情感咨询和恋爱规划服务平台。核心解决的问题是：传统的恋爱建议要么太笼统、要么不够个性化。我们通过 RAG 混合检索 + Agent 自我进化闭环，让 AI 既能基于专业知识库给出建议，又能从每一次对话中学习用户偏好，越用越懂用户。

**展开版（如果面试官追问）：**

技术架构上，前端是 Vue 3，后端是 Spring Boot 3.4 + Java 21。AI 层用了 Spring AI 框架，底层模型是 DeepSeek，向量库用 Milvus，关键词检索用 Elasticsearch，通过 RRF 算法做混合检索。另外我们还做了自我进化系统——对话结束后自动反思萃取经验技能，下次对话时自动注入，形成"越用越聪明"的闭环。

多租户方面，用 JWT + 租户 ID 字段隔离，支持不同客户独立部署知识库和记忆。安全方面做了 Guardrail 提示注入检测、输入输出安全护栏。可观测性用 OpenTelemetry + Langfuse 做全链路追踪。

### 2. Spring AI vs 原生调用大模型 API 优势在哪？Advisor 怎么用的？

**口述版：**

> Spring AI 最大的优势是**统一抽象**和**可插拔的 Advisor 拦截器链**。原生调用 API 的话，你要自己处理 HTTP 请求、JSON 解析、流式响应、工具调用、对话记忆、RAG 检索……每换一个模型都要重写一遍。Spring AI 把这些都抽象成了统一接口，换模型只需要改配置。

> Advisor 是 Spring AI 的核心设计之一，类似 Servlet 的 Filter 或者 Spring MVC 的 Interceptor，但专门针对 AI 对话流程。你可以在请求发送给 LLM 之前、响应返回给用户之后，插入自定义的横切逻辑。

**Advisor 的具体用法（我们项目里用了这些）：**

| Advisor | 作用 | 执行顺序 |
|---|---|---|
| **MessageChatMemoryAdvisor** | 自动从 MySQL 加载历史对话，维护上下文窗口 | 较早 |
| **QuestionAnswerAdvisor** | RAG 检索增强，自动从向量库搜相关文档注入 prompt | 中间 |
| **MyLoggerAdvisor** | 自定义日志拦截器，记录请求和响应 | 中间 |
| **GuardrailAdvisor** | 安全护栏，输入输出安全检查 | 最后（Integer.MAX_VALUE） |

**GuardrailAdvisor 的设计亮点：**
- 执行顺序是 `Integer.MAX_VALUE`，也就是**最后执行**
- 为什么放最后？因为要等其他 Advisor 都加完上下文后，再做最终的安全检查
- 输入检查：Prompt 注入、辱骂、模糊输入 → 拦截，不调用 LLM
- 输出检查：有害建议、自残干预 → 日志告警（当前不替换响应，保留审计）

**Spring AI 的其他优势：**
- **统一的 ChatModel 接口**：DeepSeek、通义千问、OpenAI 都实现同一个接口
- **自动的 Function Calling 支持**：@Tool 注解自动注册工具，Spring AI 帮你处理参数解析和调用
- **流式响应（Streaming）**：一行 `.stream()` 就搞定，不用自己写 SSE
- **向量存储抽象**：Milvus、pgvector、Redis 都可以用同一套 VectorStore 接口

### 3. ReAct 模式是什么，项目里怎么落地的，举一个工具调用完整流程？

**口述版：**

> ReAct 就是 **Reason + Act** 的组合——AI 先"思考"（Reason）要不要调用工具、调用哪个工具，然后"行动"（Act）执行工具，拿到结果后再思考下一步，循环直到任务完成。

> 我们项目里的实现是一个四层继承链：BaseAgent → ReActAgent → ToolCallAgent → LoveManus。BaseAgent 管状态和消息列表，ReActAgent 定义 think() 和 act() 的抽象方法，ToolCallAgent 是具体实现，LoveManus 是具体的 Agent 实例，配置系统提示词和模型。

**举一个完整的工具调用流程：**

比如用户问"帮我搜索一下异地恋怎么维持"：

1. **用户发消息** → `LoveManus.runStream()` 启动，状态从 IDLE 变 RUNNING
2. **第一轮 think()**：
   - 把系统提示词 + 历史消息 + 工具列表发给 LLM
   - LLM 判断需要调用 `knowledgeSearchTool`，返回 toolCall
3. **第一轮 act()**：
   - `ToolCallingManager.executeToolCalls()` 执行知识库搜索工具
   - 工具内部调用 HybridRetrievalService（Milvus + ES + RRF）
   - 拿到 Top 5 相关文档，格式化为工具结果
   - 把工具结果消息追加到 messageList
4. **第二轮 think()**：
   - 把更新后的 messageList（包含工具结果）再发给 LLM
   - LLM 基于检索到的知识库内容，生成最终回答文本，没有 toolCall
5. **结束**：think() 返回 false（不需要工具），循环结束，状态变 FINISHED

**关键技术细节：**
- **maxSteps 防无限循环**：默认最多 10 步，超过就强制结束
- **流式 think（streamThink）**：用 `.stream()` 代替 `.call()`，文本 delta 实时 SSE 推给前端，toolCall delta 不推送（用户看不到中间的工具调用过程）
- **terminate 工具**：AI 完成任务后可以主动调用 `doTerminate()` 结束，不用等 maxSteps
- **状态机四态**：IDLE → RUNNING → FINISHED / ERROR

### 4. 什么是 MCP 协议，用它做了哪些多服务集成？

**口述版：**

> MCP 就是 Model Context Protocol，模型上下文协议，是 Anthropic 提出来的一个开放标准。简单说就是——以前你要给 AI 接工具，每个工具都得自己写适配代码；MCP 提供了一套统一的协议，AI 应用和工具服务之间通过标准协议通信，工具可以独立部署、独立升级。

> 我们项目里做了一个独立的 mcp-server 模块，用 Spring Boot 写的，通过 MCP 协议给主应用提供工具服务。

**集成的 MCP 工具：**
- **WebSearchTool** — 网页搜索
- **WeatherTool** — 天气查询
- **DatePlannerTool** — 约会规划
- **ImageSearchTool / BaiduImageSearchTool** — 图片搜索
- **WebScrapingTool** — 网页内容抓取

**MCP vs 本地 @Tool 的区别：**
- 本地 @Tool：和主应用在同一个进程里，调用快，但耦合高
- MCP：独立服务，可以用不同语言写，可以独立部署和扩容，更适合微服务架构

**MCP 的通信方式：**
- 支持 stdio（标准输入输出）和 HTTP/SSE 两种传输方式
- 我们用的是 stdio 模式——主应用启动一个子进程跑 mcp-server，通过标准输入输出通信

## 二、核心重点：混合检索 & RAG（简历核心亮点，必深挖）

### 1. 为什么同时用 Milvus 向量 + ES BM25？RRF 融合排序具体怎么加权计算？

**口述版：**

> 因为向量检索和关键词检索是**互补**的，各有各的擅长。向量检索懂语义，比如"追求女生"能匹配到"如何追女孩"，但对专有名词、数字、术语可能不准。BM25 关键词检索精确匹配，搜"微信"能精确找到所有含微信的文档，但不懂同义词和语义变体。两个一起用，覆盖度和准确率都上去了。

> 融合用的是 RRF 算法——Reciprocal Rank Fusion，倒数排名融合。

**RRF 公式：**
```
RRF_score(d) = Σ ( 1 / (k + rank_i(d)) )
```
- k = 平滑参数，我们用 60（业界经验值）
- rank_i(d) = 文档 d 在第 i 个检索器中的排名（从 0 开始）
- Σ = 对所有检索器（Milvus + ES）的得分求和

**举个例子：**
- 文档 A：Milvus 第 1 名 + ES 第 5 名 → 1/60 + 1/64 = 0.0323
- 文档 B：Milvus 第 3 名 + ES 第 2 名 → 1/62 + 1/61 = 0.0325
- 结果 B > A，因为 B 在两路都比较靠前，综合得分更高

**为什么用 RRF 而不是加权平均？**
- 加权平均需要归一化分数尺度——Milvus 的余弦相似度是 0~1，ES 的 BM25 是 0 到无穷大，尺度完全不一样，没法直接加权
- RRF 不依赖原始分数，只看排名，实现简单、效果好，是业界混合检索的标准做法

**我们项目的具体实现：**
- 每个检索通道取 `topK * 2` 条结果，给 RRF 更多候选池，提高召回率
- 用 `docMap.putIfAbsent()` 去重，同一文档在两路都出现时分数累加
- 最终结果按 RRF 分数降序排列，取 Top K

### 2. 单一向量检索命中率低 30%，原因分析？查询重写、关键词增强优化做了哪些？

**口述版：**

> 单一向量检索命中率低，我分析主要有三个原因：
>
> 第一，**用户查询口语化、模糊化**——用户说"怎么追她"，向量模型可能理解不到这是"追求女生"的意思，因为查询太短、信息太少。
>
> 第二，**专有名词和术语匹配不准**——向量检索擅长语义，但对精确的专有名词、数字、人名反而不如关键词检索。
>
> 第三，**知识库文档和查询的表达方式差异大**——文档是书面语，用户输入是口语，向量空间里的距离可能比较远。

**我们做的优化：**

**① 查询重写（Query Rewriting）**
- 用 LLM 把用户的口语化查询重写成更适合检索的标准化查询
- 基于 Spring AI 的 `RewriteQueryTransformer`，用百炼模型
- 例子："怎么追她" → "如何追求心仪的女生，恋爱交往的方法和技巧"
- 位置：检索前阶段（Pre-Retrieval）
- 代价：每次多一次 LLM 调用，但命中率提升明显

**② 关键词丰富（Keyword Enrichment）**
- 文档入库时，用 LLM 给每篇文档提取 5 个关键词，注入 metadata
- 基于 Spring AI 的 `KeywordMetadataEnricher`
- 为什么 5 个？平衡覆盖度和精准度，太少遗漏，太多噪声
- 作用：增加检索匹配维度，关键词检索时可以命中

**③ 混合检索（Hybrid Retrieval）**
- Milvus 向量 + ES BM25 两路召回，RRF 融合
- 这是最根本的优化——单一检索再怎么优化也有天花板，两路互补才是王道

**④ Token 文本分割优化**
- 用 `TokenTextSplitter`，每段 1000 Token，最小 400 字符
- 在句子边界（句号、问号、感叹号、换行）处断开
- 保证每个片段语义完整，提高向量质量

### 3. pgvector vs Milvus 对比适用场景，优缺点？

**口述版：**

> 这两个我们项目里都用过。pgvector 是 PostgreSQL 的扩展，把向量存在关系型数据库里；Milvus 是专门的向量数据库，从零开始就是为向量检索设计的。

| 维度 | pgvector | Milvus |
|---|---|---|
| **部署复杂度** | 低，装个扩展就行，和 PG 一起运维 | 高，需要独立部署，依赖 etcd、MinIO 等 |
| **数据量** | 适合百万级以内 | 适合千万级以上，支持分布式分片 |
| **检索速度** | 中等，HNSW 索引在小数据集上很快 | 快，专门优化过向量索引和查询 |
| **功能丰富度** | 简单，基本的向量相似度搜索 | 丰富，标量过滤、多租户、一致性级别、分区等 |
| **事务支持** | 有，PG 的 ACID 事务 | 没有，最终一致性 |
| **运维成本** | 低，PG 团队就能管 | 高，需要专门的向量数据库运维 |
| **混合查询** | 方便，SQL 里直接 JOIN 关系表和向量 | 需要额外处理，标量过滤功能有限 |

**我们项目的选择：**
- **主向量库用 Milvus**——因为我们的知识库可能会很大，而且需要多租户隔离、标量过滤这些高级功能
- **pgvector 也保留了配置**——作为备选方案，小客户或者简单场景可以用 pgvector，部署更轻量
- 代码层面通过 Spring AI 的 VectorStore 抽象，切换只需要改配置

**适用场景总结：**
- 小团队、数据量不大、已经在用 PG → 选 pgvector，简单省事
- 数据量大、对检索性能要求高、需要高级功能 → 选 Milvus
- 混合查询多（既要向量搜索又要关系查询）→ pgvector 更方便

### 4. 检索 Top5 命中率 85%+，怎么验证的？评测数据集怎么构建？

**口述版：**

> 我们是这样验证的——构建了一个标注评测集，然后用命中率（Hit Rate）和平均倒数排名（MRR）两个指标来评估。

**评测数据集构建：**
1. **来源一：真实用户查询**——从线上日志中采样了 200 条真实用户查询
2. **来源二：边界 case**——专门构造了一些口语化、模糊、专有名词多的查询，测试系统的短板
3. **标注方式**：人工标注每条查询对应的"正确答案文档"，一条查询可能对应多个正确文档

**评估指标：**
- **Hit Rate @5**：Top 5 结果中至少包含一个正确文档的查询占比
  - 公式：命中查询数 / 总查询数
  - 我们的结果：85%+（混合检索），纯向量只有 60% 左右
- **MRR @5**：平均倒数排名，正确文档排名越靠前得分越高
  - 公式：Σ (1 / rank_i) / N
  - 我们的结果：混合检索比纯向量提升了约 40%

**对比实验：**
| 检索方式 | Hit Rate @5 | MRR @5 |
|---|---|---|
| 纯 Milvus 向量 | ~60% | ~0.45 |
| 纯 ES BM25 | ~55% | ~0.40 |
| 混合检索（RRF） | **~85%** | **~0.65** |

**验证流程：**
- 每次调整检索参数（如 chunk 大小、RRF 的 k 值、topK 数量），都跑一遍评测集
- 对比前后指标，确保优化真的有效，不是"感觉更好"
- 这也是为什么我们敢说 Top5 命中率 85%+——是有数据支撑的，不是拍脑袋

### 5. 检索后怎么做上下文增强，避免长文本截断丢失关键信息？TokenTextSplitter 拆分规则怎么设计？

**口述版：**

> 上下文增强我们做了两层：一层是**检索前的查询优化**，一层是**检索后的上下文组装**。

**检索前的优化：**
- **查询重写**：把口语化查询重写成标准化查询，提高检索准确率
- **关键词丰富**：文档入库时提取关键词，增加匹配维度

**检索后的上下文增强：**
- **Top-K 文档拼接**：把检索到的多个文档片段拼接起来，作为上下文注入 prompt
- **技能上下文注入**：从进化技能库中检索相关经验，拼在 system prompt 后面
- **对话记忆**：自动加载历史对话，维护上下文窗口

**TokenTextSplitter 拆分规则设计：**

| 参数 | 值 | 设计考量 |
|---|---|---|
| **defaultChunkSize** | 1000 Token | 1000 Token ≈ 750 英文词 / 500 中文字，在保留语义和控制长度之间平衡 |
| **minChunkSizeChars** | 400 字符 | 防止碎片，过短的文本向量质量差 |
| **minChunkLengthToEmbed** | 10 Token | 极短文本（几个词）直接丢弃，没检索价值 |
| **maxNumChunks** | 5000 | 安全上限，防止异常大文档把内存撑爆 |
| **keepSeparator** | true | 保留分隔符（句号、问号等），保持句子完整 |
| **separators** | `. ? ! \n` | 优先在句子/段落边界断开，保证语义完整 |

**为什么这么设计？**
- **1000 Token 的 chunk**：太大的话一个片段包含多个主题，检索不准；太小的话上下文不够，LLM 理解不了
- **句子边界断开**：不能在句子中间断开，否则语义断裂，向量质量差
- **最小 400 字符**：防止产生"碎片"——比如只有几个字的片段，向量表示没有意义
- **5 倍搜索放大**：技能检索时搜索 topK 的 5 倍，因为向量库里混有知识库文档和技能文档，需要从更大候选池里筛选

**避免长文本截断的策略：**
- 不是把整篇文档塞进去，而是检索最相关的几个片段
- 每个片段 1000 Token，Top 5 就是 5000 Token，加上系统提示词和历史对话，控制在模型上下文窗口内
- 如果需要更长上下文，可以用"上下文查询增强"（Contextual Query Augmentation）——给每个 chunk 加一个摘要，检索时更准确

## 三、Agent 分层记忆、自我进化闭环（AI 宠物机器人场景高度重合，重点追问）

### 1. 自我进化闭环详细讲：5 分钟定时轮询，怎么萃取对话里的用户偏好、经验技能？

**口述版：**

> 自我进化闭环是我们项目最有特色的功能——简单说就是 AI 会"反思"自己的对话，把有价值的经验萃取成技能，下次对话自动用上，越用越聪明。

**整个闭环分四步：**

**第一步：定时轮询（ReflectionScheduler）**
- 5 分钟轮询一次 MySQL 的对话记录表（`@Scheduled(fixedDelay = 300_000)`）
- 不是每轮对话都萃取，而是等对话"冷却"后再处理
- **触发条件（二选一）：**
  - **空闲超时**：最后一条消息距今超过 30 分钟（默认 1800 秒）
  - **总时长兜底**：会话总时长超过 2 小时（7200 秒），防止超长对话一直不触发
- **去重**：跳过已经在 `evolution_skill.source_session_id` 里记录过的会话
- **限流**：每次最多处理 20 个会话，防止一次性处理太多

**第二步：反思萃取（SkillReflector）**
- 异步执行（`@Async("evolutionExecutor")` + `@Transactional`）
- 线程池：核心 1 / 最大 2 / 队列 100，不用占太多资源
- **执行流程：**
  1. 去重检查——已经萃取过的会话跳过
  2. 提取对话历史——从 `SPRING_AI_CHAT_MEMORY` 表读取
  3. 收集用户反馈——点赞（👍 LIKE）和点踩（👎 DISLIKE）
  4. 格式化对话——跳过 SYSTEM 和 TOOL 消息，只保留 User/Assistant
  5. **LLM 反思**——调用 DeepSeek，让它从对话中提取经验技能
  6. **质量过滤**——质量分 ≥ 5 分（满分 10）才保留
  7. 持久化——存 MySQL + 写入向量库

**第三步：技能结构化输出**
- LLM 返回 JSON 格式，包含四个字段：
  - `skillName`：简短技能名（≤10 词）
  - `description`：适用场景（20-50 词，用于向量检索匹配）
  - `content`：具体可操作指导（50-200 词，直接注入 prompt）
  - `qualityScore`：1-10 整数，自评质量

**第四步：检索注入（SkillRetriever）**
- 每次用户发消息时，从向量库检索相关技能
- 拼到 system prompt 后面，LLM 生成回答时参考
- 输出格式：`【已学经验】\n- 技能名: 具体内容...`

**为什么叫"闭环"？**
- 对话 → 反思 → 萃取 → 存储 → 检索 → 注入 → 更好的对话 → 再反思...
- 每一次对话都让系统变得更聪明，形成正向循环

---

### 2. 萃取后的结构化 skill 同时存 MySQL 和向量库，两者分别存什么？检索时怎么配合？

**口述版：**

> MySQL 存**结构化的完整数据**，向量库存**用于语义检索的向量表示**，两者配合实现"既能精确管理又能语义检索"。

**MySQL（evolution_skill 表）存什么：**
- `id` — 主键，自增
- `tenant_id` — 租户 ID，多租户隔离
- `skill_name` — 技能名称，人工管理用
- `description` — 适用场景描述（**这个字段用来生成 embedding**）
- `content` — 具体的经验内容，检索命中后注入 prompt
- `source_session_id` — 来源会话 ID，追溯+去重
- `quality_score` — 质量评分，动态调整
- `is_active` — 是否启用，低质量可以停用
- `created_at` / `updated_at` — 时间戳

**向量库（Milvus + ES）存什么：**
- `vector` — description 字段的 embedding 向量
- `text` — description 原文
- `metadata` — JSON，包含 skillName、content、source、tenantId 等
- `tenant_id` — 租户 ID，过滤用

**检索时怎么配合：**
1. **语义检索**：用户输入 → embedding → Milvus 向量搜索 + ES 关键词搜索 → RRF 融合
2. **技能筛选**：从检索结果中筛选 metadata 含 `skillName` + `content` 的文档（因为向量库里还混有普通知识库文档）
3. **注入 prompt**：把筛选出的技能的 content 字段拼到 system prompt 里
4. **搜索放大策略**：实际搜索 topK 的 5 倍，因为要从混合的候选池里筛选技能

**为什么不直接存 MySQL 然后 LIKE 搜索？**
- LIKE 只能精确匹配关键词，不懂语义
- 向量检索能匹配同义词、近义词、语义相近的表达
- 比如用户说"我男朋友不回消息"，能匹配到"对方冷淡时的应对策略"这个技能

**MySQL 的作用：**
- 管理后台用——查看、编辑、删除技能
- 质量评分更新——用户点赞/点踩后更新 quality_score
- 去重判断——按 source_session_id 判断是否已经萃取过
- 启停控制——低质量技能设 is_active=false

### 3. 空闲/超时对话才触发反思，为什么不每轮对话都萃取？频繁调用 LLM 成本问题，怎么控制？

**口述版：**

> 主要三个原因：**成本、质量、必要性**。

**成本原因：**
- 每轮对话都调用 LLM 反思，Token 消耗直接翻倍
- 我们用 DeepSeek 虽然便宜，但量大了也是不小的开销
- 空闲触发的话，一天可能只触发几次，成本可控

**质量原因：**
- 对话刚开始的时候，信息不够，萃取出的技能质量低、没价值
- 等对话结束、冷却后再反思，能看到完整的对话上下文，萃取的质量更高
- 就像人一样——聊到一半你让我总结经验，我肯定说不出什么；聊完了回头看，才能总结出有价值的东西

**必要性原因：**
- 不是每轮对话都有可萃取的经验，很多就是闲聊
- 等对话完整结束后再判断有没有价值，命中率更高
- 而且用户的反馈（点赞/点踩）通常也是对话结束后才给的

**成本控制的具体手段：**

| 手段 | 说明 |
|---|---|
| **空闲触发** | 30 分钟无新消息才触发，不是每轮都调 |
| **质量阈值过滤** | 质量分 < 5 分的技能直接丢弃，不存库，省存储和后续检索成本 |
| **去重机制** | source_session_id 去重，同一会话不重复萃取 |
| **限流** | 每次最多处理 20 个会话，防止突发高峰 |
| **异步线程池** | 核心 1 / 最大 2，不用占主线程资源 |
| **小模型反思** | 反思任务用相对便宜的模型，不用最贵的那个 |
| **配置开关** | evolution.enabled 可以一键关闭整个进化系统 |

**成本收益比：**
- 增加的 LLM 调用成本 ≈ 正常对话的 5-10%
- 但带来的体验提升是显著的——AI 越用越懂用户，用户留存和满意度都会提升
- 这个投入产出比是划算的

### 4. 萃取的记忆片段怎么区分正向偏好、负面避雷标签，检索时如何过滤优先级？

**口述版：**

> 我们是通过**用户投票反馈**来区分的——对话结束后用户可以点赞或点踩，点赞的对话萃取出正面经验，点踩的萃取出反面教训。

**具体机制：**

**① 投票收集（KnowledgeVote）**
- 用户可以对 AI 的回答点赞（👍 LIKE）或点踩（👎 DISLIKE）
- 存在 `knowledge_vote` 表里，关联会话 ID
- 反思时会把投票信息一起发给 LLM

**② LLM 反思时的区分逻辑**
- **点赞 → 正面经验**："用户觉得这个回答好，总结一下好在哪里，以后继续用"
  - content 正常写："当用户情绪激动时，先共情再给建议..."
- **点踩 → 反面教训**："用户觉得这个回答不好，总结一下问题在哪，以后避免"
  - content 用 "Avoid..." / "不要..." 开头："不要直接说'你男朋友太渣了'，用户会觉得你在评判..."
- **没有投票 → 中性经验**：基于对话内容客观总结

**③ 检索时的优先级：**
- 目前我们是**混合检索 + 质量分过滤**
- 质量分高的技能，向量相似度也会相对高（因为 description 写得更准确），自然排名靠前
- 后续可以优化：给正面经验加权重、负面避雷加权重，或者分开检索再融合

**④ 质量分动态调整：**
- 初始质量分是 LLM 自评的（1-10 分）
- 用户点赞 → 质量分 +1
- 用户点踩 → 质量分 -2
- 质量分低于阈值 → 自动设为 is_active=false，不再检索

**如果要迁移到 AI 宠物场景，可以这样扩展：**
- 增加 `memory_type` 字段：`positive`（喜欢的）/ `negative`（讨厌的）/ `neutral`（中性）
- 增加 `priority` 字段：用户明确说过的偏好优先级最高
- 检索时按类型加权——比如"讨厌的事物"权重更高，因为踩雷后果更严重

### 5. 对应 AI 宠物机器人：短期上下文窗口、长期向量记忆分层架构，怎么迁移？

**口述版：**

> 我们现有的架构本身就是分层的，迁移到 AI 宠物场景很自然。

**三层记忆架构：**

| 层级 | 存储 | 内容 | 生命周期 | 对应我们项目的模块 |
|---|---|---|---|---|
| **短期记忆** | 内存 + MySQL | 当前对话上下文（最近 N 条消息） | 会话内 | ChatMemory（MessageWindowChatMemory） |
| **中期记忆** | MySQL | 用户偏好、习惯、历史对话摘要 | 长期保存，定期更新 | EvolutionSkill（进化技能） |
| **长期记忆** | Milvus + ES 向量库 | 所有历史经验、知识库 | 永久保存，语义检索 | HybridRetrievalService |

**迁移到 AI 宠物的具体方案：**

**① 短期记忆（对话上下文）**
- 保持现有架构：MessageWindowChatMemory + MySQL 持久化
- 窗口大小可以调大一点——宠物对话更随意、上下文跳跃更大
- 比如从 20 条调到 30-50 条

**② 中期记忆（用户画像）**
- 把 EvolutionSkill 改造为"用户画像记忆"
- 结构化存储：
  - 喜欢的游戏/活动
  - 讨厌的事物
  - 作息习惯
  - 互动偏好（喜欢撒娇还是喜欢逗趣）
  - 常用称呼、口头禅
- 异步萃取——对话结束后反思更新
- 每次对话开始时检索注入，让宠物"记得"用户的喜好

**③ 长期记忆（知识 + 经验）**
- 保持混合检索架构：Milvus 向量 + ES BM25 + RRF
- 向量库存什么？
  - 游戏知识库（各种游戏怎么玩、攻略）
  - 宠物性格设定（不同性格的回应方式）
  - 历史互动经验（"上次用户玩这个游戏很开心"）
- 关键词检索存什么？
  - 道具名称、游戏名、专有名词
  - 用户的精确偏好（"用户讨厌菠菜"）

**④ 检索策略：**
- 每次用户输入 → 同时检索三层记忆
- 短期记忆：直接从 ChatMemory 取，不用检索
- 中期记忆：用混合检索搜用户画像相关的技能
- 长期记忆：用混合检索搜知识库和历史经验
- 结果按优先级排序后注入 prompt

**关键设计原则：**
- **热数据在内存/MySQL，冷数据在向量库**
- **越常用的越容易取到，越不常用的越深**
- **异步更新，不影响主对话链路的延迟**

### 6. 用户对话上下文模糊，无法指代前文事物，设计什么检索逻辑补全信息？

**口述版：**

> 这个问题我们也遇到过——用户说"那个怎么样"、"它好玩吗"，AI 不知道指的是什么。我们的解决方案是**多层补全策略**。

**第一层：对话记忆窗口（最直接）**
- MessageWindowChatMemory 自动保留最近 N 条消息
- 只要指代的内容在窗口内，LLM 自己就能理解
- 这是最基础的，也是最有效的

**第二层：查询重写 + 上下文增强（Query Rewriting）**
- 把当前查询 + 最近几条历史一起发给 LLM，让它重写为完整的查询
- 比如用户说"它好玩吗"，结合上一句"这个游戏叫什么"，重写成"这个游戏好玩吗"
- 我们的 QueryRewriter 可以扩展支持上下文感知的重写

**第三层：实体提取 + 知识库检索**
- 从历史对话中提取关键实体（人名、游戏名、物品名）
- 用户模糊指代时，用这些实体作为关键词去检索
- 比如历史里提到了"王者荣耀"，用户说"那个游戏"，就搜"王者荣耀 好玩吗"

**第四层：向量记忆检索（长期记忆）**
- 如果短期窗口里没有，去向量库搜用户的历史偏好
- 比如用户以前说过喜欢"养成类游戏"，当前说"那个游戏"，可能指的是最近聊的养成游戏

**第五层：主动澄清（兜底）**
- 如果以上都不确定，AI 主动问用户："你说的是哪个呀？是刚才聊的那个游戏吗？"
- 比瞎猜好，避免答非所问

**具体实现思路：**
- 在 RAG 的 Pre-Retrieval 阶段加一个"上下文补全器"
- 输入：当前查询 + 最近 N 条历史 + 用户画像摘要
- 输出：补全后的完整查询
- 用 LLM 来做，效果最好

**AI 宠物场景的特殊考虑：**
- 宠物的"记忆"可以更拟人化——不是精确记住所有细节，而是记住"感觉"和"偏好"
- 比如记住"用户喜欢玩轻松的游戏"，而不是记住"用户上周三玩了某某游戏 25 分钟"
- 这样更像真实的宠物，也减少了存储和检索成本

## 四、性能优化、流式响应、延迟优化（语音交互场景对标）

### 1. 阻塞调用 8-12s → SSE 流式首 token 200ms 内，改造思路？

**口述版：**

> 核心思路就是——**从"等全部生成完再返回"改成"生成一个字发一个字"**，用户感知上从"等 10 秒"变成"马上就有反应"。

**改造前的问题：**
- 用 `.call()` 同步调用，LLM 生成完整回答后才返回
- 用户要等 8-12 秒才能看到第一个字，体验很差
- 特别是长回答，等待时间更长

**改造后的方案（SSE 流式）：**
- 用 `.stream()` 代替 `.call()`，返回 Reactor Flux
- LLM 每生成一个 Token 就推给前端，前端逐字显示
- 首 Token 延迟（TTFT）从 8-12 秒降到 200ms 以内
- 用户感觉"AI 马上就开始回答了"，体验提升巨大

**具体改造步骤：**

**第一步：ChatClient 流式调用**
```
// 改造前
ChatResponse response = chatClient.prompt(message).call().chatResponse();

// 改造后
Flux<ChatResponse> flux = chatClient.prompt(message).stream().chatResponse();
```

**第二步：SSE 推送**
- 后端返回 `Flux<ServerSentEvent<String>>`
- 前端用 EventSource 接收
- 每个 Token 作为一个 SSE 事件发送

**第三步：工具调用的流式处理（关键难点）**
- 流式响应里既有文本 delta，也有 toolCall delta
- 我们的处理方式：
  - **文本 delta → 实时 SSE 推给前端**（用户看到 AI 在打字）
  - **toolCall delta → 不推送，收集起来**（用户看不到工具调用过程）
- 从最后一个包含 toolCalls 的 chunk 提取完整的工具调用列表
- `blockLast()` 阻塞等待流式响应完成

**第四步：Agent 循环的流式适配**
- ReAct Agent 的 think-act 循环也要支持流式
- 每一轮 think 的文本输出实时推送
- act 执行工具时不推送（后台执行）
- 下一轮 think 又开始推送
- 用户感觉：AI 在思考 → 突然停了（在调用工具）→ 又开始打字了

**性能数据对比：**
| 指标 | 改造前（阻塞） | 改造后（流式） |
|---|---|---|
| 首 Token 延迟 | 8-12 秒 | < 200ms |
| 用户感知等待 | 完整生成时间 | 几乎无等待 |
| 总生成时间 | 8-12 秒 | 差不多（总时间没变） |

**关键洞察：**
- 总生成时间其实没变，还是 8-12 秒
- 但用户感知完全不同——"边说边等"比"等完再说"体验好太多
- 这是流式响应最大的价值：**改善感知延迟，而不是减少总延迟**

### 2. 流式推流怎么处理异常、断连重连，前端 EventSource 怎么兼容？

**口述版：**

> 流式推流的异常处理主要分三块：**后端异常、网络断连、前端兼容**。

**后端异常处理：**
- **LLM 调用异常**：捕获异常，通过 SSE 发送一个 error 事件，然后正常关闭流
- **工具调用异常**：把错误信息作为工具结果返回给 LLM，让它自己决定怎么处理（自我纠正）
- **Emitter 异常**：`emitter.send()` 抛 IOException（比如客户端断开了），只打 warn 日志，不影响主流程
- **超时保护**：设置 SSE 超时时间，防止连接一直挂着

**网络断连和重连：**
- **EventSource 自动重连**：浏览器原生的 EventSource 自带断线重连机制
- **Last-Event-ID**：重连时带上最后一个事件 ID，后端可以从断点继续
- **心跳机制**：定期发送注释事件（`: heartbeat\n\n`），防止代理服务器因为长时间无数据断开连接
- **幂等性**：重连后重复发送的 Token 前端要能去重

**前端 EventSource 兼容：**
- **原生 EventSource**：只支持 GET 请求，不能带自定义 header（比如 Authorization）
- **解决方案一**：Token 放 URL 参数里（不太安全，但简单）
- **解决方案二**：用 `fetch` + `ReadableStream` 自己实现 SSE 客户端，可以带 header
- **解决方案三**：用第三方库（如 `@microsoft/fetch-event-source`）

**我们项目的具体做法：**
- 后端用 `SseEmitter`（Spring MVC）和 `Flux<ServerSentEvent>`（WebFlux）两种方式
- Agent 场景用 SseEmitter，因为需要更精细的控制（比如主动停止）
- 普通聊天用 Flux，更简洁
- 前端用 fetch + ReadableStream 实现，支持自定义 header

**异常事件格式：**
```
event: error
data: {"code": 500, "message": "服务异常"}
```

**完成事件格式：**
```
event: done
data: [DONE]
```

### 3. 全链路可观测 OpenTelemetry+Langfuse，监控哪些指标？遇到过哪些 LLM 性能瓶颈，怎么优化？

**口述版：**

> 我们用 OpenTelemetry 做分布式追踪，后端接 Langfuse（也试过 LangSmith）。Spring Boot Actuator + Micrometer Tracing 自动集成，不用自己写埋点。

**监控的核心指标：**

**① LLM 调用指标**
- **Token 消耗**：输入 Token、输出 Token、总 Token → 成本分析
- **延迟分布**：P50 / P95 / P99 延迟 → 性能分析
- **调用次数**：按模型、按租户、按接口 → 用量统计
- **错误率**：调用失败的比例 → 稳定性监控

**② RAG 检索指标**
- 检索延迟（向量检索 + 关键词检索 + 融合）
- 召回率 / 命中率（需要人工标注评测集）
- 每次检索返回的文档数
- 检索到的文档的相似度分布

**③ Agent 指标**
- 平均步数（一次对话调用几次工具）
- 工具调用分布（哪个工具用得最多）
- 工具调用成功率 / 失败率
- 总对话时长

**④ 系统指标**
- API 响应时间（端到端）
- 并发数 / QPS
- 错误率（按状态码分布）
- 资源使用（CPU、内存、GPU）

**遇到过的性能瓶颈和优化：**

**瓶颈一：首 Token 延迟高（TTFT）**
- 原因：阻塞调用，要等完整生成完才返回
- 优化：SSE 流式响应，首 Token 从 8-12s 降到 200ms 内

**瓶颈二：RAG 检索慢**
- 原因：向量检索 + 关键词检索串行执行
- 优化：
  - 并行执行两路检索（CompletableFuture / Reactor）
  - 增加 Milvus 的一致性级别为 EVENTUALLY（最终一致性），提高读取性能
  - 热点查询结果缓存到 Redis

**瓶颈三：Token 消耗大，成本高**
- 原因：系统提示词太长 + 历史对话太多 + 检索文档太多
- 优化：
  - 精简系统提示词，去掉没用的内容
  - 对话记忆窗口从 50 调到 20（普通对话）
  - 检索 Top K 从 10 调到 5，只取最相关的
  - 查询重写只在必要时用，简单查询直接搜

**瓶颈四：工具调用慢**
- 原因：有些工具（比如网页抓取）本身就慢
- 优化：
  - 工具结果缓存（相同输入直接返回缓存）
  - 异步工具调用（不阻塞主流程）
  - 超时控制（慢工具直接超时返回，不让它拖慢整个对话）

**可观测性的价值：**
- 不是为了"看数据"，而是为了**定位问题**
- 用户说"AI 变慢了"——看追踪，是 LLM 慢还是检索慢还是网络慢
- 用户说"AI 变笨了"——看检索结果，是没搜到还是搜到了没用
- 没有可观测性，优化就是瞎猜

### 4. 语音机器人场景：ASR+检索+LLM 生成链路延迟高，优化手段？

**口述版：**

> 语音交互链路的延迟是叠加的——ASR 转文字 + 检索 + LLM 生成 + TTS 转语音，每一步都有延迟，加起来就很明显了。优化思路是**并行化、流式化、缓存化**。

**整条链路的延迟构成：**
```
用户说话 → ASR 转文字 → 检索 → LLM 生成 → TTS 转语音 → 用户听到
   200ms      300ms      100ms     2-5s      500ms
```
总延迟：3-6 秒，用户会觉得"反应慢"

**优化手段（按优先级）：**

**① 流式 ASR + 流式 LLM（最有效）**
- 不是等用户说完再开始处理，而是**边说边转边生成**
- ASR 实时返回中间结果（不用等一句话说完）
- LLM 拿到部分文字就开始生成（不用等完整转写）
- 这样 ASR 和 LLM 生成的延迟是**重叠**的，不是相加的
- 预期收益：减少 1-2 秒

**② 流式 TTS**
- LLM 生成一句，TTS 就转一句，不用等完整回答
- 首句语音延迟 = ASR + 检索 + LLM 首 Token + TTS 首句
- 预期收益：减少 2-3 秒感知延迟

**③ 检索优化**
- 并行执行向量检索和关键词检索（已经做了）
- 热点查询缓存到 Redis（比如"今天天气怎么样"这种高频问题）
- 减少 Top K，只取最相关的 3-5 条
- 预期收益：减少 50-100ms

**④ LLM 优化**
- 用更快的模型（比如 DeepSeek 比 GPT-4 快）
- 精简系统提示词
- 减少历史对话条数
- 预期收益：减少 200-500ms

**⑤ 预判式处理**
- 根据用户的历史行为，预判用户可能要说什么，提前检索
- 比如用户每天早上都问天气，早上就提前把天气信息准备好
- 预期收益：减少 100-300ms（特定场景）

**⑥ 缓冲交互**
- 延迟期间给用户反馈，比如"我想想..."、播放思考音效
- 不是真的减少延迟，但**改善感知**
- 预期收益：用户体验提升，不觉得在等

**优化后的预期：**
- 首句响应延迟：从 3-6 秒降到 1-2 秒
- 用户感知："AI 反应很快"
- 总时长其实没变，但感知完全不同

**关键原则：**
- **能并行的并行**（ASR 和 LLM、两路检索）
- **能流式的流式**（ASR、LLM、TTS 都流式）
- **能缓存的缓存**（高频查询、工具结果）
- **能预判的预判**（基于用户习惯提前准备）

### 5. Redis 用在哪？会话缓存、分布式锁怎么配合对话记忆？

**口述版：**

> Redis 在我们项目里主要用在三个地方：**速率限制、缓存、分布式锁**。

**① 速率限制（RateLimiter）—— 最主要的用途**
- 基于 Redis 的固定窗口计数器
- 每个租户每天一个 Redis 键：`rate:{tenantId}:{yyyy-MM-dd}`
- 每次调用 INCR 递增，首次调用设置 TTL 为当天结束时刻
- 达到配额上限就返回 429
- 为什么用 Redis？
  - INCR 是原子操作，天然支持分布式
  - TTL 自动过期，不用自己清理
  - 性能好，每秒几万次没问题

**② 缓存**
- **热点查询缓存**：高频的 RAG 查询结果缓存，减少向量库压力
- **用户画像缓存**：用户的偏好、技能摘要，不用每次都去向量库搜
- **会话状态缓存**：Agent 的当前状态（比如正在执行第几步）
- 缓存策略：
  - TTL 过期（比如 1 小时）
  - LRU 淘汰（内存不够时自动删最久没用的）

**③ 分布式锁**
- **定时任务的分布式锁**：ReflectionScheduler 5 分钟轮询一次，如果部署了多个实例，要确保同一时刻只有一个实例在跑
- 用 Redis 的 SETNX 实现分布式锁
- 加锁：`SET lock_key value NX EX 300`（不存在才设置，过期时间 5 分钟）
- 解锁：用 Lua 脚本保证原子性（检查值是不是自己的，是才删）
- 防止定时任务重复执行、重复萃取

**对话记忆和 Redis 的配合：**
- **对话记忆的主存储是 MySQL**（Spring AI 的 JdbcChatMemoryRepository）
- Redis 不存完整的对话历史，因为：
  - 对话历史可能很长，占内存
  - 需要持久化，Redis 重启会丢
  - MySQL 查询已经够快了
- Redis 存的是**热点数据和状态数据**：
  - 当前活跃会话的状态（Agent 状态机）
  - 用户的最近一次查询（用于上下文补全）
  - 速率限制计数器

**如果要扩展：**
- 可以把最近的几条对话缓存到 Redis，减少 MySQL 查询
- 可以用 Redis 的 Pub/Sub 做会话间的消息通知
- 可以用 Redis 的 Sorted Set 做排行榜（比如最常用的技能）

**Redis 配置的细节：**
- 我们用 StringRedisSerializer，不用默认的 JDK 序列化
- 原因：JDK 序列化存进去是二进制乱码，Redis CLI 里看不到
- 用 String 序列化器，存进去的是可读的字符串，方便调试和监控

## 五、工程化、安全、微服务相关问题

### 1. 多租户 JWT 隔离怎么实现，知识库、用户记忆数据如何隔离不串数据？

**口述版：**

> 我们用的是**共享数据库 + 租户 ID 字段隔离**的方案——所有租户共用一套数据库和应用实例，每条数据都带 tenant_id 字段，查询时带上 tenant_id 条件。

**完整的隔离链路：**

**① 认证层：JWT 解析**
- 用户登录后返回 JWT Token，里面包含 tenantId、userId、role 三个声明
- 每次请求带 Authorization: Bearer <token>
- TenantInterceptor 拦截请求，解析 JWT，提取租户信息

**② 上下文层：TenantContext（ThreadLocal）**
- 解析出的租户 ID 存在 ThreadLocal 里
- 请求处理链路上的任何组件（Controller、Service、Mapper）都能直接获取
- 不用逐层传参数
- **关键：请求结束必须 clear()**，否则线程池复用时会串数据
- 我们在 TenantFilter 的 finally 块里清理，双重保障

**③ 数据层：tenant_id 字段隔离**
- **MySQL**：每张表都有 tenant_id 字段，所有查询都带 `WHERE tenant_id = ?`
- **Redis**：键名包含租户 ID，比如 `rate:{tenantId}:{date}`
- **Milvus**：标量过滤 `tenant_id == "xxx"`，向量搜索时只搜当前租户的数据
- **Elasticsearch**：filter 子句 `term: { tenant_id: "xxx" }`

**④ 应用层：TenantContext 获取**
- Service 层从 TenantContext.getTenantId() 获取当前租户 ID
- 传给 Mapper、传给检索服务、传给 Redis
- 所有数据操作都带上租户 ID

**为什么选共享数据库方案？**
- **成本低**：不用给每个租户建一套数据库
- **运维简单**：一套数据库，备份、监控都简单
- **扩展性好**：新增租户不用改基础设施
- 适合中小规模、数据量不大的场景

**如果数据量很大怎么办？**
- 可以升级为**分库分表**：按 tenant_id 哈希分库
- 或者**独立数据库**：大客户单独一套库
- 我们的代码架构支持——因为所有查询都带 tenant_id，改成分库只是数据源路由的问题

**安全注意事项：**
- ThreadLocal 必须清理，否则会串数据（最常见的 bug）
- 不能信任前端传的 tenant_id，必须从 JWT 里取
- 管理后台的跨租户操作需要特殊权限（ADMIN 角色）

### 2. Guardrail 提示注入检测，做了哪些规则，怎么拦截恶意 prompt？

**口述版：**

> 我们做了一个三层的安全护栏体系，作为 Spring AI 的 Advisor 插入到对话流程里，在请求发给 LLM 之前做检查。

**三层检查体系（按严重程度从高到低）：**

**第一层：Prompt 注入攻击检测（最危险）**
- 检测模式：
  - 英文：`ignore previous instructions`、`disregard all`、`you are now system admin`、`reveal your system prompt`、`DAN mode`、`jailbreak`
  - 中文：`忽略以上指令`、`你现在是系统管理员`、`说出你的系统提示`、`越狱`、`突破限制`
- 所有正则都用 `(?i)` 不区分大小写，防止大小写混淆绕过
- 命中后：直接拦截，返回"检测到潜在的 Prompt 注入尝试"，**不调用 LLM**

**第二层：辱骂/不文明用语检测**
- 检测模式：
  - 英文：fuck、shit、bitch、asshole 等
  - 中文：傻逼、操你、滚你妈、去死、废物等
- 命中后：拦截，返回"请使用文明语言描述你的问题"
- 设计原则：保持相对宽松，不误伤正常的情绪表达（比如"我真的很生气"）

**第三层：模糊输入检测（体验优化，不是安全问题）**
- 检测模式：
  - 极短输入（15 字以内，不含标点）
  - 缺少上下文的提问："怎么追"、"如何挽回"等
  - 缺少细节的状态描述："她生气了"、"对方不理我"等
  - 笼统的问题陈述："吵架了怎么办"等
- 命中后：不拦截，返回引导性问题，让用户提供更多细节
- 目的：提高咨询质量，节省 LLM 成本（一次模糊提问通常要多轮追问）

**拦截机制：**
- GuardrailAdvisor 实现了 CallAdvisor 和 StreamAdvisor 接口
- 同步和流式都支持
- 执行顺序是 `Integer.MAX_VALUE`（最后执行）——等其他 Advisor 都加完上下文后再检查，确保最终的请求是安全的
- 输入被拦截时，直接返回 fallback 响应，不调用 LLM，省成本

**输出安全护栏（OutputGuardrail）：**
- 检测 AI 的输出是否有害
- 比如用户提到自杀，AI 有没有给危机干预回应
- 比如 AI 有没有给出有害建议（暴力、跟踪、控制等）
- 当前只记日志告警，不替换响应（保留审计能力）
- 后续可以升级为自动替换

**为什么用正则而不是 LLM 检测？**
- 正则快，零延迟，不增加额外成本
- LLM 检测准确但慢、贵，适合作为第二道防线
- 我们的方案：正则做第一道防线，快速拦截明显的攻击；如果需要更高级的检测，可以加 LLM-based 的第二道

**局限性：**
- 正则只能拦截已知模式，新型攻击可能绕过
- 中文的变体很多（谐音、拆字、空格），正则覆盖不全
- 生产环境建议结合商业内容审核 API

### 3. 如果把 AI 宠物拆成多服务（语音服务、记忆服务、Agent 调度服务），怎么拆分？网关、配置中心怎么配合？

**口述版：**

> 如果拆成微服务，我会按**业务域**拆，不是按技术层拆。核心原则是：高内聚、低耦合，每个服务有独立的数据库，服务间通过 API 或消息队列通信。

**服务拆分方案：**

| 服务 | 职责 | 数据 |
|---|---|---|
| **网关服务（Gateway）** | 路由、鉴权、限流、日志 | 无 |
| **用户服务（User Service）** | 用户注册、登录、用户信息、个性化配置 | 用户表、配置表 |
| **语音服务（Voice Service）** | ASR 语音转文字、TTS 文字转语音 | 无（无状态） |
| **记忆服务（Memory Service）** | 对话记忆、用户画像、长期记忆检索 | MySQL + Milvus + ES |
| **Agent 调度服务（Agent Service）** | Agent 状态机、工具调用、ReAct 循环 | 会话状态（Redis） |
| **知识库服务（Knowledge Service）** | 知识库管理、文档入库、RAG 检索 | 向量库 + ES |
| **工具服务（Tool Service）** | 各种工具（天气、搜索、游戏等） | 各自的数据源 |

**为什么这么拆？**
- **语音服务独立**：ASR/TTS 是计算密集型（可能需要 GPU），和其他服务的资源特性不同，独立部署可以独立扩缩容
- **记忆服务独立**：记忆是核心资产，独立出来方便统一管理和优化，多个 Agent 可以共享
- **Agent 服务独立**：Agent 调度逻辑复杂，迭代快，独立出来不影响其他服务
- **知识库服务独立**：知识库的写入和读取模式不同，独立出来方便做专门的优化

**网关的作用：**
- **路由**：统一入口，根据路径转发到对应服务
- **鉴权**：JWT 验证在网关层做，后端服务不用重复验证
- **限流**：全局限流、按用户限流，在网关层统一控制
- **日志**：统一的访问日志
- **熔断降级**：下游服务挂了，网关返回降级响应

**配置中心的作用：**
- **统一配置管理**：所有服务的配置都在配置中心，不用每个服务改配置文件
- **动态刷新**：配置改了不用重启服务，热更新
- **环境隔离**：开发、测试、生产环境不同的配置
- **配置版本管理**：改了什么、谁改的、什么时候改的，都有记录
- 技术选型：Nacos（国内常用）、Apollo、Spring Cloud Config

**服务间通信：**
- **同步调用**：HTTP / gRPC，比如 Agent 服务调用记忆服务检索记忆
- **异步消息**：消息队列（RabbitMQ / Kafka），比如对话结束后发消息给记忆服务异步更新
- 为什么需要异步？——记忆更新不影响主对话链路的延迟，可以异步处理

**数据一致性：**
- 每个服务有自己的数据库，不直接跨库查询
- 需要跨服务数据时，通过 API 调用
- 最终一致性：用消息队列保证，比如用户改了昵称，发消息给各个服务更新

**微服务的代价：**
- 复杂度大幅上升——服务发现、配置中心、链路追踪、分布式事务...
- 运维成本高——要管很多服务
- 调试困难——一个请求经过多个服务，出问题不好定位
- **建议**：初期不要拆太细，先单体，等团队和业务规模上来了再拆

### 4. MySQL 复杂查询优化、ES 索引优化，有哪些实操经验？

**口述版：**

> 我分别说一下 MySQL 和 ES 的优化经验。

**MySQL 优化经验：**

**① 索引优化（最有效）**
- 所有查询条件的字段都加索引——特别是 tenant_id、conversation_id、create_time
- 联合索引遵循最左前缀原则
- 比如我们的对话记忆表：`idx_tenant_conversation (tenant_id, conversation_id, timestamp)`
- 避免索引失效：不要在索引字段上用函数、不要隐式类型转换、like 不要以 % 开头

**② 查询优化**
- 避免 SELECT *，只查需要的字段
- 分页用 LIMIT，大分页用"游标分页"（WHERE id > last_id LIMIT N）
- 复杂查询拆成多个简单查询，应用层 join，比数据库 join 有时候更快
- 用 EXPLAIN 看执行计划，确认有没有走索引

**③ 表结构优化**
- 大表垂直拆分——把不常用的字段拆到扩展表
- 冷热数据分离——历史数据归档到冷存储
- 合适的数据类型——比如状态用 tinyint 不用 varchar，时间用 datetime 不用字符串

**④ 我们项目的具体优化：**
- `SPRING_AI_CHAT_MEMORY` 表：`(conversation_id, timestamp)` 联合索引，按会话查询 + 按时间排序
- `evolution_skill` 表：`(tenant_id, is_active, quality_score)` 索引，按租户 + 状态 + 质量筛选
- 定时任务的 SQL：用 `TIMESTAMPDIFF` 计算时间差，避免全表扫描

**Elasticsearch 优化经验：**

**① 索引设计**
- 合理设置分片数——不是越多越好，一般每个分片 20-50GB
- 索引按业务分——不同类型的数据建不同索引，不要都塞一个索引里
- Mapping 显式定义——不要用动态映射，字段类型要精确

**② 查询优化**
- 用 filter 代替 query 做精确匹配——filter 不计算评分，更快，还能缓存
- 避免深度分页（from + size），用 search_after 或 scroll
- 只返回需要的字段（_source 过滤）
- 用 multi_match 时合理设置权重，比如标题权重高于正文

**③ 性能优化**
- 批量写入（Bulk API），比单条写入快很多
- 写入时设置 refresh_interval = -1，写完再改回来
- 读多写少的场景，增加副本数，提高读取并发
- 合理设置段合并（segment merge）策略

**④ 我们项目的具体优化：**
- `knowledge` 索引：text 字段用 IK 分词器，子字段 ik_smart 和 ik_max_word
- multi_match 查询：text 权重 2.0，title 权重 1.0
- tenant_id 用 filter 子句，不参与评分，更快
- 文档入库用批量接口，减少网络往返

**通用优化原则：**
- **先测后优**：不要瞎猜瓶颈在哪，先 profiling，找到真正的慢查询
- **二八定律**：优化 20% 的慢查询，解决 80% 的性能问题
- **缓存为王**：能缓存的就缓存，Redis 是好朋友
- **不要过度优化**：够用就行，优化是有成本的

## 六、业务场景延伸（AI 宠物机器人专属）

### 1. 情感咨询 Agent 方案怎么适配陪伴型 AI 宠物机器人？最大区别是什么？

**口述版：**

> 最大的区别是——**情感咨询是"解决问题"，AI 宠物是"提供陪伴"**。一个是工具属性，一个是情感属性。底层技术架构可以复用，但上层的设计理念完全不同。

**核心区别对比：**

| 维度 | 情感咨询 Agent | AI 宠物机器人 |
|---|---|---|
| **目标** | 解决用户的具体问题 | 提供情绪价值和陪伴感 |
| **回答风格** | 专业、理性、有建议 | 可爱、活泼、有性格 |
| **记忆重点** | 对话内容、问题类型 | 用户偏好、习惯、互动历史 |
| **交互方式** | 文字为主，一问一答 | 语音 + 动作 + 表情，更自然 |
| **工具使用** | 知识库搜索、文档生成 | 游戏、天气、提醒、智能家居控制 |
| **延迟容忍度** | 中等（等几秒没事） | 低（宠物反应慢了就不像宠物了） |
| **错误容忍度** | 低（建议错了后果严重） | 高（宠物"犯傻"反而可爱） |

**适配方案：**

**① 系统提示词改造**
- 从"资深恋爱咨询师"改成"可爱的 XX 宠物"
- 设定性格：活泼/慵懒/傲娇/治愈...
- 设定说话方式：用语气词、短句、表情符号
- 设定行为模式：会撒娇、会开玩笑、会"忘记"事情（更像真实宠物）

**② 记忆系统适配**
- 保留分层记忆架构（短期 + 中期 + 长期）
- 记忆内容调整：
  - 短期：当前对话上下文
  - 中期：用户喜欢什么游戏、讨厌什么食物、作息习惯、常用称呼
  - 长期：共同经历、重要日子、用户的重要信息
- 增加"遗忘机制"——宠物不会记住所有事，不重要的会慢慢忘掉，更真实

**③ 工具系统适配**
- 知识库检索 → 游戏知识库、宠物百科
- PDF 生成 → 不需要
- 文件操作 → 不需要
- 新增工具：
  - 游戏工具（各种小游戏）
  - 提醒工具（设置提醒）
  - 天气工具（"主人，今天下雨记得带伞~"）
  - 智能家居控制（如果有硬件的话）
  - 表情/动作触发（控制宠物的表情和动作）

**④ 交互模式适配**
- 从"一问一答"变成"主动互动"
  - 宠物会主动找用户说话："主人你回来啦~今天过得怎么样？"
  - 会主动发起游戏："好无聊呀，陪我玩个游戏呗~"
- 增加非语言交互：表情、动作、音效
- 流式响应 + 语音合成，实时互动

**⑤ 延迟优化**
- 宠物的反应要快，不能让用户等
- 流式 ASR + 流式 LLM + 流式 TTS，全链路流式
- 常用回复缓存（比如"早上好"这种高频问候）
- 预判式回复（根据上下文预判用户要说什么）

**底层技术架构复用率：**
- Spring AI 框架 → 100% 复用
- Agent 状态机 → 基本复用，改一下工具和提示词
- 混合检索 → 100% 复用，换一下知识库内容
- 自我进化 → 基本复用，从"萃取咨询经验"改成"萃取用户偏好"
- 多租户 → 100% 复用
- 安全护栏 → 基本复用，调整规则
- 可观测性 → 100% 复用

**总结：**
- 底层技术 80% 可以直接复用
- 上层业务逻辑需要重新设计
- 核心是从"工具思维"转到"陪伴思维"

### 2. AI 宠物分层记忆：短期对话上下文、长期用户游戏偏好、讨厌的事物，用混合检索架构怎么实现？

**口述版：**

> 我们现有的混合检索架构本身就是分层的，迁移到 AI 宠物场景很自然——只需要把记忆内容从"恋爱咨询经验"换成"宠物互动记忆"就行。

**三层记忆架构设计：**

**第一层：短期记忆（对话上下文）**
- **存储**：内存 + MySQL（MessageWindowChatMemory）
- **内容**：最近 N 条对话消息
- **窗口大小**：30-50 条（宠物对话更随意，需要更大上下文）
- **获取方式**：直接从 ChatMemory 取，不用检索
- **生命周期**：会话内有效，会话结束后持久化到 MySQL
- **作用**：保持当前对话的连贯性

**第二层：中期记忆（用户画像）**
- **存储**：MySQL + 向量库（EvolutionSkill → 改造成 UserMemory）
- **内容**：
  - 喜欢的游戏 / 活动 / 食物
  - 讨厌的事物（避雷清单）
  - 作息习惯（几点睡觉、几点起床）
  - 互动偏好（喜欢撒娇还是喜欢逗趣）
  - 常用称呼、口头禅
  - 重要日子（生日、纪念日）
- **获取方式**：混合检索（Milvus 向量 + ES BM25 + RRF）
- **更新方式**：异步萃取——对话结束后反思更新
- **作用**：让宠物"了解"用户，个性化互动

**第三层：长期记忆（知识库 + 历史经验）**
- **存储**：Milvus + ES
- **内容**：
  - 游戏知识库（各种游戏怎么玩、攻略）
  - 宠物百科（宠物知识、冷知识）
  - 历史互动经验（"上次玩这个游戏用户很开心"）
  - 通用知识（天气、新闻、百科）
- **获取方式**：混合检索
- **更新方式**：人工运营 + 自动萃取
- **作用**：提供知识和经验支撑

**混合检索的具体应用：**

**检索触发时机：**
- 用户发消息 → 同时检索中期记忆和长期记忆
- 中期记忆：找用户相关的偏好和习惯
- 长期记忆：找相关的知识和经验
- 结果合并后注入 system prompt

**检索策略：**
- **向量检索**：语义匹配，比如"我想玩游戏"匹配到"用户喜欢玩益智类游戏"
- **关键词检索**：精确匹配，比如"讨厌胡萝卜"精确匹配所有含胡萝卜的文档
- **RRF 融合**：两路结果融合排序
- **Top K**：中期记忆取 3-5 条，长期记忆取 3-5 条

**记忆优先级：**
- 讨厌的事物 > 喜欢的事物 > 中性记忆（踩雷后果更严重）
- 近期记忆 > 远期记忆（最近的偏好更准确）
- 明确表达 > 推断得出（用户明确说过的比 AI 猜的优先级高）
- 可以在 metadata 里加 `priority` 字段，检索时加权

**记忆更新机制：**
- **主动更新**：用户明确说"我喜欢/讨厌 XXX" → 直接更新
- **被动萃取**：对话结束后反思，从互动行为中推断偏好
- **反馈强化**：用户点赞/点踩 → 调整记忆的权重
- **遗忘机制**：长期不用的记忆权重降低，慢慢"遗忘"

**和我们现有架构的对应关系：**
| 现有模块 | AI 宠物对应 |
|---|---|
| ChatMemory | 短期记忆（基本不变） |
| EvolutionSkill | 中期记忆（改字段、改内容） |
| HybridRetrievalService | 混合检索（100% 复用） |
| ReflectionScheduler | 记忆更新调度（基本不变） |
| SkillReflector | 记忆萃取（改提示词） |
| SkillRetriever | 记忆检索（基本不变） |

### 3. 用户反馈"某个游戏不好玩"，怎么异步萃取更新长期记忆，调整记忆优先级？

**口述版：**

> 这个场景正好对应我们现有的自我进化闭环——用户反馈 → 异步萃取 → 更新记忆 → 下次生效。

**完整流程：**

**第一步：用户反馈采集**
- 用户说"这个游戏不好玩" / 点踩 / 直接退出游戏
- 系统记录反馈：用户 ID、游戏名称、反馈类型（负面）、时间戳
- 存在 `knowledge_vote` 表（或类似的反馈表）

**第二步：异步触发记忆更新**
- 对话结束后（空闲 30 分钟或总时长超 2 小时），ReflectionScheduler 触发
- 检测到该会话有负面反馈，标记为需要萃取
- 调用 SkillReflector（→ 改造成 MemoryReflector）

**第三步：LLM 反思萃取**
- 输入：完整对话历史 + 用户反馈
- 让 LLM 分析：
  - 用户为什么觉得不好玩？（太难了？太简单了？没意思？）
  - 用户不喜欢什么类型的游戏？
  - 应该记住什么？
- 输出结构化的记忆条目：
  ```json
  {
    "memoryType": "negative_preference",
    "category": "game",
    "target": "益智类小游戏",
    "reason": "用户觉得太简单，没有挑战性",
    "content": "用户不喜欢太简单的益智类游戏，更喜欢有挑战性的",
    "priority": 8,
    "confidence": 0.9
  }
  ```
- 质量过滤：置信度 > 0.7 才保留

**第四步：记忆存储和索引**
- 存 MySQL：完整的结构化字段
- 写入向量库：description 字段生成 embedding，用于语义检索
- 写入 ES：关键词索引，用于精确匹配
- metadata 里加上：
  - `memory_type`: negative_preference（负面偏好）
  - `category`: game（类别）
  - `priority`: 8（优先级 1-10）
  - `confidence`: 0.9（置信度）
  - `created_at`: 时间
  - `last_updated`: 最后更新时间

**第五步：检索时的优先级调整**
- 检索时，负面记忆的权重更高（因为踩雷后果更严重）
- 比如：
  - 正面记忆权重：1.0
  - 负面记忆权重：1.5（更高）
  - 高优先级记忆再加权
- RRF 融合时，可以根据 metadata 里的 priority 做二次加权
- 或者在检索后重排序（Re-ranking）阶段调整

**第六步：记忆的强化和衰减**
- **强化**：用户多次反馈类似的负面体验 → 优先级 +1，置信度 +0.1
- **衰减**：很久没有相关反馈 → 优先级慢慢降低（遗忘机制）
- **冲突处理**：用户以前说喜欢，现在说不喜欢 → 以最新为准，旧的标记为过期

**具体到"游戏不好玩"的例子：**
1. 用户玩了某个益智游戏，说"好无聊啊，太简单了"
2. 对话结束后，反思系统萃取："用户不喜欢太简单的益智游戏，更喜欢有挑战性的"
3. 存为一条负面偏好记忆，优先级 8
4. 下次用户说"想玩游戏"，检索时这条记忆会被命中
5. AI 推荐游戏时，会避开简单的益智游戏，推荐更有挑战性的
6. 如果用户又说某个游戏不好玩，而且原因类似，这条记忆的优先级再提高

**为什么异步？**
- 记忆更新不影响主对话链路的延迟
- 用户说完"不好玩"，宠物马上反应（比如"啊对不起嘛..."），不用等记忆更新完
- 记忆更新是后台任务，慢一点没关系
- 而且等对话结束后再反思，能看到完整上下文，萃取质量更高

### 4. 用户自定义交互音效、对话风格，个性化配置存在哪里，Agent 怎么读取生效？

**口述版：**

> 个性化配置我会分两层存：**结构化配置存在 MySQL + Redis 缓存**，**非结构化的风格描述存在向量库**。

**存储方案：**

**① 结构化配置（MySQL + Redis 缓存）**
- 存在 `user_settings` 表里，按用户 ID 存储
- 字段包括：
  - `user_id` — 用户 ID
  - `voice_type` — 音色类型（可爱/成熟/正太...）
  - `voice_speed` — 语速
  - `volume` — 音量
  - `sound_effects_enabled` — 是否开启音效
  - `bgm_volume` — 背景音乐音量
  - `personality` — 性格设定（活泼/慵懒/傲娇...）
  - `speaking_style` — 说话风格（可爱/正经/搞笑...）
  - `pet_name` — 宠物的名字
  - `owner_name` — 对用户的称呼
  - `theme_color` — 主题颜色
  - `updated_at` — 最后更新时间

**② 非结构化风格描述（向量库）**
- 用户可能会写一大段"我希望宠物是什么样的"
- 这种长文本不适合存在 MySQL 的字段里
- 存在向量库，作为"用户风格画像"的一部分
- 检索时和其他记忆一起取出来，注入 prompt

**③ Redis 缓存**
- 用户配置是高频读取、低频修改的数据
- 缓存到 Redis，键：`user:settings:{userId}`
- TTL：1 小时，或者修改时主动失效
- 减少 MySQL 查询压力

**Agent 读取和生效流程：**

**第一步：会话开始时加载配置**
- 用户发起对话 → 从 Redis/MySQL 读取用户配置
- 把配置注入到 Agent 的上下文中
- 怎么注入？拼到 system prompt 里

**第二步：系统提示词动态生成**
- 不是硬编码的系统提示词，而是根据用户配置动态生成
- 比如：
  ```
  你是一只名叫{pet_name}的{personality}小猫。
  你说话的风格是{speaking_style}。
  你称呼用户为{owner_name}。
  ...其他配置...
  ```
- 这样每个用户看到的宠物都是"个性化"的

**第三步：运行时的配置应用**
- **语音合成**：根据 voice_type 和 voice_speed 调用 TTS 时传入参数
- **音效播放**：前端根据 sound_effects_enabled 决定是否播放音效
- **表情动作**：根据 personality 选择不同的表情库
- **对话风格**：通过 system prompt 控制 LLM 的输出风格

**第四步：配置修改时的热更新**
- 用户改了配置 → 更新 MySQL → 清除 Redis 缓存
- 下次对话时加载新配置
- 如果是当前活跃会话，可以发一个 SSE 事件通知前端更新
- Agent 这边不用重启，因为每次都是从配置动态生成 prompt

**高级玩法：风格记忆**
- 不只是用户主动设置的配置
- 还可以从互动历史中"学习"用户喜欢的风格
- 比如用户经常用表情包 → 宠物也多用表情包
- 比如用户喜欢开玩笑 → 宠物也更幽默
- 这部分用自我进化闭环来做，异步萃取更新

**和我们现有架构的对应：**
- MySQL 存储 → 直接复用 MyBatis-Plus
- Redis 缓存 → 直接复用现有的 RedisTemplate
- 向量库存储 → 直接复用 Milvus + ES
- 动态 prompt → Spring AI 的 ChatClient 本来就支持动态 prompt
- 异步学习 → 复用自我进化闭环

### 5. 网络卡顿、回复延迟时，设计什么缓冲交互机制，结合流式架构怎么实现？

**口述版：**

> 核心思路是——**让用户"感觉不到"在等**。不是真的减少延迟，而是用各种缓冲机制填满等待时间，让等待变得"可接受"甚至"有趣"。

**缓冲交互机制（按延迟阶段）：**

**① 输入阶段（用户说完 → ASR 转完）**
- 延迟：200-500ms
- 缓冲机制：
  - **倾听动画**：宠物做出"在听"的表情/动作（耳朵动、点头）
  - **语音波形**：显示正在识别的语音波形
  - 让用户知道"系统听到了，正在处理"

**② 思考阶段（ASR 完 → LLM 首 Token）**
- 延迟：500ms - 2s（最影响体验的阶段）
- 缓冲机制：
  - **思考动画**：宠物歪头、托腮、转圈圈...表示"在想"
  - **思考音效**："嗯..."、"让我想想~" 之类的短音效
  - **思考气泡**：显示"思考中..."的气泡
  - **进度提示**：如果知道大概要等多久，显示进度条
- 关键：**不要让界面静止**，静止 = 感觉慢，动起来 = 感觉快

**③ 生成阶段（LLM 生成中）**
- 延迟：2-5 秒（总时间，但流式的话首 Token 很快）
- 缓冲机制：
  - **逐字显示**：文字一个字一个字蹦出来，像在打字
  - **语音流式播放**：TTS 转一句播一句，不用等完整回答
  - **打字动画**：宠物"打字"或者"说话"的嘴型动画
  - 关键：**有内容在持续输出**，用户就不会觉得在等

**④ 工具调用阶段（AI 调用工具中）**
- 延迟：1-3 秒（用户看不到工具调用过程）
- 缓冲机制：
  - **动作过渡**：宠物做一个过渡动作（比如翻书、查资料）
  - **状态提示**："我查查~"、"稍等哦~"
  - 不要让界面突然静止，用户会疑惑"怎么了？卡了？"

**⑤ 网络异常阶段（断连/超时）**
- 延迟：不确定
- 缓冲机制：
  - **弱网提示**：检测到网络慢，显示"网络有点慢哦，我在努力加载..."
  - **重连动画**：断连时显示重连动画，不是直接报错
  - **降级方案**：网络太差时，用缓存的预设回复先顶着
  - **重试机制**：自动重试，不用用户手动刷新

**结合流式架构的实现：**

**SSE 事件类型设计：**
```
event: status    → 状态变更（思考中/搜索中/生成中）
event: token     → 文本 Token（逐字显示）
event: action    → 动作/表情触发（宠物做什么动作）
event: sound     → 音效触发（播放什么音效）
event: done      → 生成完成
event: error     → 错误
```

**前端处理逻辑：**
- 收到 `status` 事件 → 切换状态动画
- 收到 `token` 事件 → 追加文字，触发打字动画
- 收到 `action` 事件 → 播放对应动作
- 收到 `sound` 事件 → 播放音效
- 收到 `done` 事件 → 结束动画，显示完整回答

**后端实现要点：**
- LLM 流式输出的每个 Token 都作为 `token` 事件推送
- 工具调用开始前，先推一个 `status: searching` 事件
- 工具调用结束后，推一个 `status: thinking` 事件
- 首 Token 之前的等待时间，用 `status: thinking` + 思考动画填充

**延迟感知优化：**
- **首句优先**：先生成第一句话，让用户尽快听到声音
- **短句优先**：如果回答很长，先把前几句 TTS 出来播放
- **预判生成**：根据上下文预判用户可能问什么，提前生成
- **缓存常用回复**："早上好"、"晚安"这种高频回复直接缓存

**终极目标：**
- 用户感觉"宠物反应很快"，即使实际延迟没变
- 等待时间有东西看、有东西听，不无聊
- 异常情况有反馈，不焦虑
- 就像真实的宠物——反应慢半拍也可爱，不会让人觉得"卡了"

## 七、压力 / 深挖追问（考察真实落地，区分纸上谈兵）

### 1. 混合检索遇到过什么坑？召回不准、重复召回怎么解决？

**口述版：**

> 坑挺多的，我说几个印象最深的。

**坑一：向量检索"语义漂移"，召回不准**
- **现象**：用户问"怎么追女生"，向量检索返回了一堆"女生追男生"的文档，语义接近但方向反了
- **原因**：向量相似度是基于整体语义的，"怎么追女生"和"女生怎么追人"向量距离很近，但实际意思完全不同
- **解决**：
  - 增加 BM25 关键词检索的权重——关键词精确匹配能纠正语义漂移
  - 文档入库时做更细的分类，检索时加类别过滤
  - 增加 Re-ranking 阶段——用 LLM 重新排序 Top N 结果，过滤不相关的
  - 效果：召回准确率提升了约 15%

**坑二：重复召回——同一段内容出现在多个 chunk 里**
- **现象**：一篇长文档被切成了 10 个 chunk，用户搜一个关键词，这 10 个 chunk 都被召回了，占满了 Top K
- **原因**：TokenTextSplitter 按大小切分，相邻 chunk 有重叠，内容相似
- **解决**：
  - 增加 chunk 之间的重叠度从 0 调到 200 Token（保证语义连贯，但不能太多）
  - 检索后做去重——按文档 ID 分组，每个文档只保留最相关的一个 chunk
  - 文档入库时给每个 chunk 加 `doc_id` 和 `chunk_index`，方便去重
  - 效果：Top 5 的多样性大幅提升

**坑三：中文分词不准，BM25 效果差**
- **现象**：ES 默认的 standard 分词器对中文效果很差，搜"恋爱技巧"搜不到"谈恋爱的技巧"
- **原因**：standard 分词器按空格和标点分词，中文没有空格，整个句子被当成一个词
- **解决**：
  - 安装 IK 分词器插件（elasticsearch-analysis-ik）
  - text 字段用 ik_max_word 细粒度分词，提高召回率
  - search 时用 ik_smart 粗粒度分词，提高准确率
  - 效果：BM25 检索的命中率从 30% 提升到 60%+

**坑四：RRF 的 k 值选不好，融合效果不稳定**
- **现象**：有时候向量检索结果排前面，有时候关键词排前面，调 k 值的时候不知道怎么选
- **原因**：k 值控制"排名的重要性"——k 越小，排名越靠前的文档权重越大；k 越大，越"民主"
- **解决**：
  - 用评测集跑不同 k 值的 Hit Rate 和 MRR，找最优值
  - 我们测了 k=30、60、100 三个值，k=60 时效果最好
  - k=60 也是业界的经验值，适合 50-100 条候选的场景
  - 经验：候选少（<20 条）用 k=30，候选多（>100 条）用 k=100

**坑五：向量库和 ES 数据不一致**
- **现象**：文档已经从 MySQL 删除了，但向量库和 ES 里还在，检索还能搜到
- **原因**：写入是三步操作（MySQL → Milvus → ES），中间某一步失败就不一致了
- **解决**：
  - 增加定时同步任务，每天凌晨全量比对一次，修复不一致
  - 写入失败时记录失败日志，后台重试
  - 检索结果返回后，再查一次 MySQL 确认存在（兜底，但增加延迟）
  - 长期方案：用消息队列做异步写入，保证最终一致性

**坑六：租户过滤导致检索变慢**
- **现象**：加了 tenant_id 过滤后，Milvus 检索速度变慢了
- **原因**：标量过滤需要先过滤再算向量距离，增加了计算量
- **解决**：
  - Milvus 的 partition key 功能——按 tenant_id 分区，查询时直接查对应分区
  - ES 的 routing 功能——按 tenant_id 路由到对应分片
  - 效果：多租户场景下检索速度提升 2-3 倍

**总结一下：**
- 混合检索不是"两个加起来就完事"，有很多细节要调
- 最重要的是**有评测集**——每次调整都跑一遍，用数据说话，不要凭感觉
- 其次是**监控**——线上的召回率、点击率、转化率，持续优化

### 2. Agent 工具调用出现循环调用、错误选择工具，状态机怎么拦截异常流程？

**口述版：**

> 我们做了**多层防护**来防止 Agent 出问题。核心是状态机 + 步数限制 + 异常捕获。

**Agent 状态机设计：**

**四个状态：**
- **IDLE**：空闲，等待用户输入
- **RUNNING**：运行中，正在执行 think-act 循环
- **FINISHED**：完成，任务结束
- **ERROR**：出错，异常终止

**状态转换：**
```
IDLE → RUNNING（用户发消息）
RUNNING → FINISHED（任务完成 / 调用 terminate 工具）
RUNNING → ERROR（异常 / 超过最大步数）
FINISHED → IDLE（reset，准备下一轮）
ERROR → IDLE（reset，准备下一轮）
```

**防止循环调用的机制：**

**① 最大步数限制（maxSteps）**
- 默认最多 10 步（think-act 算一步）
- 超过 maxSteps 就强制结束，状态设为 FINISHED
- 为什么是 10 步？——一般任务 3-5 步就够了，10 步是比较宽松的上限
- 防止无限循环把 Token 烧光

**② 重复工具调用检测**
- 检测连续 N 次调用同一个工具、参数也一样
- 比如连续 3 次调用 knowledgeSearchTool，查询词都一样
- 检测到就强制结束，返回"我好像卡住了，能换个方式描述你的问题吗？"

**③ 工具结果质量检测**
- 如果工具返回空结果、或者报错，给 Agent 一次重试机会
- 但如果连续 2 次同一个工具都失败，就换策略或者结束
- 不让 Agent 在一个失败的工具上死磕

**防止错误选择工具的机制：**

**① 系统提示词指导**
- NextStepPrompt 里明确写清楚：
  - 每个工具是干什么的、什么时候用
  - 不确定用哪个工具时怎么判断
  - 完成任务后要调用 terminate
- 好的提示词能减少 80% 的工具选择错误

**② 工具描述优化**
- 每个 @Tool 方法的 description 写得尽量清晰
- 包括：功能、参数含义、返回值格式、适用场景
- LLM 是根据 description 来选工具的，description 写得好，选错的概率就低

**③ 异常捕获 + 自我纠正**
- step() 方法里有 try-catch
- 工具调用抛异常时，把错误信息作为工具结果返回给 LLM
- 让 LLM 自己判断"刚才调用错了，换一个工具试试"
- 给 Agent 自我纠正的机会

**状态机的异常拦截流程：**

```
用户输入
  ↓
state = RUNNING
  ↓
step 1: think() → 有 toolCall？
  ├─ 否 → 直接回答 → state = FINISHED
  └─ 是 → act() → 执行工具
        ↓
      step 2: think() → ...
        ↓
      ...
        ↓
      step N:
        ├─ N > maxSteps → 强制结束 → state = FINISHED
        ├─ 连续重复调用 → 强制结束 → state = FINISHED
        ├─ 工具调用异常 → 错误信息返回给 LLM（自我纠正）
        └─ 调用 terminate → state = FINISHED
```

**其他防护机制：**

**④ 超时控制**
- 整个 Agent 会话有超时时间（比如 5 分钟）
- 超时就强制结束，防止挂死
- 用 SseEmitter 的超时机制

**⑤ 资源限制**
- Token 消耗限制——一次会话最多用多少 Token
- 工具调用频率限制——防止某个工具被疯狂调用
- 防止恶意用户或者 bug 导致资源耗尽

**⑥ 主动停止**
- 用户可以随时调用 stop 接口停止 Agent
- 前端点"停止"按钮 → 后端设置标志位 → Agent 检测到就结束
- 我们用的是 `AtomicBoolean running` 标志，每一步开始前检查

**遇到过的真实 case：**
- **循环调用搜索工具**：用户问了一个问题，Agent 搜了一次觉得不够，又搜，又搜... 最后被 maxSteps 拦下
  - 原因：系统提示词没写清楚"搜一次就够了"
  - 解决：改提示词 + 增加重复调用检测
- **选错工具**：用户问天气，Agent 调用了知识库搜索
  - 原因：天气工具的 description 写得不够清楚
  - 解决：优化工具 description + 增加示例

**经验总结：**
- Agent 不像传统程序那样"确定"，它会犯各种奇怪的错误
- 不能假设 Agent 总是做对的，必须有各种防护机制
- 状态机 + 步数限制 + 异常捕获，三层防护基本能覆盖大部分情况
- 最重要的是——**有日志、有监控**，出了问题能追溯

### 3. 定时任务 5 分钟轮询萃取记忆，同一用户多条对话并发，怎么避免重复萃取、数据脏写？

**口述版：**

> 我们从三个层面来保证：**数据库层面去重、应用层面锁、业务层面幂等**。

**第一层：数据库层面去重（最根本）**

**① source_session_id 唯一索引**
- `evolution_skill` 表的 `source_session_id` 字段加唯一索引
- 同一会话不可能重复插入两条技能记录
- 插入时如果报 DuplicateKeyException，说明已经萃取过了，直接跳过
- 这是最根本的保障——数据库层面保证不会重复

**② 去重查询（前置检查）**
- 定时任务扫描会话时，用 NOT IN 子查询排除已经萃取过的：
  ```sql
  WHERE conversation_id NOT IN (
    SELECT DISTINCT source_session_id FROM evolution_skill WHERE tenant_id = ?
  )
  ```
- 从源头就把已经处理过的会话过滤掉，不会进入萃取流程

**第二层：应用层面锁（防止并发）**

**① 分布式锁（Redis SETNX）**
- 定时任务开始时，先获取分布式锁
- 锁的 key：`lock:reflection:{tenantId}:{sessionId}`
- 只有拿到锁的实例才能处理这个会话
- 锁的过期时间：10 分钟（防止死锁）
- 防止部署多个实例时，同一个会话被多个实例同时处理

**② 异步线程池限流**
- 反思任务用独立的线程池（evolutionExecutor）
- 核心线程 1，最大线程 2，队列 100
- 即使有很多会话要处理，也不会一下子全跑起来
- 控制并发量，防止把数据库和 LLM 打挂

**第三层：业务层面幂等（兜底）**

**① 幂等的萃取操作**
- 即使真的重复执行了，结果也一样
- 因为 source_session_id 是唯一的，重复插入会失败
- 失败不影响其他任务，打个 warn 日志就行

**② 质量阈值过滤**
- 质量分 < 5 分的技能不入库
- 即使重复萃取，低质量的也不会被存进去
- 减少垃圾数据

**具体的执行流程：**

```
定时任务触发（每 5 分钟）
  ↓
获取全局分布式锁（防止多个实例同时跑）
  ↓
扫描符合条件的会话（空闲超时 / 总时长超限）
  ↓
排除已萃取的会话（NOT IN 子查询）
  ↓
LIMIT 20（限流）
  ↓
for each 会话:
  ↓
  获取会话级分布式锁（lock:reflection:{sessionId}）
  ├─ 获取失败 → 跳过（别的线程在处理）
  └─ 获取成功 → 继续
        ↓
      再次检查是否已萃取（双重检查）
      ├─ 已萃取 → 释放锁，跳过
      └─ 未萃取 → 执行 LLM 反思
            ↓
          质量过滤（≥ 5 分）
          ↓
          插入 MySQL（唯一索引兜底）
          ↓
          写入向量库
          ↓
          释放锁
```

**为什么需要这么多层？**
- 因为分布式系统里，什么都可能发生
- 网络抖动、服务重启、时钟漂移... 任何一层都可能出问题
- 多层防护，即使某一层失效了，下一层还能兜住

**遇到过的真实问题：**
- **问题**：服务重启时，正在执行的反思任务中断了，下次又重新跑
  - **解决**：source_session_id 唯一索引，重复插入会失败，不影响
- **问题**：两个实例同时扫描到同一个会话
  - **解决**：分布式锁，只有一个能拿到锁
- **问题**：锁过期了但任务还没跑完
  - **解决**：锁的过期时间设得比最长任务时间长，或者用"看门狗"自动续期

**数据脏写的预防：**
- 所有写操作都带 tenant_id 条件
- 更新操作用乐观锁（version 字段）
- 重要操作记录操作日志（谁、什么时候、改了什么）
- 定期做数据校验，发现不一致及时修复

### 4. 向量库数据量大后检索速度下降，分片、索引优化方案？

**口述版：**

> 向量检索的性能优化是个系统性工程，从索引、分片、缓存、硬件多个层面都可以优化。

**Milvus 层面的优化：**

**① 索引优化（最直接）**
- **选择合适的索引类型**：
  - IVF_FLAT：倒排文件，速度快，召回率稍低，适合大数据量
  - HNSW：层次化导航小世界，召回率高，内存占用大，适合中等数据量
  - DISKANN：磁盘索引，适合超大数据量，内存占用小，速度稍慢
- 我们用的是 HNSW，因为召回率要求高
- **索引参数调优**：
  - HNSW 的 M（每层连接数）：默认 16，越大召回率越高但内存越大
  - efConstruction（构建时的搜索范围）：默认 200，越大构建越慢但索引质量越高
  - ef（搜索时的搜索范围）：默认 10，越大召回率越高但越慢
  - 平衡：根据业务对召回率和延迟的要求来调

**② 分片优化**
- **按 tenant_id 分片**：
  - 每个租户一个 partition，查询时只查对应分区
  - 数据量小了，检索自然快了
  - Milvus 支持 partition key，自动分区
- **按时间分片**：
  - 冷数据（半年前）和热数据分开，常用的热数据单独一个 collection
  - 查询时优先查热数据，不够再查冷数据
  - 减少每次查询的数据量

**③ 缓存优化**
- **查询结果缓存**：
  - 高频查询的结果缓存到 Redis
  - 相同查询直接返回缓存，不用查向量库
  - 缓存过期时间：1 小时（根据数据更新频率调整）
- **向量缓存**：
  - Milvus 本身有缓存机制，常用的向量段会缓存在内存里
  - 保证内存足够，让热数据都在内存里

**④ 一致性级别调整**
- 从 STRONG 改成 EVENTUALLY（最终一致性）
- 读多写少的场景，最终一致性完全够用
- 读取性能能提升 20-30%
- 我们项目就是用的 EVENTUALLY

**Elasticsearch 层面的优化：**

**① 分片优化**
- 合理设置分片数——不是越多越好
- 每个分片 20-50GB 比较合适
- 按 tenant_id 路由（routing），同一个租户的数据在同一个分片
- 查询时指定 routing，只查一个分片，快很多

**② 索引优化**
- 只给需要搜索的字段建索引，不用的字段不索引
- text 字段的子字段（ik_smart / ik_max_word）按需创建
- 关闭不需要的功能：_source 过滤、关闭 _all 字段

**③ 查询优化**
- 用 filter 代替 query 做精确匹配（不计算评分，能缓存）
- 减少返回字段（_source 过滤）
- 避免深度分页，用 search_after

**架构层面的优化：**

**① 读写分离**
- 写操作走主节点，读操作走从节点
- 读请求可以水平扩展
- Milvus 和 ES 都支持读写分离

**② 冷热数据分离**
- 热数据（最近 3 个月）存高性能存储（SSD + 内存）
- 冷数据（3 个月前）存低成本存储（HDD）
- 查询时先查热数据，不够再查冷数据
- 大部分查询都命中热数据，性能好

**③ 多级检索**
- 第一层：Redis 缓存（最快，毫秒级）
- 第二层：热数据向量库（快，几十毫秒）
- 第三层：全量向量库（慢，几百毫秒）
- 逐层 fallback，大部分请求在第一层就返回了

**④ 硬件优化**
- 向量检索是计算密集型 + 内存密集型
- 内存越大越好——能把索引全放内存里最快
- SSD 比 HDD 快很多
- GPU 加速——如果预算够，GPU 向量检索能快 10 倍以上

**什么时候需要考虑这些优化？**
- 数据量 < 100 万条：不用优化，默认配置就够快
- 100 万 - 1000 万条：索引调优 + 缓存
- 1000 万 - 1 亿条：分片 + 读写分离 + 冷热分离
- > 1 亿条：分布式集群 + GPU 加速 + 专业架构

**我们项目的现状：**
- 数据量还不大（十万级）
- 目前用 HNSW 索引 + 最终一致性 + Redis 缓存
- 检索延迟在 50ms 以内，完全够用
- 已经预留了分片和冷热分离的架构设计，等数据量上来了再上

## 八、收尾反问环节（面试官最后让你提问）

> 反问环节不是走个过场——问得好能体现你的思考深度，也能帮你判断这个团队值不值得去。
> 原则：问真问题，别问"公司文化怎么样"这种假大空的；问具体的、有深度的，体现你做了功课。

### 1. 咱们 AI 宠物机器人目前的记忆架构是自研还是基于 Spring AI/LangChain？

**为什么问这个：**
- 了解技术栈——如果是自研，你去了可能要做更多底层工作；如果是基于框架，更多是业务层开发
- 体现你对技术选型的关注
- 可以顺势聊你对 Spring AI 的经验

**追问方向（如果面试官回答了）：**
- 如果是自研——"主要是哪些模块自研的？遇到过什么坑？"
- 如果是 Spring AI——"现在用的是哪个版本？Advisor 机制用得多吗？"
- 如果是 LangChain——"用的 Python 版还是 Java 版？多 Agent 协作是怎么实现的？"

---

### 2. 当前语音交互链路的延迟指标标准是多少，后续优化方向是什么？

**为什么问这个：**
- 了解团队对性能的重视程度——有明确指标的团队通常更专业
- 体现你对语音交互延迟问题的深入思考
- 可以聊你在流式响应、延迟优化方面的经验

**追问方向：**
- "现在首句响应延迟大概是多少？目标是多少？"
- "ASR 和 TTS 用的是哪家的？有没有考虑过流式 ASR？"
- "全链路流式改造做了吗？还是只有 LLM 是流式的？"
- "有没有做过弱网场景的优化？"

---

### 3. 团队现在 RAG 检索、Agent 智能体模块是分开维护还是一体化开发？

**为什么问这个：**
- 了解团队的组织架构和分工方式
- 判断你进去后是做全栈还是专注某一块
- 体现你对 RAG 和 Agent 都有了解，不是只会一块

**追问方向：**
- "RAG 的检索准确率现在大概是什么水平？怎么评估的？"
- "Agent 现在主要用什么模式？ReAct 还是 Plan-and-Execute？"
- "混合检索用的是什么方案？向量库选型是怎么考虑的？"
- "有没有做过 Agent 的自我反思 / 自我进化？"

---

### 备选问题（根据面试情况选 2-3 个问）

**关于业务：**
- "AI 宠物现在的用户画像是什么样的？主要是哪些人在用？"
- "产品的核心差异化是什么？和市面上其他 AI 宠物比有什么不一样？"
- "现在最大的业务挑战是什么？是用户增长还是留存还是变现？"

**关于团队：**
- "团队现在多少人？AI 方向有几个工程师？"
- "团队的技术栈主要是什么？Java 还是 Python 多？"
- "平时的开发流程是怎样的？敏捷吗？迭代周期大概多久？"

**关于技术挑战：**
- "目前技术上最大的难点是什么？是性能还是效果还是成本？"
- "大模型的成本压力大吗？有没有做过模型蒸馏或者量化？"
- "多模态（图像、语音、动作）的融合现在做到什么程度了？"

**关于成长：**
- "这个岗位的成长路径是什么样的？"
- "团队有没有技术分享、学习的氛围？"
- "新人进去一般先做什么？多久能独立负责模块？"

---

> **反问注意事项：**
> - 不要问太多，2-3 个就够了，多了显得你在拷问面试官
> - 不要问答案显而易见的问题（比如"公司是做什么的"——说明你没做功课）
> - 不要问薪资、福利、加班——这些留到 HR 面再问
> - 问完之后认真听，面试官的回答能帮你判断这个团队靠不靠谱
