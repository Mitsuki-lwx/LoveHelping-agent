三层分层架构，三层各自独立运作，通过异步管道串联。
用户画像层：存储跨轮次稳定事实（包括不变事实、验证过的偏好、当前话题焦点），在首次全量摘要时诞生，之后每轮都注入上下文。作用是阻止压缩导致关键事实丢失。
大文件占位替换层：单条消息超过阈值的大文件直接落盘，Prompt中仅保留结构化索引占位符。关键决策是在Prompt组装阶段就决定是否替换，保证Prompt Cache稳定。
全量摘要层：到达警戒线时异步触发全量摘要，禁止工具调用，生成后原子替换旧上下文，再回注最近的工具结果和原文，保证压缩点前后体验平滑。
对保真度要求极高的场景，可挂载第四层——向量数据库全量存储，用检索增强作为最终兜底，代价是检索延迟和可能导致语境断裂。

你理解的 Agent memory 经典框架是什么？它的发展趋势是什么，最头部的玩家在怎么做？
我理解为可以分成四层记忆，分为短期的上下文记忆，存事实的语义记忆比如知识库，能学到东西的情境记忆就是持久化的对话历史，规则性的程序性记忆比如工具调用的规则，流程的规则，这种分层是为了在读写速度、存储成本和可解释性之间做隔离。
趋势我认为是从怎么存到存哪里，从被动到主动，要学习要自进化，从多到精，多元化，压缩，走向平台化和可编辑，走向平台化的代价是延迟增加，可编辑的代价是状态爆炸，所以未来的记忆系统必须是一个可配置的，而不是一刀切。
头部玩家几乎都体现了从被动存储向主动管理、自动演化的记忆机制转变。有选择外挂式记忆或者模型内生记忆的，资本加速进场，注重基础设施建设比如云平台，其实就是都在比谁能用最低延迟把最准的记忆喂进上下文。

定期复盘：
分五层
第一层是调度层，每天九点有调度器唤醒负责的agent，圈好所需复盘的内容，过滤没有价值的信息
第二层是读取层，从记忆库分类拉取不同维度的信息，任务进度用时间窗口查询，异常用关键词精确匹配，用户画像用向量相似度检索，环境变量用结构化SQL查询。多路并行检索，最后统一汇总，比如任务进度，异常，用户画像，环境变量
第三层是推理层，按顺序进行事实的归纳总结，然后是对比过去的差距，最后是提出建议和方向
第四层是管理层，写回记忆系统，给新的复盘加标记以及更高优先级，给久的更低优先级
第五层是交付层，给用户简报，主要是给出进度结论以及建议，并接受用户反馈并且发给第三层作为明天的新约束。

如果 session state 为 busy，此时用户又发来新消息，或者异步工具完成事件也到达，runtime 应该如何处理？
session state 为 busy时，每个 session 有自己的队列，根据 session_id 分发事件到对应的队列，将用户消息放入 session 专属的消息队列，等当前任务完成后按 顺序取出执行。然后给同时给用户一个即时反馈，如果是同步 HTTP 接口，可以返回 202 ，并提供轮询或 WebSocket 推送结果。
异步工具完成事件也到达同样放入 session 的消息队列，等当前任务完成后执行，并且工具回调应该排在新用户消息前面


.Claude Code 的工具输出方式和国内 GLM / 豆包等 OpenAI-compatible function calling 有什么不同？他们各自这样设计的优缺点是什么？
Claude Code的设计哲学是工具即运行时，工具不是模型的外部附件，而是Agent认知能力的内置模块。所有工具调用都经过一个统一的14步管道，强制进行权限检查、参数校验、结果审计。这样的好处是安全性极强，特别适合需要长时间运行、高自主性的复杂Agent。缺点就是太重，学习曲线陡，而且跟专有协议强绑定。
而GLM、豆包走的OpenAI兼容路线，是模型只负责把自然语言翻译成结构化的`tool_calls`，执行完全交给开发者。好处是轻量、接入快、跨模型迁移成本低，特别适合标准化的API集成场景。缺点是工具管理的职责全部落到开发者身上，要自己实现管理。
所以我的判断是：如果要构建AI程序员这种深度嵌入系统的高复杂Agent，Claude Code的强管控更适合；如果你要做快速迭代的或需要跨模型兼容，OpenAI兼容范式是更好的选择。两者没有绝对优劣，是管控力和灵活性的取舍。
