架构总览：一条请求走过的路

关键设计：所有聊天端点（含 /LoveManus）都收敛到 ChatEntry 单一入口——护栏、限流、并发闸门、trace 串联都在这里，避免各端点各做一套。唯一的例外是沙盘 /sandbox/chat（直调 GraphRunner，已补 L3 护栏）。

模块地图：每段源码在做什么

controller 接口层

8 个控制器，HTTP 入口。聊天类端点全部转交 ChatEntry，其余走各 Service。

AiControllerLove_app/chat/sync、sse、sse_emitter、sse/rag、LoveManus + task/stop（已加归属校验）
AuthControllerregister/login/me/account；注册强制 role=USER（防自封 ADMIN）
MemoryController会话 register/列表/历史/计数/清除/反馈 + /admin/conversations；敏感端点带 checkOwnership
MemoryFactsController事实的查/改/删（用户可纠正记忆）
SandboxController · MediaController · VoteController · InsightController沙盘会话、图片上传、技能投票/审核、洞察分析

infrastructure/orchestration 编排核心

请求的中枢：入口收敛 + 状态图路由 + 真流式回传。想读懂主链路，先读这里。

ChatEntry统一入口：prompt-leak 探测 → 护栏 L3 → 限流 → 在线闸门 → 组装图输入 → 桥接 SSE（90s orTimeout）
ChatExecutor唯一汇聚点：SYSTEM_PROMPT + 记忆块 + 技能块 → LLM；话术三级 marker 切片（🛡️⚡🌸）
OrchestrationGraphStateGraph 装配；classify 优先级：offTopic > forceAgent > sandbox > vision > simple > needTools > normal
GraphRunner执行门面：supplyAsync → invoke → 落库（agent/vision）→ trace 日志 → Langfuse 上报
CapabilityRouter纯正则零 LLM：needTools / isAdviceRequest / isOffTopic / isSimpleQuestion
节点类QuickAnswer / NormalChat / GraphVision / SandboxChat / OffTopic / AgentLlm ⇄ AgentTool / Check
StreamRegistrychatId → SSE sink 的注册表（不用 state 传引用，避免 RedisSaver 序列化失败）
ToolResolver · AgentToolPolicy本地 4 工具 + MCP 工具合并（MCP 挂了降级本地）；按能力域白名单过滤

infrastructure/ai 模型网关

所有 LLM 调用都经过这里的装饰器，负责重试、降级与成本埋点。

LlmGateway（@Primary ChatModel）call()：重试 → 备模型降级 → 空回复防御；4xx 不重试、429 尊重 Retry-After；记 llm.call / llm.tokens
VisionChatClient手写 RestClient 调 /v1/chat/completions，图片转 base64 data URL
AgentMetrics / GuardrailInterceptor无装配点（ReactAgent 已移除）——死代码

harness 治理护栏

安全底线：规则级拦截优先于模型遵从性（测得 glm-flash 压不住时靠它兜底）。

GuardrailRuleService启动时从 guardrail_rule 表加载规则并预编译；check() 返回最高 level；L3 = 硬阻断
GuardrailAdvisorChatClient 最内层 advisor：输入 L3 → 转介/婉拒文案；输出命中 → 替换 BLOCK_TEXT
OutputGuardrail两类拦截：① 用户提自残词但回复缺转介 → 补危机话术；② 命中"报复/跟踪/查手机"等有害建议词
MyLoggerAdvisor最外层：打印请求/响应全文（含 system prompt 泄露排查用途）

memory 长期记忆

「落库 → 萃取 → 召回 → 注入」闭环，记住用户是谁、经历过什么。

MessageChatMemorySpring AI ChatMemory 实现：消息加密 + HMAC + prompt_version 落 message 表
MemoryExtractionScheduler每 30min 扫「有归属、有消息、无摘要」的会话 → 萃取（受预算约束）
MemoryExtractorLLM 抽取摘要 + 事实（画像必抽 / 建议禁抽 / confidence 8-9 示例）——今天刚精化过
MemoryStore持久化 + 上下文组装：摘要覆盖更新 + 事实去重（≥7 分 ACTIVE）；编辑即转正；生命周期清理
MemoryVectorStorepgvector 语义通道：topK×3 放大后按 userId 过滤
Desensitizer规则脱敏姓名/手机/住址

evolution 自我进化

从真实对话里沉淀「AI 该怎么说」的方法论（区别于记忆的「用户是谁」）。

ReflectionScheduler每 5min 挑未反思会话（空闲超时 或 总时长超限）
SkillReflector@Async + LLM 反思：点赞抽正面经验、点踩抽「Avoid…」教训；无产出插 skip-mark 防重复烧配额
SkillIngestor落库为 PENDING（人工审核）→ 审核通过后向量化
SkillRetriever放大召回 → 只留 APPROVED → 拼【已学经验】注入 prompt，打点 skill.injection
SessionTracker仅打 DEBUG 日志，触发逻辑已迁走——死代码

rag 知识库管线

Spring AI 官方 RAG 管线（advisor 契约），只服务 normal/sandbox 节点的上下文注入。

RagAdvisorConfig装配 RetrievalAugmentationAdvisor：检索器 + 查询增强 + 重排后处理
ParentChildDocumentRetriever混合召回：向量 topN*3 + jieba 关键词 → RRF 融合（k=60）
ParentChildDocumentTransformer实际是 overlap 扁平切块（400 字 + 80 尾句重叠），父子经评测判定为过度设计
LoveAppDocumentLoader · KnowledgeBaseIncrementalSync扫 classpath:document/*.md；按 doc_hash 增量 added/replaced/skipped
rerank/*LLM 重排（编号解析 + 失败降级原序）；QueryRewriter 实测负收益已关闭

retrieval 检索门面

手写检索门面（不经 advisor），给 agent 工具、技能检索、记忆向量库直接调用。

HybridRetrievalServicesearch()：向量 + pg_trgm 整句相似度 → RRF；打点 rag.hit / rag.empty
RetrieverType · HybridRetrievalProperties枚举/配置；Javadoc 仍描述已移除的 Milvus+ES，实际只有 pgvector

链路一：一次聊天的完整旅程

① AiController
收下 prompt/chatId，转 ChatEntry.chat()（LoveManus 走 forceAgent=true）
② TenantInterceptor
解析 JWT → TenantContext（匿名则三字段为 null，下游各自兜底）
③ ChatEntry 三道闸
prompt-leak 规则短路 → 护栏 L3 抛 4001（自伤走转介话术）→ 限流 → 在线并发闸门 4003
④ GraphRunner.runAsync
恢复父 trace 上下文 → 线程池里 invoke 图（90s 超时保护）
⑤ classify 路由
offTopic > forceAgent > sandbox > vision > simple > needTools > normal
⑥ 分支执行
quick/normal 走 ChatExecutor（带 RAG advisor）；agent 走 LLM ⇄ 工具循环（≤15 步，工具事件实时推 🔧）
⑦ ChatExecutor 组装
SYSTEM_PROMPT + <user_memory> + 【已学经验】 + 检索上下文 → LlmGateway
⑧ CheckNode → SSE
输出复检（L3 替换文案）→ 增量经 StreamSink 实时回传 → complete 时释放闸门

链路二：记忆闭环（记住你是谁）

落库
MessageChatMemoryAdvisor → MessageChatMemory.add：加密 + HMAC + prompt_version → message 表
萃取（每 30min）
调度器挑「有归属 + 有消息 + 无摘要」会话 → MemoryExtractor LLM 抽取摘要与事实
存储
摘要 → conversation_summary（覆盖更新 + 向量化）；事实 → user_memory（≥7 分 ACTIVE，否则 CANDIDATE）
召回注入
下次对话 assembleContext → retrieveAsContext(userId, query) → 拼进 system prompt
纠正
用户编辑事实即转正（confidence=10）；清除会话连坐删摘要与事实（不会"已清还记着"）

三张表的分工

表角色
message原始逐条消息真源（加密、软删、带 feedback/prompt_version）——窗口上下文与萃取的输入
conversation_summary会话级压缩摘要（按会话覆盖更新）——跨会话上下文与向量召回源
user_memory用户级跨会话稳定事实（category/confidence/status/hit_count/ttl，用户可改）

链路三：进化闭环（学会怎么说话）

选会话（每 5min）
ReflectionScheduler 挑「未反思过」且（空闲超时 或 总时长超限）的会话，受预算约束
LLM 反思
SkillReflector 结合点赞/点踩：赞→正面经验，踩→「Avoid…」反面教训；过滤 qualityScore 达标项
入库待审
SkillIngestor 以 PENDING 落库（不自动向量化）；无产出插 is_active=0 skip-mark 防重复烧配额
审核 → 向量化
/evolution/skill/{id}/audit 审核通过 → SkillIngestor.vectorize 写入 pgvector
注入回答
SkillRetriever 放大召回 → 只留 APPROVED → 拼【已学经验】进 prompt
记忆 vs 进化：记忆是「关于用户的事实」（user 维度、用户可改、有 ttl）；进化是「关于AI 该怎么说的方法论」（tenant 维度、LLM 产出、人工审核、按语义召回）。

RAG 为什么有两套（rag/ 与 retrieval/）

rag/（生成侧管线）retrieval/（工具侧门面）
契约实现 Spring AI 的 DocumentRetriever / QueryTransformer / DocumentPostProcessor普通方法，无框架契约
被调用方只能由 RetrievalAugmentationAdvisor 在 preretrieval→retrieval→postretrieval 管线里调KnowledgeSearchTool、SkillRetriever、MemoryVectorStore 直接调
服务场景normal/sandbox 节点的上下文注入agent 工具、技能检索、记忆语义检索
策略差异overlap 切块 + 查询改写 + jieba 关键词 + RRF + LLM 重排pg_trgm 整句相似度 + 向量 → RRF，无改写/重排开销
结论同一张 vector_store 表上的历史双轨：advisor 管线无法复用方法式门面，门面也不需要 advisor 的改写/重排开销。改动检索时务必确认改的是哪一条。
